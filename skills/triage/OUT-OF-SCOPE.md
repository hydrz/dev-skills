# 不在范围内知识库

仓库中的 `.out-of-scope/` 目录长期记录被否决的功能请求。它有两个用途：

1. **保留决策记录**：issue 关闭后，功能被否决的理由不会丢失
2. **去重**：新 issue 与之前的否决相匹配时，skill 可以直接展示之前的决定，避免重新争论

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件。请求同一件事的多个 issue 归入同一个文件。

## 文件格式

文件用易读的方式编写，更像一篇简短的设计文档，而不是数据库条目。用段落、代码和示例把理由讲清楚，让第一次看到它的人也能理解。

````markdown
# 深色模式

本项目不支持深色模式或面向用户的主题切换。

## 为什么不在范围内

渲染管线假设 `ThemeConfig` 中只定义了一套调色板。支持多主题需要：

- 一个包裹整个组件树的主题上下文提供者
- 每个组件按主题解析样式
- 保存用户主题偏好的持久化层

这是一次重大的架构改动，与项目专注内容创作的定位不符。主题应由嵌入或再分发产物的下游使用者处理。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，构建时解析
  fonts: FontStack;
}
```

## 此前的请求

- #42：“加个深色模式”
- #87：“为无障碍提供夜间主题”
- #134：“深色主题选项”
````

### 文件命名

使用简短、描述性的 kebab-case 概念名，例如 `dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称要足够清楚，让浏览目录的人不打开文件就知道被否决的是什么。

### 编写理由

理由要有实质内容：不是“我们不想要”，而是说明为什么。好的理由会引用：

- 项目范围或理念（“本项目专注 X；主题由下游处理”）
- 技术约束（“支持它需要 Y，这与我们的 Z 架构冲突”）
- 战略决定（“我们选择了 A 而不是 B，因为……”）

理由要能长期成立。暂时性的情况（“我们现在太忙”）不是真正的否决，而是推迟，不写进这里。

## 何时检查 `.out-of-scope/`

分诊时（第 1 步：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否与某个已有的不在范围内概念匹配
- 按概念相似度匹配，而不是按关键词：“夜间主题”应匹配 `dark-mode.md`
- 匹配到时告诉维护者：“这与 `.out-of-scope/dark-mode.md` 相似。我们之前否决它是因为[理由]。你现在仍然这样认为吗？”

维护者可能：

- **确认**：把新 issue 加到已有文件的“此前的请求”列表，然后关闭
- **重新考虑**：删除或更新该文件，issue 进入正常分诊
- **认为不匹配**：两个 issue 相关但不同，进入正常分诊

## 何时写入 `.out-of-scope/`

只在 **enhancement**（不是 bug）以 `wontfix` *被否决*时写入。这同样适用于 enhancement 类的 PR 和 issue：被否决的 PR 也记录在这里，避免同样的请求以新代码的形式再次出现。

因为**已实现**而以 `wontfix` 关闭的，不写入这里。那是已经实现的功能，不是被否决的请求；记录下来会让去重检查出现错误的否决记录。关闭评论改为指出该功能在哪里。

流程：

1. 维护者判定某个功能请求不在范围内
2. 检查是否已有匹配的 `.out-of-scope/` 文件
3. 有：把新 issue 追加到“此前的请求”列表
4. 没有：新建文件，写上概念名、决定、理由和第一个请求
5. 在 issue 上发评论说明决定，并提及对应的 `.out-of-scope/` 文件
6. 以 `wontfix` 标签关闭 issue

## 更新或删除

维护者对之前否决的概念改变主意时：

- 删除对应的 `.out-of-scope/` 文件
- 无需重新打开旧 issue，它们是历史记录
- 触发重新考虑的新 issue 进入正常分诊
