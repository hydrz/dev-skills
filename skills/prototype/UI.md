# UI 原型

在同一个路由上生成**几个差异明显的 UI 变体**，通过底部浮动切换条切换。用户在浏览器中逐个查看变体，选出一个（或组合多个变体的优点），其余的丢弃。

如果问题涉及逻辑或状态，而不是界面外观，选错分支了。使用 [LOGIC.md](LOGIC.md)。

## 适用场景

- “这个页面应该是什么样子？”
- “确定之前，我想看看这个仪表盘的几种方案。”
- “试试设置页的其他布局。”
- 任何用户原本要花一天时间在脑中比较几个模糊方案的时候。

## 两种子形态：强烈建议选择子形态 A

UI 原型只有**放在应用的真实环境中**才容易判断：真实的页头、真实的侧栏、真实的数据、真实的信息密度。孤立的一次性路由缺少这些上下文，每个变体单独看起来都还不错。只要有合适的现有页面能承载变体，默认使用子形态 A。只有原型确实找不到合适的宿主页面时，才使用子形态 B。

### 子形态 A：修改现有页面（优先）

路由已经存在。变体渲染在**同一个路由**上，由 `?variant=` 查询参数控制。保留现有的数据获取、参数和鉴权，只替换渲染部分。除非有具体理由，否则默认使用这种方式。

如果要做原型的内容还没有页面，但*自然属于某个现有页面*（仪表盘中的新区块、设置页中的新卡片、现有流程中的新步骤），也属于子形态 A：把变体放在宿主页面中。

### 子形态 B：新建页面（最后手段）

只在要做原型的内容确实无法放入任何现有页面时使用（例如全新的顶层界面，或无法合理嵌入其他地方的流程）。

按照项目现有的路由约定创建一个**一次性路由**，不另建顶层结构。命名要让人一眼看出这是原型（例如在路径或文件名中包含 `prototype`）。同样使用 `?variant=`。

决定使用子形态 B 之前再确认一次：真的没有现有页面可以承载吗？空白路由会掩盖一些在真实页面中才会暴露的设计问题。

两种子形态使用完全相同的浮动切换条。

## 过程

### 1. 写下问题，确定变体数量

默认 **3 个变体**。超过 5 个后，变体之间很难保持明显差异，只会增加干扰，所以上限是 5 个。

用一行写下计划，放在原型位置或文件顶部的注释中：

> “设置页的三个变体，通过 `?variant=` 切换，位于现有的 `/settings` 路由上。”

无论用户是否在场提出反对意见，这行计划都有用。

### 2. 生成差异明显的变体

逐个起草变体。每个变体都要遵守：

- 页面的用途和它能获取的数据。
- 项目的组件库或样式体系（TailwindCSS、shadcn、MUI、纯 CSS，项目用什么就用什么）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**在结构上不同**：不同的布局、不同的信息层级、不同的主要交互方式，而不只是颜色不同。三个略有调整的卡片网格不是 UI 原型，只是壁纸。两份草稿过于相似时，带着明确要求（例如“不要使用卡片网格”）重做其中一份。

### 3. 接入切换逻辑

在路由上创建一个切换组件：

```tsx
// 伪代码，按项目框架调整
const variant = searchParams.get("variant") ?? "A";
return (
  <>
    {variant === "A" && <VariantA {...data} />}
    {variant === "B" && <VariantB {...data} />}
    {variant === "C" && <VariantC {...data} />}
    <PrototypeSwitcher variants={["A", "B", "C"]} current={variant} />
  </>
);
```

子形态 A（现有页面）：现有的数据获取全部保留在切换组件之上，每个变体只替换渲染的子树。

子形态 B（新页面）：在 `/prototype/<名称>` 下的一次性路由中使用同一个切换组件。

### 4. 制作浮动切换条

在屏幕底部居中放置一个小的固定定位切换条，包含三部分：

- **左箭头**：切换到上一个变体（循环）。
- **变体标签**：显示当前变体的键；变体有导出名称时一并显示，例如 `B（侧栏布局）`。
- **右箭头**：切换到下一个变体（循环）。

行为：

- 点击箭头时，使用框架的路由功能更新 URL 查询参数（Next 用 `router.replace`，React Router 用 `navigate` 等），让变体可以分享、刷新后不丢失。
- 键盘：`←` 和 `→` 也可以切换。焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 上时，方向键保持原本的行为。
- 视觉上与页面明显区分（例如高对比度胶囊形状、轻微阴影），让人一眼看出它不属于被评估的设计。
- 生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查控制，这样即使原型被误合并，用户也看不到切换条。

切换条做成共享组件，两种子形态都可以复用，放在项目存放共享 UI 的位置。

### 5. 交给用户

提供 URL（以及 `?variant=` 的各个取值）。用户会在方便时查看。最有价值的反馈通常是 **“我想要 B 的页头配 C 的侧栏”**，这才是用户真正想要的设计。

### 6. 保存结论并清理

某个变体胜出后，先保存结论（选择了哪个变体、为什么），然后按 [SKILL.md](SKILL.md) 中的方式保存原型。把胜出的变体整合进正式代码，其余变体移到一次性分支，不留在主干：

- **子形态 A**：把胜出的变体整合进现有页面；从主干删除落选变体和切换条。
- **子形态 B**：把胜出的变体升级为正式路由；从主干删除一次性路由和切换条。

所有变体都是一手资料，所以放进一次性分支保存，而不是直接删除；留在主干中的变体组件和切换条很快会过时，还会误导下一位阅读代码的人。

## 反模式

- **仅在颜色或文案上有微调的变体。** 那是微调，不是原型。真正的变体在结构上必须不同。
- **变体之间共享过多代码。** 共享一个 `<Header>` 可以，共享一个 `<Layout>` 就失去了意义。每个变体都应该能自由改变布局。
- **将变体连向真实的修改操作。** 变体只读即可。需要写操作时指向桩实现：问题是“界面应该是什么样子”，而不是“后端能否工作”。
- **把原型直接提升为生产代码。** 变体代码是在原型约束下写的（没有测试、错误处理最少），整合进正式代码时必须按生产标准重写。
