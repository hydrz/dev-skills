# 交付收尾与发布就绪

处于开发实现（`implement`）、代码评审（`code-review`）与完成验证（`verifying-completion`）之后，在代码真正上线或部署前执行。

**核心目标：** 门禁复核 → 场景自适应交割 → 现场安全清理 → 发布物料与上线就绪核验。

是否集成、如何集成由用户决定。你负责把选项与状态说明清楚，并防范未经验证的代码直接流入主干或线上。

## 1. 门禁与状态复核

收尾之前必须先获得真实证据，绝不在假设或推测中推进：

1. **未提交变更检查**：运行 `git status --porcelain`。若存在未暂存或未提交的修改，先提示用户提交或妥善处理，避免污染收尾上下文。
2. **测试门禁复核**：遵循 `verifying-completion` skill，重新完整运行项目的全量测试套件并阅读输出。**测试失败则立即停止**，测试通过（0 失败）方可继续。
3. **评审遗留检查**：若经历了代码评审（`code-review`），核实所有“严重”与“重要”级别的评审意见是否均已在当前分支上解决。

## 2. 识别环境与场景分流

```bash
GIT_DIR=$(git rev-parse --path-format=absolute --git-dir)
GIT_COMMON=$(git rev-parse --path-format=absolute --git-common-dir)
WORKTREE_PATH=$(git rev-parse --show-toplevel)
CURRENT_BRANCH=$(git branch --show-current)
```

确认基线分支（默认为 `main` 或父任务分支）。根据当前 Git 状态与远程协作上下文，自适应分流为以下三种交付场景：

---

### 场景 1：本地直合交付（Local Direct Landing）

**适用条件**：单人开发、小步迭代或无需 PR 评审的代码交付。

**执行步骤**：

1. **主干合并**：切换到主仓库根目录并切回基线分支，拉取最新代码并合并功能分支：
   ```bash
   git checkout <基线分支>
   git pull
   git merge <功能分支>
   ```
2. **合并冲突处理**：若发生冲突，自动调用 `resolving-merge-conflicts` skill 协助分析解决；无法确认时保留现场并请求用户决策，绝不强行推进。
3. **合并后回归测试**：在基线分支上重新运行完整测试套件。**测试失败立即停止**，保留现场并调查，绝不继续清理或推送到远程。
4. **清理现场**：测试通过后，按 [CLEANUP.md](CLEANUP.md) 移除临时工作树并删除已合并的本地功能分支：
   ```bash
   git branch -d <功能分支>
   ```
5. **进入第 4 步发布就绪准备**。

---

### 场景 2：提交评审交付（Push & PR Delivery）

**适用条件**：团队协作、需同行评审或 CI 门禁核验的代码交付。

**执行步骤**：

1. **推送远程**：推送功能分支至远程仓库：
   ```bash
   git push -u origin <功能分支>
   ```
2. **联动结构化 PR**：调用 `/pr` skill 撰写结构化 PR 描述（包含算法伪代码或调用树摘要、Before/After 运行证据与单向门/爆炸半径分析）。
3. **附带变更说明**：检查项目中是否使用 Changesets 等版本工具；若有，在提交 PR 时一并附带变更集（Changeset）说明文件。
4. **保留现场等待审查**：**绝对保留当前工作树与本地分支**，用户与 agent 后续需在此工作区中根据评审反馈继续修改。把 PR 链接报告给用户。

---

### 场景 3：评审后收口与发版就绪（Post-Review Landing & Release）

**适用条件**：远程 PR 已经在 GitHub/GitLab 获得批准并合并入主干，或者本地分支已通过远程审核待最后收尾。

**执行步骤**：

1. **同步最新主干**：切换到主仓库根目录的基线分支，拉取包含 PR 的最新提交：
   ```bash
   git checkout <基线分支>
   git pull origin <基线分支>
   ```
2. **清理本地残留**：安全删除已合入的本地旧功能分支与关联工作树（见 [CLEANUP.md](CLEANUP.md)）。
3. **进入第 4 步发布就绪准备**。

---

## 3. 现场丢弃保障

只有用户明确提出丢弃工作时，才进入销毁流程。先展示待销毁影响并等待用户确认：

```text
这将永久删除：
- 分支 <名称>
- 全部提交：<提交列表>
- 工作树 <路径>

输入 discard 确认。
```

等待用户输入确切的 `discard`。收到后，按 [CLEANUP.md](CLEANUP.md) 执行强制清理与分支删除。

## 4. 上线前就绪核验（Release Readiness）

代码合入主干后，在真正上线或发布前，逐项核对发布就绪清单：

1. **版本与变更记录**：
   - 是否已包含对应的变更集（Changeset）或已更新 `CHANGELOG.md`？
   - 若项目配置了自动化版本 PR（如 Changesets 机器人），提醒用户下一步只需审阅并合并自动生成的 `chore: version skills` PR。
2. **环境与配置核验**：
   - 本次改动是否引入了新的环境变量、配置项或第三方服务密钥？
   - 是否更新了 `.env.example` 或配置向导（`wizard`）？
3. **数据库与数据迁移**：
   - 是否包含数据库迁移脚本（Migrations）？
   - 生产部署前是否需要先执行迁移，还是向下兼容的扩展-迁移-收缩（Expand & Contract）结构？
4. **明确指示下一步行动（Next Steps）**：
   - 向用户清晰汇报交付总结与线上就绪状态；
   - 指出正确的上线或发布命令（例如：“在 GitHub 上合并 Version PR”、“触发 release 流水线”或“运行部署脚本”）；
   - **严格守则**：除非用户明确指示且符合该仓库流水线规范，否则**严禁在本地直接向保护的 `main` 分支随意推送越权提交、私自打 Git Tag 或创建 GitHub Release**。

## 常见借口与对应事实

| 借口                                    | 事实                                                                                                |
| :-------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| “实现时测试刚跑过，收尾不用重跑”        | 收尾时的代码往往经历了评审修复与整理。必须对即将交付的代码重新运行并验证证据。                      |
| “PR 创建完了，工作树可以删了”           | PR 评审过程中通常会有修改意见。工作未最终合入前必须保留工作树。                                     |
| “分支合并直接走本地最快”                | 涉及团队协作和 CI 检查时，必须走 PR 交付；只有明确授权或单人模式才走本地直合。                      |
| “既然合并完了，我顺便把 tag 打了推上去” | 许多项目使用自动化 Release 流水线。擅自在本地打 tag 会打乱 CI 发布机制；必须遵循项目 release 规范。 |
| “测试失败只是偶发网络抖动，直接合入”    | 合并后测试失败必须立即中止流程并保留现场，绝不将不可信代码推向主干。                                |
