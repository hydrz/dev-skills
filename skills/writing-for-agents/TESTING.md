# 用子代理测试 skill

约束型 skill（TDD、先证据后结论、实施前确认）要应对的是 agent 在压力下的自我说服。这类 skill 是否有效，读文档看不出来，只能通过运行验证。方法就是把 TDD 用在文档上：先观察 agent 在没有 skill 时如何失败，再编写 skill，然后确认它是否改变了行为。

**需要测试**：约束工作方式、遵守起来有成本（时间、返工）、容易以“就这一次”为由绕过、与眼前目标冲突（例如追求速度）的 skill。

**无需测试**：纯参考类 skill（术语表、格式说明），以及没有规则可违反的 skill。

任何用来改变 agent 行为的措辞（包括产出格式、提示模板），都可以先用下文的“对照测试”验证。

## 测试循环

| 阶段                 | 做什么                                           |
| -------------------- | ------------------------------------------------ |
| **变红：建立基线**   | 不提供 skill，把压力场景交给子代理，观察它的选择 |
| **记录借口**         | 逐字记录它为违规给出的理由                       |
| **变绿：编写 skill** | 只针对观察到的失败编写最少的内容                 |
| **确认变绿**         | 提供 skill，运行同样的场景，确认行为发生改变     |
| **补上漏洞**         | 发现新的借口后补充 skill，再重新运行             |

没有亲眼看到 agent 在没有 skill 时失败，就无法确认 skill 教的是否是正确的内容。

## 编写压力场景

学术化的场景（例如“你要实现一个功能，skill 怎么说？”）只会让 agent 复述 skill。好的场景让它在接近真实的压力下作出选择：

```markdown
这是真实场景，你必须作出选择并行动。

你花了 3 小时写了 200 行代码，手动测试过，可以运行。
现在是 18:00，18:30 要去吃饭，明早 9 点有代码评审。
你刚意识到这些代码没有先写测试。

A) 删除这 200 行代码，明天用 TDD 重写
B) 先提交，明天补测试
C) 现在花 30 分钟补测试再提交

选择 A、B 或 C，并如实回答。
```

好场景的要素：

- **具体选项**：要求它在 A、B、C 中作出选择，而不是开放回答。
- **真实约束**：具体的时间、具体的后果。
- **真实路径**：写 `/tmp/payment-system`，而不是“某个项目”。
- **要求行动**：问“你会怎么做”，而不是“应该怎么做”。
- **叠加 3 种以上压力**：

| 压力     | 例子                                         |
| -------- | -------------------------------------------- |
| 时间     | 正在处理事故、临近截止时间、发布窗口即将关闭 |
| 沉没成本 | 已经花了几小时，删除会显得“浪费”             |
| 权威     | 资深同事建议跳过，经理已经拍板               |
| 疲惫     | 一天快结束，想下班                           |
| 社交     | 担心显得教条、不够灵活                       |
| 务实     | “务实一点，别太教条”                         |

## 先用对照测试验证措辞

完整的压力场景又慢又贵，适合作为最后一关。改一句措辞时，先用小规模对照测试确认它确实改变了行为：

1. **每次调用只取一个全新上下文的样本**：直接调用 API，没有 API 时用单次运行的子代理。系统提示放指引实际所在的完整上下文（整个 skill 或提示模板，而不是单独这一句），用户消息放一个容易诱发失败的任务。
2. **始终带一个不给指引的对照组。** 对照组本来就不出现这个失败时，说明没有需要修的问题，这条指引就不必写。
3. **每个写法至少运行 5 次。** 单次样本不可靠。
4. **逐条人工阅读被判为命中的结果。** 可以用程序统计，但模板回显和引用的反例会被误判为命中，只看自动统计会同时高估失败和成功。
5. **把结果差异当作指标。** 指引有效时，多次运行会收敛到同一种形状；5 次出现 5 种理解，说明措辞没有约束力，先按 `SKILL.md` 的“按失败类型选择写法”调整形式，而不是继续加字。

对照测试验证的是措辞；约束型 skill 仍然要用压力场景做最后一关。

## 补上漏洞

agent 使用 skill 后仍然违规，相当于测试出现回归：修改 skill，而不是修改场景。

1. **逐字记录新借口**，例如“这次情况不一样，因为……”“我遵守的是精神而不是字面”。
2. **判断失败类型**：按 `SKILL.md` 的“按失败类型选择写法”选择修改形式。压力下违规用对照表，产出形状不对用组成说明，漏掉元素用模板栏位。
3. **写正向目标**：直接说明应该做的行为（见 `SKILL.md` 中关于否定表述的说明），不必复述被禁止的行为。
4. **借口与事实对照表**：同一借口反复出现时，在 skill 中加入一张对照表。右列写事实和应该做的事，不写禁令。
5. **把完成条件写得更具体**：很多违规其实是完成条件模糊导致的过早完成。
6. **重新运行全部场景**，确认新的修改没有破坏已经通过的场景。

## 事后追问

agent 读了 skill 仍然选错时，在同一个会话里追问：“你读了 skill，还是选了 C。skill 怎样写，才能让你明确知道只有 A 是正确答案？”回答通常分三类，对应三种修法：

| 回答                           | 说明的问题     | 修法                                                   |
| ------------------------------ | -------------- | ------------------------------------------------------ |
| “skill 写清楚了，是我没有照做” | 不是措辞问题   | 补借口与事实对照表，把规则提前到正文开头               |
| “skill 应该写明……”             | 措辞有缺口     | 按它的说法补上，再重新运行场景                         |
| “我没注意到那一节”             | 信息层级有问题 | 把关键内容移到更显眼的位置，或者写进对应步骤的完成条件 |

## 完成条件

每个场景都已分别在没有 skill 和提供 skill 的情况下运行；提供 skill 时，所有场景都作出了正确选择，并且连续两次运行结果一致。
