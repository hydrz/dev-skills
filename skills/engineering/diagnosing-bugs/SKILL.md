# 诊断 bug

对付疑难 bug 的纪律。按阶段推进；跳过某个阶段时，明确说出理由。

探索代码库时，读 `CONTEXT.md`（如果有）建立对相关模块的清晰心智模型，并查看相关区域的 ADR。

## 脱敏

本 skill 会让你展示命令、输出和抓取的产物。**先把每个密钥脱敏**：原位写 `<已脱敏>`。回路基于环境变量构建，让凭据留在环境里，不出现在你展示的内容里。抓取的产物常带认证头：只引用携带信号的那几行。

脱敏后的输出不足以诊断时，说明这一点并请用户协助。

## 阶段 1：建立反馈回路

**这就是本 skill 的核心。** 其余都是机械的。只要你有一个针对这个 bug 的**紧**（tight）的通过/失败信号（一个在*这个* bug 上**变红**的信号），你就一定能找到原因；二分、假设检验、插桩都只是在消费它。没有这个信号，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**激进、有创意、不放弃。**

### 起手

构建回路的原料往往就在眼前：

- **完整读错误信息**：堆栈读到底，记下行号、文件路径、错误码。
- **看最近的变更**：`git log`、`git diff`、新依赖、配置改动、环境差异。

### 构建回路的方式，大致按这个顺序

1. **失败的测试**，放在能触达 bug 的任意接缝上：单元、集成、端到端。
2. **curl / HTTP 脚本**，打向运行中的开发服务器。
3. **CLI 调用**，喂一个固定输入，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并断言 DOM、控制台、网络。
5. **回放抓取的轨迹**。把真实的网络请求、载荷、事件日志存盘，单独让代码路径回放一遍。
6. **一次性脚手架**。拉起系统的最小子集（一个服务、依赖用 mock），一次函数调用就能走到 bug 的代码路径。
7. **属性 / 模糊测试回路**。bug 是"有时输出错误"，就跑 1000 个随机输入找失败模式。
8. **二分脚手架**。bug 出现在两个已知状态之间（提交、数据集、版本），把"启动到状态 X、检查、重复"自动化，好用 `git bisect run`。
9. **差分回路**。同一输入分别跑旧版本和新版本（或两种配置），diff 输出。
10. **人在回路的 bash 脚本**。最后手段。必须有人点击时，用 [scripts/hitl-loop.template.sh](scripts/hitl-loop.template.sh) 驱动*人*，让回路依然是结构化的。抓到的输出回传给你。

回路建对了，bug 就修好了九成。

### 收紧回路

把回路当成产品来打磨。有了*一个*回路之后，**收紧**它：

- 能更快吗？（缓存准备工作、跳过无关的初始化、缩小测试范围。）
- 信号能更尖吗？（断言具体症状，而不是"没崩"。）
- 能更确定吗？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

一个 30 秒还时灵时不灵的回路比没有好不了多少；一个 2 秒的确定性回路就是紧的，是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发条件循环 100 次、并行、加压、缩小时间窗口、注入 sleep。50% 复现率的 bug 可以调，1% 的不行，所以持续提高复现率直到可调。和时序相关的测试不稳定，读 [CONDITION-BASED-WAITING.md](CONDITION-BASED-WAITING.md)。

### 确实建不出回路时

停下来明确说出来。列出你试过的方法。向用户要：(a) 能复现问题的环境的访问权，(b) 脱敏后的抓取产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。没有回路就不进入假设阶段。

### 完成判据：一个会变红的紧回路

阶段 1 完成的标志：回路是**紧**的并且**能变红**。你能说出**一条命令**（脚本路径、测试调用、一条 curl），你**已经至少运行过一次**（展示调用和输出，已脱敏），并且它：

- [ ] **能变红**：它走的是真实的 bug 代码路径，断言的是**用户描述的确切症状**，所以会在这个 bug 上变红、修好后变绿。不是"运行不报错"，它必须能*抓住这个具体的 bug*。
- [ ] **确定**：每次运行结论一致（不稳定的 bug：复现率被固定在一个高水平，见上文）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可运行**：你能无人值守地运行它；需要人参与时只通过 `scripts/hitl-loop.template.sh`。

发现自己在这条命令存在之前就读代码构建理论，**停下来：直接跳到假设正是本 skill 要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现并最小化

运行回路，看着它随 bug 出现而变红。

确认：

- [ ] 回路产生的是**用户**描述的失败模式，而不是碰巧在附近的另一个失败。bug 找错，修复就错。
- [ ] 失败可以多次复现（非确定性 bug：复现率足够高，可以对着调）。
- [ ] 你已经抓到确切症状（错误信息、错误输出、慢的耗时），后续阶段可以用它验证修复真的解决了问题。

### 最小化

变红之后，把复现缩到**仍然变红的最小场景**。输入、调用方、配置、数据、步骤，**一次砍一样**，每砍一次重跑回路，只保留对失败起承重作用的东西。

为什么值得：最小复现缩小了阶段 3 的假设空间（可疑的活动部件更少），也会成为阶段 5 里干净的回归测试。

完成判据：**剩下的每个元素都是承重的**：去掉任何一个，回路就变绿。

没复现、没最小化，就不往下走。

## 阶段 3：提出假设

检验任何假设之前，先生成 **3 到 5 个排好序的假设**。只生成一个假设会锚定在第一个看似合理的想法上。

假设的来源：

- **对照能工作的样例**：代码库里找一段相似但正常工作的代码，逐条列出它和坏掉的这段之间的差异，再小的差异也列上。
- **回溯根源**：错误出现在调用栈深处时，沿调用链往回追，找坏值最初从哪来。方法见 [ROOT-CAUSE-TRACING.md](ROOT-CAUSE-TRACING.md)。
- **完整读参考实现**：你在套用某个模式时，把参考实现逐行读完。

每个假设都必须**可证伪**：写出它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

说不出预测的假设只是感觉：丢掉或磨尖。

**检验之前把排好序的清单给用户看。** 用户常有能瞬间重排的领域知识（"我们刚部署了一个改动，和 #3 有关"），或者知道哪些假设已经排除过。这是便宜的检查点，省大量时间。不必阻塞等待；用户不在时按你的排序继续。

## 阶段 4：插桩

每个探针都要对应阶段 3 的某个具体预测。**一次只改一个变量。**

工具偏好：

1. 环境支持时，**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界上加**定向日志**。多组件系统（CI → 构建 → 签名、API → 服务 → 数据库）里，在每个组件边界记录进入的数据、离开的数据、环境与配置是否传递到位，跑一次，看证据显示在哪一层断了，再深挖那一层。
3. 日志要瞄准假设；"全部打日志再 grep"会淹没信号。

**每条调试日志都打上唯一前缀**，比如 `[DEBUG-a4f2]`。收尾清理只需一次 grep。打了标签的日志会被清掉，没打的会留下来。

**性能分支。** 性能退化时，日志通常不是对的工具。先建立基线测量（计时脚手架、`performance.now()`、profiler、查询计划），再二分。先测量，后修复。

## 阶段 5：修复与回归测试

**修复之前**写回归测试，但前提是存在一个**正确的接缝**。

正确的接缝指的是测试能照 bug 在调用点实际发生的样子去复现**真实的 bug 模式**。唯一可用的接缝太浅（bug 需要多个调用方而测试只有一个调用方；单元测试复现不了触发 bug 的调用链），在那里写回归测试只会带来虚假的安心。

**没有正确的接缝，这件事本身就是发现。** 记下来：是代码库架构让这个 bug 无法被锁住。留给阶段 6。

存在正确接缝时：

1. 把最小复现变成那个接缝上的失败测试。
2. 看它失败。
3. 应用修复：**在根源处修**，一次一个改动，只改和这个根因有关的东西。
4. 看它通过。
5. 对原始（未最小化的）场景重跑阶段 1 的回路。

根源处修完后，数据穿过的其他层要不要也加校验，读 [DEFENSE-IN-DEPTH.md](DEFENSE-IN-DEPTH.md)。

### 修了三次还不好

修复没起作用，回到阶段 1，用新信息重新分析。数一下试过几次：

- **少于 3 次**：回到阶段 3，带着新证据重排假设。
- **3 次及以上**：停下来质疑架构。每次修复都在另一个地方暴露新的共享状态或耦合、修复需要"大规模重构"才能落地、每次修复都在别处制造新症状，这些都说明问题不是某个假设错了，而是结构错了。把这个判断和证据交给用户讨论，再决定是否继续修。

## 阶段 6：收尾

宣布完成之前必须满足：

- [ ] 原始复现不再出现（重跑阶段 1 回路，读输出）
- [ ] 回归测试通过，并做过红绿验证（撤掉修复会变红）；或者已记录缺少正确接缝
- [ ] 所有 `[DEBUG-...]` 插桩已删除（grep 前缀确认）
- [ ] 一次性原型已删除（或移到明确标注的调试位置）
- [ ] 最终被证实的假设写进了提交或 PR 描述，让下一个调试的人学到东西

完成声明遵循 `verifying-completion`：调用 Skill 工具，参数为 `verifying-completion`。

然后问：**怎样才能从一开始就防住这个 bug？** 答案涉及架构改动（没有好的接缝、调用方之间耦合太紧、隐藏的共享状态），带着具体细节告诉用户可以运行 `/improve-codebase-architecture`。在修复*之后*提，这时你比任何时候都更了解情况。

## 多个互不相关的失败

一次出现多个失败，且它们属于互不相关的领域（不同的测试文件、不同的子系统、没有共享状态），每个领域派一个子代理并行诊断。每个子代理拿到：一个明确的范围、失败的测试名与错误信息、"不改范围外的代码"的约束、要求返回根因与改动摘要。它们回来后，检查改动是否冲突，跑完整测试套件。失败之间可能相关（修一个可能修好另一个）时，先放在一起诊断。
