# 加深模块

根据依赖情况，安全地把一组浅模块合并加深。沿用 [SKILL.md](SKILL.md) 中的术语：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估一个可加深的候选项时，先对它的依赖分类。依赖类别决定了加深后的模块如何通过接缝测试。

### 1. 进程内依赖

纯计算、内存状态、没有 I/O。总是可以加深：合并模块，直接通过新接口测试。不需要适配器。

### 2. 可在本地替代的依赖

有本地测试替身的依赖（例如用 PGLite 替代 Postgres、使用内存文件系统）。存在替身时就可以加深。测试套件在替身上运行加深后的模块。接缝位于模块内部，模块的外部接口上不暴露端口。

### 3. 自有的远程依赖（端口与适配器）

跨网络的自有服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块负责业务逻辑，通信方式作为**适配器**注入。测试使用内存适配器，生产使用 HTTP、gRPC 或消息队列适配器。

推荐的表述：*“在接缝处定义端口，生产使用 HTTP 适配器、测试使用内存适配器。这样即使部署跨越网络，逻辑也集中在一个深模块中。”*

### 4. 真正的外部依赖（mock）

你无法控制的第三方服务（Stripe、短信平台等）。加深后的模块把外部依赖作为注入的端口接收，测试提供 mock 适配器。

## 接缝使用规则

- **只有一个适配器时，接缝只是假设；有两个适配器时，接缝才真实存在。** 至少有两个合理的适配器（通常是生产和测试）时，才引入端口。只有一个适配器的接缝只会多一层间接调用。
- **内部接缝与外部接缝。** 深模块可以有内部接缝（实现私有，供自身测试使用），也可以有位于接口处的外部接缝。测试用到的内部接缝保留在内部，不必因此暴露到接口上。

## 测试策略：替换旧测试，而不是叠加

- 加深后的模块接口上有了测试后，浅模块上的旧单元测试就失去了价值，删除它们。
- 在加深后模块的接口上编写新测试。**接口就是测试面。**
- 测试通过接口断言可观察的结果，不断言内部状态。
- 测试描述的是行为而不是实现，所以内部重构后应该依然有效。如果实现一变测试就必须修改，说明测试绕过了接口。
