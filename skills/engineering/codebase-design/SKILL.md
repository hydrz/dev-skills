# 代码库设计

设计**深模块**（deep module）：大量行为藏在小接口后面，放在干净的接缝处，能通过这个接口测试。凡是在设计或重构代码的地方，都用这套语言和原则。目标是给调用方杠杆，给维护者局部性，给所有人可测性。

## 术语

严格使用这些词，不要换成"组件""服务""API""边界"。用语一致正是全部意义所在。

**模块**（module）：任何有接口和实现的东西。刻意不限尺度：函数、类、包，或跨层的切片。_避免_：单元、组件、服务。

**接口**（interface）：调用方正确使用模块所需知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需配置、性能特征。_避免_：API、签名（太窄，只指类型层面的表面）。

**实现**（implementation）：模块内部，它的代码主体。与**适配器**不同：一个东西可以是小适配器带大实现（Postgres 仓储），也可以是大适配器带小实现（内存假实现）。谈接缝时用"适配器"，其他时候用"实现"。

**深度**（depth）：接口处的杠杆。调用方（或测试）每学一单位接口能用到的行为量。大量行为藏在小接口后面，模块就**深**；接口几乎和实现一样复杂，模块就**浅**。

**接缝**（seam，Michael Feathers）：不改动该处代码就能改变行为的位置；模块接口所在的*位置*。接缝放在哪里是一个独立的设计决策，与接缝后面放什么不同。_避免_：边界（与 DDD 的限界上下文撞车）。

**适配器**（adapter）：在接缝处满足接口的具体实现。描述*角色*（填哪个槽），不描述内容（里面有什么）。

**杠杆**（leverage）：调用方从深度中得到的东西。每学一单位接口能获得更多能力。一份实现，回报给 N 个调用点和 M 个测试。

**局部性**（locality）：维护者从深度中得到的东西。变更、bug、知识、验证集中在一处，而不是散落在各个调用方。修一次，处处都好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口         │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│      深的实现        │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│             大接口               │  ← 方法多、参数复杂
├─────────────────────────────────┤
│  薄实现                          │  ← 只是转手
└─────────────────────────────────┘
```

设计接口时问：

- 能减少方法数量吗？
- 能简化参数吗？
- 能把更多复杂性藏进去吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可 mock、可替换的部件组成，它们只是不属于接口。模块可以有**内部接缝**（实现私有，供自己的测试使用），也有位于接口处的**外部接缝**。
- **删除测试。** 想象删掉这个模块。复杂性随之消失，它只是个转手；复杂性在 N 个调用方处重新冒出来，它在挣自己的饭钱。
- **接口就是测试面。** 调用方和测试跨越同一条接缝。你想越过接口去测，模块多半形状不对。
- **一个适配器是假想的接缝，两个适配器才是真的。** 接缝两侧真有东西在变化，才引入接缝。
- **小文件、单一职责。** agent 能同时装进上下文的代码，它推理得最好；文件聚焦，编辑也更可靠。一个文件越长越大，往往说明它做得太多。把一起变化的东西放在一起，按职责拆，不按技术分层拆。

## 为可测性设计

好接口让测试顺理成章：

1. **接收依赖，而不是自己创建。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积小。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，以其**接口**衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**处，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 已否决的说法

- **把深度当作实现行数与接口行数之比**（Ousterhout）：这会奖励往实现里灌水。我们用"深度即杠杆"。
- **把"接口"当作 TypeScript 的 `interface` 关键字或类的公有方法**：太窄。这里的接口包括调用方必须知道的每一个事实。
- **"边界"**：与 DDD 的限界上下文撞车。说**接缝**或**接口**。
