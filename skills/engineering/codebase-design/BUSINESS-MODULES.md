# 业务模块

规划业务模块、决定模块内部用多重的结构，或者讨论“要不要用 DDD”时，读这份文件。

核心判断：保留 DDD 的战略部分（按业务划分限界上下文），把战术模式（聚合、仓储、领域服务等）当作按需升级的工具，而不是默认模板。不要问“项目要不要用 DDD”，要问“哪个业务模块复杂到值得用 DDD”。

## 术语

**限界上下文**（bounded context）：一套领域模型和通用语言成立的范围。同一个词在不同上下文中可以有不同含义。

**业务模块**（business module）：实现某个限界上下文的一组代码，拥有自己的数据和对外接口。它是**模块**在业务尺度上的一种形态，接口、深度、接缝等原则同样适用。业务模块和限界上下文默认一一对应，但前者说的是代码组织，后者说的是语言和模型的范围。

## 默认架构

- **系统结构**：模块化单体（modular monolith）优先。一个进程里放多个业务模块，模块之间保持隔离。只有独立部署、团队隔离或独立扩缩容成为真实需求时，才把某个业务模块拆成独立服务。模块边界守得住，拆分时改动就小。
- **模块之间**：强约束，见下一节。
- **模块内部**：按用例组织代码（vertical slice），结构轻重由复杂度决定，见“按复杂度升级”。
- **接口定义**：模块之间的请求、响应、事件和错误可以先写成契约，再写实现。项目采用契约优先或使用 TypeSpec 时，读 [CONTRACT-FIRST.md](CONTRACT-FIRST.md)。

## 模块之间强约束，模块内部弱约束

业务模块之间只通过以下方式交互：

- 模块的公开接口（进程内调用的导出函数或类型）
- HTTP 或 RPC 契约
- 事件契约

具体来说，订单模块只能调用支付模块导出的公开接口或订阅它的事件。它不 import 支付模块的内部代码，也不读写支付模块的表。发现跨模块访问内部代码或数据时，把它当作需要修复的结构问题。

模块内部没有统一规定。同一个仓库里，一个模块可以是 `handler → store`，另一个模块可以是 `handler → aggregate → repository`。选择依据是这个模块的业务复杂度，而不是架构规范的统一要求。

## 按用例组织目录

模块内部按用例拆目录，把一个用例需要的处理函数、校验和存储访问放在一起：

```text
order/
├── create/
├── cancel/
├── query/
└── model/        ← 多个用例共享的领域对象，需要时才创建
```

避免按技术分层建目录（`domain/`、`application/`、`infrastructure/`、`repositories/`、`valueobjects/`）。分层目录让一个用例的代码分散在多个目录中，修改一个功能要来回跳转，削弱局部性。

**抽象税**（abstraction tax）指架构本身带来、而业务并不需要的复杂度。典型信号：一个简单的增删改查要经过六层调用、八个文件、DTO 映射、仓储接口和服务接口。业务复杂度只有 10，结构却额外增加了 30。按删除测试判断：删掉某一层后复杂性随之消失，这一层就是抽象税。

## 三种模型分开

| 模型                       | 用途                                     | 变化原因           |
| -------------------------- | ---------------------------------------- | ------------------ |
| 契约模型（contract model） | 请求、响应、事件等跨模块或对外传输的结构 | 调用方的兼容性要求 |
| 领域模型（domain model）   | 表达业务规则和不变量                     | 业务规则变化       |
| 存储模型（database model） | 表结构、索引、持久化格式                 | 查询性能和存储方式 |

三种模型的变化原因不同。用同一个类型同时充当 API DTO、领域实体和数据库实体，它们的生命周期会互相绑死：改一个字段的存储方式会破坏对外契约，加一条业务规则要改传输结构。

- 简单增删改查模块可以合并成一个类型，省掉映射代码。
- 核心业务模块保持分开。模块从简单升级到有业务不变量时，同步把模型拆开。

## 按复杂度升级

从最轻的结构开始。出现下表的升级信号时，再升到下一级。每一级都是在前一级基础上增加，不是推倒重写。

| 级别 | 适用情况         | 结构                                                        | 升级到下一级的信号                                   |
| ---- | ---------------- | ----------------------------------------------------------- | ---------------------------------------------------- |
| 1    | 简单增删改查     | 处理函数直接读写存储                                        | 出现多步流程、校验规则分散在多个处理函数中           |
| 2    | 一般业务流程     | 按用例组织目录                                              | 同一个实体有明确的状态和状态转换                     |
| 3    | 有状态转换       | 用例目录加共享的领域对象，状态转换写成领域对象的方法        | 出现必须始终成立的业务不变量，或需要多个实体保持一致 |
| 4    | 有复杂业务不变量 | 值对象（value object）和聚合（aggregate），仓储只为聚合创建 | 业务规则多、变化快，并且是核心竞争力所在             |
| 5    | 核心复杂领域     | 完整的 DDD 战术模式，加上领域事件（domain event）           | 无                                                   |

常见的升级信号：状态机、业务不变量、时间约束（例如结算周期、过期时间）、跨实体一致性。

以下情况与复杂度级别无关，遇到时才引入：

- **跨模块的长流程**：多个业务模块参与、不能放在一个事务里完成时，用事件加 Saga 或流程管理器（process manager）协调。
- **查询特别复杂**：读和写的形状差异很大时，用简化版 CQRS（CQRS-lite），为查询单独建读模型，不必同时引入事件溯源。
- **同一个词含义冲突**：同一个词在不同业务场景中需要不同的模型时，拆出新的限界上下文，并用 `CONTEXT-MAP.md` 记录它们的关系。

## 对比例子

**用户资料**：修改头像、修改昵称、修改时区。没有状态机，也没有跨实体一致性，停在级别 1 或 2：

```text
user/
├── update_profile.go
└── get_profile.go
```

不需要 `UserAggregate`、`UserDomainService`、`UserRepository`、`UserFactory`。

**交易、风控、结算、定价、计费、库存**：通常有状态机、业务不变量、时间约束和跨实体一致性。从按用例组织目录开始，随着信号出现逐步引入领域对象、值对象、聚合和领域事件。
