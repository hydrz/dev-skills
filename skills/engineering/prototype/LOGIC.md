# 逻辑原型

一个自包含的单文件 HTML（**可分享的演示**），任何人点按钮就能驱动一个状态模型。问题关于**业务逻辑、状态流转或数据形状**时用它：那种纸面上看着合理、真推过几个案例才发现不对的东西。

因为只有一个文件、什么都不用装，你可以把它交给非开发者（设计师、产品经理、领域专家），让他们亲自感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 何时是这个形状

- "我不确定这个状态机能不能处理先 X 再 Y 的情况。"
- "这个数据模型真的能表示……的情况吗？"
- "写之前我想先摸一摸这个 API 应该长什么样。"
- 任何有人想**按按钮、看状态变化**的时候。

问题是"这个应该长什么样"，走 [UI.md](UI.md)。

## 过程

### 1. 写下问题

写代码之前，写下要做原型的状态模型和问题。一段话，放在演示顶部（可见的介绍区，不只是代码注释）。回答错问题的逻辑原型纯属浪费，所以把问题写明，之后才能检查，无论用户此刻在看，还是离开后再回来看。

### 2. 把逻辑隔离成可移植模块

把真正在回答问题的那部分逻辑放进单独一个 `<script>` 块，写成一个小而纯的模块，以后可以原样搬进真实代码库。周围的页面是一次性的，这个模块不是。

合适的形状取决于问题：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单个值时合适。
- **状态机**：显式的状态与流转。"此刻哪些动作是合法的"本身就是问题的一部分时合适。
- **一组纯函数**，作用于普通数据类型。没有隐含的当前状态、只有变换时合适。
- **一个方法表面清晰的类或模块**，逻辑确实持有持续的内部状态时合适。

选最贴合问题的形状，而不是最容易接到页面上的形状。保持纯：模块里不碰 DOM、`document` 或按钮处理器。页面调用模块，数据只朝一个方向流。这就是原型在生命周期之外仍然有用的原因：问题一旦回答，验证过的 reducer / 状态机 / 函数集可以直接搬进真实模块。

### 3. 做可分享的 HTML 文件

一个文件，纯 HTML / CSS / JS：不用框架、不用打包器、不用服务器，全部内联，双击就能打开，被邮件转来转去也不会坏。

为非开发者写。每个标签都用**领域语言**，而不是代码语言：按钮和状态读起来像业务，而不是 reducer。用平实的话解释正在发生什么。

版面自上而下层次清晰：

1. **标题和一句话说明**：这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整的相关状态，渲染成易读的面板（带标签的字段，而不是原始 JSON），每次点击后重新渲染。对非开发者有帮助时，标出刚才变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可点，任何人都能以任意顺序戳这个模型。每次点击分发动作并重新渲染状态。
4. **引导演练**：一组**场景**，每个一个标签页。每个标签页有一段平实的场景说明（它设置了什么情况、该留意什么），下面是该场景**依次要按的按钮**。每一步都是真按钮：点它就执行那个动作并前进到下一步。开始一个演练会重置到已知的初始状态，让场景每次跑得一样。

挑能展示棘手情况的场景，也就是纸面上难以推理的那些：正常路径、一个刁钻的边界情况、一次尝试做本该非法的事。

好看但克制：干净的排版、宽松的留白、一个强调色。不要动画和花哨效果，别让任何东西抢了状态和按钮的风头。

### 4. 交出去

把文件发给他们，或替他们打开。他们会找时间点完演练、自由操作；有意思的时刻是他们说"等等，这不应该能做到"或"咦，我以为 X 会不一样"：那些是*想法*里的 bug，也正是全部意义所在。他们想加新动作或新场景，就加。原型会演进。

### 5. 留存答案与原型

原型回答了问题之后，先留存答案，再按 [SKILL](SKILL.md) 的方式留存原型。逻辑原型的对应关系：验证过的 reducer / 状态机 / 函数集搬进真实模块（决定被吸收）；HTML 外壳跟着进一次性分支，作为一手资料保留，它是单个自包含文件，在那里随时可以重跑。

## 保持原型的形状

- **不加测试。** 需要测试的原型已经不是原型了。
- **状态放内存。** 除非问题专门关于持久化，不连真实数据库。
- **只回答一个问题。** 不为"以后也许要支持 X"做通用化。
- **逻辑与页面分开。** 纯模块一旦引用 DOM、`document` 或按钮处理器，就搬不走了。页面是纯模块外面的一层薄壳。
- **一个双击即开的文件。** React 应用或开发服务器会破坏"可分享"。
- **HTML 外壳留在一次性分支。** 页面是为手动点击优化的，值得保留进生产的是它背后的逻辑模块。
