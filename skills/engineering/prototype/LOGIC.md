# 逻辑原型

一个自包含的单文件 HTML（**可分享的演示**），任何人都可以点击按钮驱动一个状态模型。问题涉及**业务逻辑、状态流转或数据结构**时使用：这类问题在纸面上看起来合理，实际推演几个案例后才会发现问题。

因为只有一个文件、不需要安装任何东西，你可以把它交给非开发者（设计师、产品经理、领域专家），让他们亲自体验这个模型。所以它要使用他们的语言，而不是代码的语言。

## 适用场景

- “我不确定这个状态机能否处理先 X 后 Y 的情况。”
- “这个数据模型真的能表示……的情况吗？”
- “写代码之前，我想先试试这个 API 应该怎么设计。”
- 任何需要**点击按钮、观察状态变化**的时候。

问题是“这个界面应该是什么样子”时，见 [UI.md](UI.md)。

## 过程

### 1. 写下问题

编写代码之前，先写下要验证的状态模型和问题。用一段话说明，放在演示页面顶部（作为可见的介绍区域，而不只是代码注释）。回答错问题的逻辑原型毫无价值，所以要把问题写明，之后才能检查原型是否回答了它，无论用户正在看，还是之后再回来查看。

### 2. 把逻辑隔离成可移植模块

把真正回答问题的逻辑放进一个单独的 `<script>` 块，写成一个小而纯的模块，以后可以原样移入正式代码库。周围的页面是一次性的，这个模块不是。

根据问题选择合适的结构：

- **纯 reducer**：`(state, action) => state`。适合动作是离散事件、状态是单个值的情况。
- **状态机**：显式定义状态和流转。适合“当前允许哪些动作”本身就是问题一部分的情况。
- **一组纯函数**，处理普通数据类型。适合没有隐含当前状态、只有数据转换的情况。
- **一个方法清晰的类或模块**，适合逻辑确实需要持有持续内部状态的情况。

选择最贴合问题的结构，而不是最容易接到页面上的结构。保持纯粹：模块中不访问 DOM、`document` 或按钮事件处理器。页面调用模块，数据只朝一个方向流动。这就是原型在一次性使用之后仍然有价值的原因：问题得到回答后，验证过的 reducer、状态机或函数集可以直接移入正式模块。

### 3. 制作可分享的 HTML 文件

只用一个文件，纯 HTML、CSS 和 JS：不用框架、不用打包工具、不用服务器，全部内联。双击就能打开，通过邮件多次转发也不会失效。

面向非开发者编写。所有标签都使用**领域语言**，而不是代码语言：按钮和状态读起来应该像业务描述，而不是 reducer。用平实的语言解释正在发生什么。

页面从上到下层次清晰：

1. **标题和一句话说明**：这个演示用来探索什么（第 1 步写下的问题）。
2. **当前状态**：完整的相关状态，渲染成易读的面板（带标签的字段，而不是原始 JSON），每次点击后重新渲染。对非开发者有帮助时，标出刚才变化的内容。
3. **自由操作按钮**：每个动作一个按钮，始终可以点击，任何人都能以任意顺序操作这个模型。每次点击都分发动作并重新渲染状态。
4. **引导场景**：一组**场景**，每个场景一个标签页。每个标签页包含一段平实的场景说明（设置了什么情况、应该关注什么），下面是该场景**按顺序需要点击的按钮**。每一步都是真实按钮：点击后执行对应动作，并进入下一步。开始一个场景时，先重置到已知的初始状态，确保每次运行结果一致。

选择能展示复杂情况的场景，也就是那些难以在纸面上推演的情况：正常路径、一个棘手的边界情况，以及一次尝试执行本应被禁止的操作。

外观美观但克制：清晰的排版、充足的留白、一个强调色。不使用动画和花哨效果，避免分散对状态和按钮的注意力。

### 4. 交给用户

把文件发给用户，或替用户打开。用户会在方便时点完引导场景并自由操作。最有价值的反馈往往是“等等，这不应该能做到”或“咦，我以为 X 会不一样”：这些暴露的是*设计想法*中的问题，也正是原型的意义所在。用户想添加新动作或新场景时，就添加。原型会随讨论不断演进。

### 5. 保存结论和原型

原型回答问题之后，先保存结论，并写回设计依据：把验证过的状态、转换和禁止的操作整理成相关范围项的行为决策（写在规格、决策项或 ADR 中），在范围清单的“设计依据”列链接它，并补全该范围项的状态集。然后按 [SKILL.md](SKILL.md) 中的方式保存原型。对逻辑原型来说：验证过的 reducer、状态机或函数集移入正式模块（决定被整合）；HTML 外壳提交到一次性分支，作为一手资料保留。它是单个自包含文件，在那里随时可以重新运行。

## 保持原型的边界

- **不写测试。** 需要测试的原型已经不是原型了。
- **状态保存在内存中。** 除非问题专门涉及持久化，否则不连接真实数据库。
- **只回答一个问题。** 不为“以后也许要支持 X”做通用化设计。
- **逻辑与页面分开。** 纯模块一旦引用 DOM、`document` 或按钮事件处理器，就无法移植了。页面只是纯模块外面的一层薄壳。
- **一个双击即可打开的文件。** React 应用或开发服务器会破坏“可分享”这一点。
- **HTML 外壳留在一次性分支。** 页面是为手动点击设计的，值得进入生产代码的是它背后的逻辑模块。
