# 原型

原型是**回答一个问题的一次性代码**。问题决定原型的形状。

## 选分支

弄清要回答的是哪类问题，依据用户的提示、周边代码，用户在的话就问：

- **"这个逻辑 / 状态模型说得通吗？"** → [LOGIC.md](LOGIC.md)。做一个可分享的单文件 HTML（自由操作按钮 + 分标签页的引导演练），把状态机推过那些纸面上难以推理的情况，非开发者也能上手点。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在同一个路由上生成几个截然不同的 UI 变体，用 URL 查询参数和底部浮动切换条来切换。

两个分支的产物完全不同，选错了整个原型就白做。问题确实模糊、用户又不在时，按周边代码选（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两个分支共用的规则

1. **从第一天起就是一次性的，并且标得清清楚楚。** 原型代码放在它将来要用的地方附近（它为之做原型的模块或页面旁边），让上下文一目了然；命名要让随便看一眼的人都知道这是原型，不是生产代码。一次性 UI 路由遵循项目现有的路由约定，不另起顶层结构。
2. **运行零门槛。** UI 原型用项目任务运行器里的一条命令启动：`pnpm <名字>`、`python <路径>`、`bun <路径>` 等。逻辑演示是一个双击就能打开的 HTML 文件。无论哪种，启动不需要动脑。
3. **默认不持久化。** 状态放内存。持久化是原型要*检验*的东西，而不是它该依赖的东西。问题明确涉及数据库时，用临时库或本地文件，名字里写清"原型，可清空"。
4. **跳过打磨。** 不写测试，错误处理只做到能跑，不做抽象。目的是快速学到东西。
5. **把状态摆出来。** 每次操作之后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到变了什么。
6. **结束时留存。** 把验证过的决定折回真实代码，然后把原型本身作为**一手资料**留存：提交到一个一次性分支（不进主干），在实现 issue 上留一个指向该分支的上下文指针。答案也要留存（结论，以及它解决的问题），写在 issue 或提交里。主干只保留验证过的决定。
