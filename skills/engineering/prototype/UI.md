# UI 原型

在同一个路由上生成**几个截然不同的 UI 变体**，用底部浮动切换条切换。用户在浏览器里翻看各个变体，挑一个（或从每个里各偷一点），其余扔掉。

问题是关于逻辑 / 状态而不是长相，走 [LOGIC.md](LOGIC.md)。

## 何时是这个形状

- "这个页面应该长什么样？"
- "定下来之前我想看看这个仪表盘的几种方案。"
- "设置页换个布局试试。"
- 任何用户本来要花一天在脑子里纠结三个模糊方案的时候。

## 两种子形状：强烈优先 A

UI 原型**紧挨着应用其余部分**时才好判断：真实的页头、真实的侧栏、真实的数据、真实的密度。一个孤零零的一次性路由是真空：每个变体单独看都还行。只要有合适的现有页面能承载变体，就默认用子形状 A。只有原型确实没有邻近的家时，才用子形状 B。

### 子形状 A：调整现有页面（优先）

路由已存在。变体渲染在**同一个路由**上，由 `?variant=` 查询参数控制。现有的数据获取、参数、鉴权全部保留，只替换渲染。这是默认选择，除非有具体理由。

原型要做的东西还没有页面、但*自然属于某个页面*（仪表盘里的新区块、设置页上的新卡片、现有流程里的新一步），也算子形状 A：把变体挂在宿主页面里。

### 子形状 B：新页面（最后手段）

只在要做原型的东西确实没有现有页面可以容纳时使用（比如全新的顶层界面，或无法合理嵌入任何地方的流程）。

按项目现有的路由约定建一个**一次性路由**，不另起顶层结构。命名要一看就是原型（比如路径或文件名里带 `prototype`）。同样用 `?variant=`。

决定用子形状 B 之前再确认一次：真的没有现有页面能嵌进去吗？空路由会藏住一个有内容的页面本会暴露出来的设计问题。

两种子形状的浮动切换条完全一样。

## 过程

### 1. 写下问题，定下 N

默认 **3 个变体**。超过 5 个就不再截然不同，开始变成噪音，所以上限是 5。

用一行写下计划，放在原型位置或文件顶部注释里：

> "设置页的三个变体，通过 `?variant=` 切换，位于现有的 `/settings` 路由上。"

无论用户在不在场反驳，这都有用。

### 2. 生成截然不同的变体

逐个起草变体。每个都要遵守：

- 页面的用途和它能拿到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，用什么就是什么）。
- 清晰的导出组件名，比如 `VariantA`、`VariantB`、`VariantC`。

变体必须**在结构上不同**：不同的布局、不同的信息层级、不同的主要交互方式，而不只是不同的颜色。三个略作调整的卡片网格不是 UI 原型，是墙纸。两份草稿太像时，带着明确的指示（"不要用卡片网格"）重做其中一份。

### 3. 接到一起

在路由上建一个切换组件：

```tsx
// 伪代码，按项目框架调整
const variant = searchParams.get("variant") ?? "A";
return (
  <>
    {variant === "A" && <VariantA {...data} />}
    {variant === "B" && <VariantB {...data} />}
    {variant === "C" && <VariantC {...data} />}
    <PrototypeSwitcher variants={["A", "B", "C"]} current={variant} />
  </>
);
```

子形状 A（现有页面）：现有的数据获取全部留在切换组件之上，每个变体只换渲染的子树。

子形状 B（新页面）：`/prototype/<名字>` 下的一次性路由挂同一个切换组件。

### 4. 做浮动切换条

屏幕底部居中的一个小的固定定位条，三部分：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体的键；变体导出了名字的话一并显示，比如 `B（侧栏布局）`。
- **右箭头**：切到下一个变体（循环）。

行为：

- 点箭头时用框架的路由更新 URL 查询参数（Next 用 `router.replace`，React Router 用 `navigate` 等），让变体可分享、刷新后不丢。
- 键盘：`←` 和 `→` 也能切换。焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时让方向键保持原本行为。
- 视觉上与页面明显区分（比如高对比度胶囊、轻微阴影），一看就不是被评估设计的一部分。
- 生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查把关，这样即使原型被误合并，切换条也不会出现在用户面前。

切换条做成一个共享组件，两种子形状都能复用，放在项目存放共享 UI 的地方。

### 5. 交出去

给出 URL（以及 `?variant=` 的各个键）。用户会找时间翻看。最有价值的反馈通常是**"我要 B 的页头配 C 的侧栏"**，那才是他们真正想要的设计。

### 6. 留存答案并清理

某个变体胜出后，先留存答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 的方式留存原型。把胜出者折进真实代码，其余的移到一次性分支，不进主干：

- **子形状 A**：把胜出者折进现有页面；从主干删掉落选变体和切换条。
- **子形状 B**：把胜出变体升级为真实路由；从主干删掉一次性路由和切换条。

全部变体是一手资料，所以放进一次性分支而不是扔掉；留在主干里的变体组件和切换条会很快腐烂，还会迷惑下一个读代码的人。

## 保持变体的形状

- **变体之间在结构上有分歧。** 只差颜色或文案的是微调，不是原型。
- **变体之间少共享。** 共享一个 `<Header>` 可以，共享一个 `<Layout>` 就失去了意义。每个变体都应该能自由推翻布局。
- **变体只读。** 需要写操作时指向桩实现：问题是"这应该长什么样"，不是"后端能不能用"。
- **胜出的变体折进来时重写。** 变体代码是在原型约束下写的（没测试、错误处理最少），折进真实代码时按生产标准重写。
