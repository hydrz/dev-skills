---

对 `HEAD` 与用户给出的固定点之间的 diff 做双轴评审：

- **标准**：代码是否符合本仓库成文的编码规范？
- **规格**：代码是否忠实实现了源头 issue / 规格？

两个轴作为**并行子代理**运行，互不污染上下文，然后由本 skill 汇总。

## 过程

### 1. 钉住固定点

用户说的就是固定点（提交 SHA、分支名、tag、`main`、`HEAD~5` 等）。没说就问。

记下一次 diff 命令：`git diff <固定点>...HEAD`（三点，比较的是 merge-base），以及提交列表 `git log <固定点>..HEAD --oneline`。

继续之前，确认固定点能解析（`git rev-parse <固定点>`）且 diff 非空。坏的引用或空 diff 应当在这里失败，而不是在两个并行子代理里。

把提交列表、`git diff --stat` 和带上下文的完整 diff（`git diff -U10 <固定点>...HEAD`）写进临时目录里一个唯一命名的文件，作为**评审包**。子代理读这个文件，diff 本身不进入你的上下文。

### 2. 找规格来源

按这个顺序找源头规格：

1. 提交信息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），按 `docs/agents/issue-tracker.md` 里的方式拉取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能相符的规格文件。
4. 都没找到就问用户规格在哪。用户说没有，**规格**子代理跳过，报告"无可用规格"。

### 3. 找标准来源

仓库里任何说明代码该怎么写的文档，比如 `CODING_STANDARDS.md`、`CONTRIBUTING.md`、`CLAUDE.md` / `AGENTS.md` 里的约定。

在仓库文档之外，**标准**轴总是带上下面的**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即便仓库什么都没写也适用。两条规则约束它：

- **仓库规范优先。** 成文的仓库规范永远胜出；仓库明确认可而基线会标记的写法，不报。
- **永远是判断题。** 每个坏味道都是带标签的启发式（"可能是依恋情结"），不是硬性违规。工具已经强制的东西不报。

每个坏味道写作 *是什么* → *怎么修*，逐个对照 diff：

- **神秘命名**：函数、变量或类型的名字说不清它做什么或存什么。→ 改名；想不出诚实的名字，说明设计本身模糊。
- **重复代码**：同样的逻辑形状在改动的多个 hunk 或文件里出现。→ 抽出共同形状，两处都调用它。
- **依恋情结**：一个方法伸手去拿另一个对象的数据，比拿自己的还多。→ 把方法搬到它依恋的数据那边。
- **数据泥团**：同样几个字段或参数总是结伴出行（一个等待诞生的类型）。→ 打包成一个类型，传它。
- **基本类型偏执**：用基本类型或字符串顶替一个值得有自己类型的领域概念。→ 给这个概念一个小类型。
- **重复的 switch**：同一类型上同样的 `switch` / `if` 级联在改动里反复出现。→ 用多态替换，或两处共用一张映射表。
- **霰弹式修改**：一个逻辑改动迫使 diff 里多个文件四处分散地修改。→ 把一起变化的东西收拢到一个模块。
- **发散式变化**：一个文件或模块因为几件不相干的理由被修改。→ 拆开，让每个模块只因一个理由变化。
- **夸夸其谈的通用性**：为规格里并不存在的需求加的抽象、参数或钩子。→ 删掉；内联回去，等真实需求出现。
- **过长的消息链**：`a.b().c().d()` 这种调用方不该依赖的长导航。→ 在第一个对象上用一个方法把这段遍历藏起来。
- **中间人**：一个类或函数几乎只是往下转发。→ 去掉它，直接调用真正的目标。
- **被拒绝的遗赠**：子类或实现者忽略或覆写了继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行派出两个子代理

两个子代理的提示都包含下面的**评审员守则**：

> 本次评审对这份检出只读：不改工作区、暂存区、HEAD 或分支状态。要看别的版本，用 `git show`，或检出到单独的临时目录。评审由你亲自完成，不再派子代理。每条发现给出 `文件:行号`、问题是什么、为什么重要、怎么修（不明显时）。按实际严重度分级：**严重**（bug、安全问题、数据丢失风险、功能损坏）、**重要**（这项改动在修好之前不可信：遗漏需求、吞掉错误、断言为空的测试、逻辑块原样重复）、**次要**（打磨类建议、"覆盖可以更广"）。只凭 diff 无法核实的要求（在未改动的代码里、或跨越多处改动），标为 ⚠️ 并说明需要检查什么，而不是去爬整个代码库。直接以结论开头，不要铺垫和收尾总结。

**标准子代理**的提示还包含：

- 评审包文件路径。
- 第 3 步找到的规范来源文件清单，**加上第 3 步的坏味道基线全文**（子代理没有别的途径拿到它）。
- 任务："逐文件 / 逐 hunk 报告：(a) diff 违反成文规范的每一处，引用规范（文件 + 条目）；(b) 你发现的每个基线坏味道，写出名字并引用 hunk。区分硬性违规与判断题：成文规范的违反可以是硬性的，基线坏味道永远是判断题，成文规范覆盖基线。工具已强制的不报。400 字以内。"

**规格子代理**的提示还包含：

- 评审包文件路径。
- 规格的路径或拉取到的内容。
- 任务："报告：(a) 规格要求但缺失或只做了一部分的；(b) diff 里有但规格没要求的行为（范围蔓延）；(c) 看起来实现了但实现方式看起来不对的。每条发现引用规格原文。400 字以内。"

规格缺失时跳过规格子代理，在最终报告里注明。

### 5. 汇总

把两份报告分别放在 `## 标准` 和 `## 规格` 标题下，原样或略作整理。**不要**合并或跨轴重排发现，两个轴是有意分开的（见 _为什么两个轴_）。

每个轴末尾给出该轴的结论：**可合并** / **修复后可合并** / **不可合并**，附一两句技术理由。⚠️ 项由你自己核实：你手里有子代理没有的跨改动上下文，确认是真实缺口的，按规格失败处理。

最后一行总结：每个轴的发现数，以及*每个轴内*最严重的问题（如有）。不要跨轴选出唯一的"最严重"：那正是分轴要防止的重排。

收到评审结果之后如何处理，调用 Skill 工具，参数为 `receiving-code-review`。

## 为什么两个轴

一项改动可能通过一个轴而挂在另一个轴上：

- 遵守了每一条规范，却实现了错误的东西 → **标准通过，规格失败。**
- 完全做了 issue 要求的事，却破坏了项目约定 → **规格通过，标准失败。**

分开报告，一个轴就遮不住另一个。
