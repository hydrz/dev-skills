# 指南

你记不住每个 skill，所以来问。

读用户描述的情况，对照下面的地图，告诉用户该用哪个 skill（或哪几个、按什么顺序）以及为什么。情况不清楚就问一两个问题再推荐。

**流程**是穿过这些 skill 的一条路径。大多数路径沿着一条**主流程**走，几条**匝道**汇入其中。其余的是独立工具，或者在底下运行的一层纪律与词汇。

## 先看规模

仪式随规模缩放，**确认闸门**不缩放：无论多小，动手之前都要让用户对"要做什么"说出明确的"是"。

| 规模 | 例子 | 路径 |
|---|---|---|
| **探针** | "能不能用 X 做到 Y？" | 说明要验证什么，用户点头后去查；需要跑代码就用 `/prototype`，报告建议 |
| **有界** | 仓库里已有流程上的一个参数、一个小接口、一处修复 | `/grill-me` 或 `/grill-with-docs` 几轮 → 在对话里给简短设计 → 用户说"是" → `/implement` |
| **架构级** | 新项目、新子系统、改变别人依赖的接口 | 完整主流程（下文） |
| **雾中巨物** | 一个会话装不下、连路都看不清 | `/wayfinder` |

两档之间拿不准，取重的那档。途中发现隐藏的复杂度，停下来升档。

## 主流程：想法 → 交付

大多数工作走的路。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 用拷问打磨想法。只要你**在一个工作目录里**，就从这里开始：它是有状态的，把学到的东西留在 `CONTEXT.md` 和 ADR 里。（没有工作目录？用 `/grill-me`，见"独立工具"。两者跑的是同一个 `grilling` 原语；`grill-with-docs` 会留下文字记录，所以只要有仓库可留，它就是更好的那个。）

2. **分支：每个问题都能在对话里定下来吗？** 某个问题需要可运行的答案（状态、业务逻辑、需要亲眼看的 UI）时，绕道做原型，两头都用 **`/handoff`** 衔接（原型住在自己的目录里，这正是 `/handoff` 的用途，见"阶段边界"）：
   - **`/handoff`** 出去，然后针对那个文件开一个新会话，
   - **`/prototype`** 用一次性代码回答问题，
   - **`/handoff`** 带回学到的东西，并在原来的想法线程里引用它。

3. **分支：这是多会话的构建吗？**
   - **是** → **`/to-spec`**（把线程变成规格，含自查），然后 **`/to-tickets`** 拆成曳光弹工单，每张声明**阻塞边**和**接口**。之后二选一：
     - **你来盯着**：对每张工单跑 **`/implement`**，**每张之间清空上下文**（`/clear`）。每张工单是自包含的，上一张的上下文可以丢弃。本地追踪器上按阻塞者优先手动推进；真实追踪器上阻塞者都完成的工单谁都能领。
     - **交给 agent 离席跑完**：**`/implement-spec`**。它作为协调者，按工单图的前沿并发派出子代理，每张工单独立评审，台账扛过上下文压缩，最后交付一个 PR，并把它代你做出的每个裁决列给你。
   - **否** → 就在这里、同一个上下文窗口里跑 **`/implement`**。

   无论哪条路，实现都在约定的接缝上驱动 **`tdd`**（一次一个红绿切片），以 **`code-review`**（标准 + 规格双轴评审）收尾，用 **`verifying-completion`** 核对完成，最后 **`finishing-a-branch`** 决定合并、开 PR 还是保留。

### 上下文卫生

步骤 1 到 3 保持在**一个不间断的上下文窗口**里（`/to-tickets` 之前不压缩、不清空），让拷问、规格、工单都建立在同一份思考之上。之后每次 `/implement` 从工单重新开始。

限制是**智能区**：模型仍能敏锐推理的窗口范围（当前最先进的模型约 15 万 token）。`/to-tickets` 之前会话就逼近这个范围时，不要带着退化硬撑；在最近的阶段边界 `/compact`，然后继续（见"阶段边界"）。

## 匝道

一个会产生工作、然后汇入主流程的起点。

- **bug 和需求越堆越多** → **`/triage`**。它让 issue 在分诊角色间流转，产出可交给 agent 的 issue，之后由 **`/implement`** 领走。

  分诊只针对**不是你创建的** issue：bug 报告、外来的功能请求，任何原始状态进来的东西。`/to-tickets` 产出的工单已经可以交给 agent，**不要再分诊**。

- **有东西坏了** → **`diagnosing-bugs`**（直接描述问题，agent 会自己用上它；也可以键入 `/diagnosing-bugs`）。用于难的那种：第一眼看不出来的 bug、时有时无的不稳定、在两个已知良好状态之间悄悄出现的回归。它在拿到一个**紧的反馈回路**（一条已经在*这个* bug 上变红的命令）之前拒绝推理，修复时附回归测试；修了三次还不好就停下来质疑架构。收尾时发现根本问题是没有好的接缝能锁住这个 bug，它会建议你跑 **`/improve-codebase-architecture`**。

- **一个庞大、朦胧的工作：全新项目或巨型功能，一个会话装不下** → **`/wayfinder`**，这里认知负担最重的流程。从这里到目的地的路还看不见时，它在 issue 追踪器上绘制一张**共享地图**，由**决策工单**组成，一次解决一张，产出**决定而不是交付物**，直到迷雾退去、道路清晰。`/grill-with-docs` 打磨的是一个会话装得下的想法，wayfinder 是给装不下的想法用的，它更慢、更密，所以只留给这种情况，范围清楚的功能不用它。

  地图清晰后，**它交接，不构建**：从 **`/to-spec`** 汇入主流程，把地图上链接的决定收拢成可构建的计划，然后照常 `/to-tickets`、`/implement` 或 `/implement-spec`。只有当工作最终被证明确实很小时，才直接 `/implement`。

## 代码库健康

不是功能工作，只是保养。

- **`/improve-codebase-architecture`** 在你有空的时候跑，让代码库一直适合 agent 在里面工作。它找出**加深机会**；挑中一个就*产生一个想法*，从 `/grill-with-docs` 带进主流程。它是找候选的勘察；**`codebase-design`**（见下）是你给选中的那个做设计的工作台。

## 底层：纪律与词汇

这些是模型调用 skill：agent 在合适的时候会自己用上，其他 skill 也会调用它们。想直接用时也可以键入名字。

**纪律**，约束行为：

- **`tdd`**：在约定的接缝上一次一个垂直切片地 红 → 绿；确认红得有道理，收尾做变异检查。
- **`verifying-completion`**：先证据后结论。说"完成 / 修好 / 通过"之前，本轮跑过对应命令并读过输出。
- **`code-review`**：自某个固定点以来的改动，按标准和规格两个轴并行评审，按严重度分级。
- **`receiving-code-review`**：收到评审意见后先核实再实现，不做表演式附和，该反驳就反驳。
- **`finishing-a-branch`**：测试变绿后，给出合并 / 开 PR / 保留三个选项，由你决定；丢弃需要输入 `discard` 确认。

**词汇**，各自是一套语言的单一真相源。**词**而不是流程出问题时直接找它们：

- **`domain-modeling`**：打磨项目的*领域*语言：质疑一个模糊的词、解开一个身兼数职的词（"账户"干了三份活）、把难以逆转的决定记成 ADR。`/grill-with-docs` 驱动的就是这门主动纪律。
- **`codebase-design`**：深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用来设计模块的*形状*：大量行为藏在小接口后面，放在干净的接缝处。`tdd` 和 `/improve-codebase-architecture` 都说这门语言。

## 阶段边界

**阶段**是会话里的一段工作：拷问、实现、QA。在两个阶段之间的**边界**上，你有五个选项，而在它们之间做选择是整张地图里最模糊的决定：

- **继续**：原地不动。不花任何代价，不丢任何东西。
- **`/clear`**：清空窗口，当这里的一切都与接下来无关时。
- **`/handoff`**：写一份可移植的 Markdown 文件。用途很窄：只用于**换 harness**、**换目录**、**交给同事**，或在**阶段中途**分出一个旁支任务。它换来的是可移植性。
- **子代理**：把一个范围紧凑的任务送进它自己的窗口，拿回一份报告。
- **`/compact`**：压缩当前上下文，用它开启一个新会话。它是**默认项**，位于决策树底部，而不是第一反应。

有序的决策树（五个问题、每个分支背后的理由、以及为什么一手资料的代价让**继续**成为最先要排除的选项）见 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)。决定**在**边界上做；阶段中途只有继续，或把剩下的工作拆给子代理。

## 独立工具

完全不在流程上。

- **`/grill-me`**：和 `/grill-with-docs` 一样无情的拷问，但**无状态**：不在本地保存任何东西，不建 `CONTEXT.md`。**不在工作目录里**时用它（打磨一个计划、一个设计、一篇文章，任何底下没有仓库的东西）。在工作目录里就用 `/grill-with-docs`：同样的拷问，还留下文字记录，严格更好。
- **`grilling`**：拷问原语本身：规模分档、轮次、前沿、事实归 agent 而决策归你。`/grill-me` 和 `/grill-with-docs` 是它的两个具名入口，`/triage`、`/wayfinder`、`/improve-codebase-architecture` 都在内部使用它。只有想要不带任何包装的拷问时才直接找它。
- **`resolving-merge-conflicts`**：逐个 hunk 处理进行中的 merge 或 rebase 冲突，按追溯到双方一手资料的**意图**来解决，而不是挑行，然后完成操作。已经身处冲突中时用它。
- **`prototype`**：一个回答一个设计问题的小型一次性程序：这个状态模型说得通吗，这个 UI 应该长什么样。"一次性"约束的是代码怎么写，而不是承诺销毁它：答案折回真实代码，原型本身作为**一手资料**保留在主干之外的 `prototype/<名字>` 分支上，由实现 issue 指向。它是主流程第 2 步的绕道，但任何设计问题在纸面上难以定下来时都可以用。
- **`research`**：把阅读跑腿活交给一个**后台 agent**：它对照**一手资料**调查问题，在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。产出的文件应带*进*主流程的 `/grill-with-docs`，因为调研是为思考提供养料，而不是取代思考。
- **`/to-questionnaire`**：卡住你的东西不在你脑子里、也不在代码库里，而在**别人**脑子里时用它，它给那个人写一份问卷。它是 `/grill-me` 的反面：不拷问你主题本身，而是拷问你**发送**这件事（发给谁、需要拿回什么），并把问题瞄准缺口。拿回来的东西是 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`wizard`**：用于只有**人**才能迈出的步骤：开通基础设施、配置凭据或 CI 密钥、在陌生的第三方控制台里点来点去、执行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、抓取每个值、写入 `.env` 和 GitHub secrets，这个流程就不再是每次都要重新给 agent 解释的东西。agent 碰到只有你能通过的墙时会自己用上它。agent 自己能做的，它就直接做；这是给确实需要人在回路里的地方用的。
- **`/wait-what`**：一条消息没看懂时的纠正工具。在对话中途、在任何其他 skill 里面都能用，agent 会用平实的话、`CONTEXT.md` 的词汇，带上你缺的背景把刚才的话重讲一遍。它是事后补救；`/grill-with-docs` 是事前的解药，因为早早约定好的通用语言才能从源头上挡住行话。
- **`/teach`**：以当前目录为有状态的工作区，分多次会话学一个概念。
- **`writing-for-agents`**：为 agent 写文档的参考：skill、AGENTS.md、被指针指向的文档；附带用子代理压测纪律型 skill 的方法。

## 前置条件

**`/setup-dev-skills`**：第一次跑工程流程之前运行，配置其他 skill 所假设的 issue 追踪器、分诊标签和文档布局。自定义的 issue 追踪器也支持。
