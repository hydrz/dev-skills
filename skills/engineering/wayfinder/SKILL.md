一个松散的想法到来，大到一个 agent 会话装不下，还裹在迷雾里：从这里到**目的地**的路还看不见。寻路是去找那条路，而不是朝目的地硬冲。本 skill 把路绘成仓库 issue 追踪器上的一张**共享地图**，然后逐张处理它的**决策工单**（解决它得到的是一个决定，而不是一块要执行的构建切片），直到路线清晰。

目的地因工作而异，给它命名是绘图的第一步：它塑造每一张工单。它可能是一份要交出去迭代的规格，一个开始规划之前必须锁定的决定，或者一次就地完成的改动，比如数据结构迁移。地图不限领域：工程工作、课程内容，只要形状合适都行。

## 规划，不执行

寻路默认是**规划**：每张工单解决一个决定，路清晰了地图就完成，此时在有人去做那件事之前已没有什么需要决定。想直接动手干活的冲动，通常是你已经走到地图边缘、该交接的信号。某项工作可以在**备注**里改写这条规则，把执行也纳入地图；没有这样写时，产出决定，而不是交付物。

## 用名字指代

每张地图和工单都是一个 issue，所以都有**名字**：它的标题。在人要读的一切内容里（叙述、地图的已做决策），用名字指代，而不是裸的 id、编号或 slug。一墙的 `#42, #43, #44` 没法读；名字一眼就懂。id 和 URL 并不消失：名字包着链接，它们藏在名字里面，而不是取代名字。

## 地图

地图是本仓库 issue 追踪器上的一个 issue，带 `wayfinder:map` 标签，是规范产物。它的工单是地图的子 issue。

地图是**索引**，不是仓库。它列出已做的决定并指向承载细节的工单；一个决定只住在一个地方，即它的工单，所以地图从不复述决定，只写要点并链接。

**地图、子工单、阻塞关系、前沿查询在物理上怎么表达，取决于追踪器。** issue 追踪器配置应已提供给你；若没有，告诉用户运行 `/setup-dev-skills`。查看追踪器文档的"寻路操作"一节，了解*本*仓库如何表达它们。完全没有追踪器配置时，默认使用本地 Markdown 追踪器。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。打开的工单**不**列在这里：它们是打开的子 issue，靠查询找到。

```markdown
## 目的地

<走完这张地图是什么样子：这项工作要找到路去的规格、决定或改动。一两行；每个会话选工单之前都先对准它。>

## 备注

<领域；每个会话都应参考的 skill；这项工作的长期偏好>

## 已做决策

<!-- 索引：每张已关闭工单一行，足以判断相关性，需要细节就点链接看工单 -->

- [<已关闭工单标题>](链接)：<答案的一句话要点>

## 尚未明确

<!-- 见"战争迷雾"：在范围内、但还无法写成工单的迷雾；随前沿推进逐渐毕业 -->

## 不在范围内

<!-- 见"不在范围内"：被判定在目的地之外的工作；已关闭，永不毕业 -->
```

### 工单

每张工单是地图的一个**子 issue**，追踪器的 issue id 就是它的身份。正文是问题，大小以一个约 10 万 token 的 agent 会话为准：

```markdown
## 问题

<这张工单要解决的决定或调查>
```

每张工单带一个 `wayfinder:<类型>` 标签：`research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#工单类型)）。

会话通过把工单指派给推进地图的开发者来**认领**它，而且**第一件事**就是认领，在任何工作之前，这样并发的会话会跳过它。指派人*就是*认领：打开且未指派的工单就是未认领的。

阻塞使用追踪器的**原生**依赖关系：这很关键，因为它在追踪器自己的界面里*可视化*地呈现前沿，人不必打开地图就能看到哪些可以领。只有缺少原生阻塞功能的追踪器才退回到正文约定。一张工单的所有阻塞者都关闭后，它就**解除阻塞**；**前沿**是打开、未阻塞、未认领的子工单，已知世界的边缘。

答案不属于正文，而是在解决时记录（见[推进地图](#推进地图)）。解决工单时产生的资产从 issue 链接出去，不粘贴进来。

## 工单类型

每张工单要么是 **HITL**（人在回路，和一个替自己发言的人一起完成），要么是 **AFK**（离席，由 agent 独自推进）。HITL 工单只能通过这种实时交流来解决；agent 不代替人那一方发言（一个自问自答的拷问 agent 就破坏了这一点）。

- **调研**（AFK）：阅读文档、第三方 API 或本地资源（如知识库），找出某个决定所等待的事实。由一个调用 Skill 工具、参数为 `research` 的子代理解决。需要当前工作目录之外的知识时使用。
- **原型**（HITL）：做一个便宜、粗糙、具体的产物（一份大纲、一个粗略方案、一个桩、UI 或逻辑代码）来提高讨论的保真度，调用 Skill 工具，参数为 `prototype`。把原型作为资产链接。"它应该长什么样"或"它应该怎么表现"是关键问题时使用。
- **拷问**（HITL）：对话。默认情况。调用 Skill 工具两次，分别为 `grilling` 和 `domain-modeling`。
- **任务**（HITL 或 AFK）：在某个*决定*能做出之前必须先完成的手动工作：没什么可决定、可做原型、可调研的，但讨论被它卡住了。注册某个服务以便评估它的 API、开通访问权限、搬运数据以便看清它的形状。这是唯一一种*做事*而不是*做决定*的类型，它的存在价值在于解除某个决定的阻塞，而不是交付目的地。agent 能独自完成的就独自完成（AFK）；否则给人一份精确的清单（HITL），需要人去做时调用 Skill 工具，参数为 `wizard`。做完即解决；答案记录做了什么，以及后续工单依赖的结果事实（凭据存放位置、新 URL、行数）。

## 战争迷雾

地图是*刻意*不完整的：看不见的地方先不画。当前工单之外是**战争迷雾**（fog of war）：你看得出将会出现、但还无法钉住的决定和调查，因为它们悬在仍未解决的问题上。解决一张工单会驱散它前方的迷雾，把现在已经可以明确的东西一张一张地毕业成新工单，直到通往目的地的路清晰、不再剩下工单。

地图的**尚未明确**一节就是写下这片朦胧视野的地方：猜测中的问题、以后要回头看的区域。它是通*往*目的地的未探明前沿：这里的一切都在范围内，只是还不够清晰，写不成工单。视野允许多模糊就写多模糊，允许多完整就写多完整；它同时也是给协作者的路标，告诉他们这项工作的走向。

**迷雾还是工单？** 判据是你*现在*能不能把问题陈述精确，*而不是*你现在能不能回答它。

- **写成工单**：问题已经清晰，哪怕它被阻塞、暂时无法处理。
- **放进尚未明确**：你还无法把它说得那么清晰。不要把迷雾预先切成工单大小：它比工单粗，一片迷雾在前沿抵达时可能毕业成好几张工单，也可能一张都没有。

**尚未明确**不包括已经决定的（已做决策）、已经是当前工单的、以及不在范围内的（下一节）。

## 不在范围内

迷雾只会*朝着*目的地聚集。目的地确定了范围，所以超出它的工作是**不在范围内**：它不是迷雾，不属于**尚未明确**。它在地图上有自己的**不在范围内**一节：被你有意识地排除在*这项*工作之外的事。决定它落在这里的是范围，而不是清晰度。

不在范围内的工作永不毕业（前沿止于目的地），只有目的地被重新划定时才会回来，而且是作为一项新工作，而不是续接。

把某件事判定为不在范围内是一个划定范围的动作，不是路线上的一步。一张已有的工单被发现位于目的地之外（绘图时误纳入，或被某个解决结果暴露出来），**关闭它**（已关闭的工单明确地离开了前沿），并在**不在范围内**一节留一行：要点加上为什么不在范围内，链接到已关闭的工单。它不进**已做决策**，那里记录的是实际走过的路线；范围边界不是路线上的一步。

## 调用

两种模式。无论哪种，**每个会话最多解决一张工单**，调研工单除外。

### 绘制地图

用户带着一个松散的想法调用。

1. **给目的地命名。** 调用 Skill 工具两次，分别为 `grilling` 和 `domain-modeling`，钉住这张地图要找路去的地方：规格、决定还是改动。目的地确定范围，所以先定它。
2. **绘出前沿。** 再拷问一次，这次**广度优先**：在整个空间里铺开，而不是在任何一条线上深挖，找出悬而未决的决定和现在就能迈出的第一步。**如果这一步没发现迷雾**（通往目的地的路已经清晰，整个旅程小到一个会话就能装下），你不需要地图。停下来，问用户想怎么继续。
3. **创建地图**（标签 `wayfinder:map`）：填好目的地和备注，已做决策留空，把迷雾勾勒进**尚未明确**。
4. **创建现在能明确的工单**作为地图的子 issue，然后在**第二遍**连上阻塞边（issue 要先有 id 才能互相引用）。连线把它们分成前沿和被阻塞的两类；还无法明确的一切留在迷雾里：**尚未明确**一节。
5. **派出调研子代理。** 为刚创建的每张 `research` 工单派一个调用 Skill 工具、参数为 `research` 的子代理并行解决，把结论留存在一次性的 `research/<名字>` 分支上，并从工单留一个上下文指针。
6. 停下：绘图是一个会话的工作，不亲手解决任何工单。

### 推进地图

用户带着一张地图（URL 或编号）调用。工单是**可选的**：没有指定时，由你而不是用户挑下一个决定。

1. 加载**地图**：低分辨率视图，而不是每张工单的正文。
2. 选工单。用户指定了就用它。否则按顺序取前沿上的第一张。**认领它**：在任何工作之前指派给自己。
3. 解决它。**按需放大**：随时拉取任何相关或已关闭工单的完整正文；**备注**里点名了哪些 skill，就调用 Skill 工具去用。拿不准时，调用 Skill 工具两次，分别为 `grilling` 和 `domain-modeling`。
4. 记录解决结果：把答案发成一条**解决评论**，**关闭** issue，并往地图的已做决策里**追加一个上下文指针**。
5. 添加新浮现的工单（先创建再连线）；把答案已让其可以明确的迷雾毕业，从**尚未明确**里清掉每一片已毕业的迷雾，让它只以新工单的形式存在。答案揭示某张工单（这张或另一张）位于目的地之外时，**判定为不在范围内**，而不是在路线上解决它。决定让地图的其他部分失效时，更新或删除那些工单。

用户可能并行推进多张未阻塞的工单，所以预期会有其他会话同时在编辑追踪器。

## 地图清晰之后

路清晰了，**交接，不构建**：从 `/to-spec` 汇入主流程，把地图上链接的决定收拢成一份可构建的计划，然后照常 `/to-tickets`、`/implement` 或 `/implement-spec`。告诉用户下一步运行哪个。
