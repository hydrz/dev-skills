# 接收评审意见

评审意见是需要评估的技术主张，不是需要安抚的情绪。

**原则：** 先核实再实现，拿不准先问，技术正确优先于社交舒适。

## 响应模式

```
收到评审意见时：

1. 读完：把全部意见读完，先不动手
2. 理解：用自己的话复述每条要求（复述不了就问）
3. 核实：对照代码库的实际情况
4. 评估：对这个代码库而言，技术上成立吗？
5. 回应：技术性确认，或有理有据地反驳
6. 实现：一次一条，每条都测
```

## 回应的写法

意见正确时，直接陈述修复：

- "已修复：<改了什么>。"
- "确实，<具体问题>。已在 <位置> 修复。"
- 或者直接改，让代码说话。

回应里只放技术内容：复述要求、提澄清问题、给出反驳理由，或者直接开始干活。"说得太对了！""好建议！"这类表演式附和不传递任何信息，也会让人误以为你还没核实就已经接受。

## 含糊的意见

```
有任何一条不清楚时：
  先不实现任何一条
  就不清楚的条目请求澄清

原因：条目之间可能相关，理解一半就会实现错。
```

例子：

```
用户："把 1 到 6 都修了"
你看懂了 1、2、3、6，没看懂 4、5。

✅ "1、2、3、6 我理解了。4 和 5 需要先澄清再动手。"
❌ 先改 1、2、3、6，回头再问 4、5
```

## 按来源区别对待

### 来自用户

- **可信**：理解之后就实现
- 范围不清时**仍然要问**
- 直接行动或给出技术性确认

### 来自外部评审者或评审子代理

实现之前逐项检查：

1. 对**这个**代码库，技术上正确吗？
2. 会破坏现有功能吗？
3. 当前实现这样写有没有原因？
4. 在所有平台、所有版本上都成立吗？
5. 评审者掌握完整上下文吗？

- 建议看起来是错的：给出技术理由反驳。
- 不容易核实：直说，"没有 <X> 我无法核实这点。要我去调查、去问，还是先照做？"
- 与用户之前做过的决定冲突：先停下来和用户讨论。

## YAGNI 检查

评审者建议"把它做完整 / 做规范"时：

```
grep 代码库，看实际有没有人用

没人用："这个接口没有调用方。按 YAGNI 删掉？"
有人用：那就把它做完整
```

你和评审者都向用户负责。用不到的功能，不加。

## 实现顺序

```
多条意见时：
  1. 先把所有不清楚的澄清
  2. 再按这个顺序实现：
     - 阻塞性问题（功能损坏、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 每条修复单独测试
  4. 确认没有回归
```

## 何时反驳

- 建议会破坏现有功能
- 评审者缺乏完整上下文
- 违反 YAGNI（功能没人用）
- 对这个技术栈而言技术上不正确
- 有遗留或兼容性方面的原因
- 与用户的架构决策冲突

怎么反驳：用技术理由，而不是防御姿态；提具体的问题；引用能工作的测试或代码；涉及架构时拉上用户。

对当面反驳感到别扭时，说出这种别扭，然后把你看到的问题告诉用户。

## 反驳错了时

```
✅ "你是对的，我查了 <X>，它确实 <Y>。现在改。"
✅ "核实过了，你说得对。我之前的理解错在 <原因>。在修。"
```

事实性地陈述更正，然后继续干活。长篇道歉和为之前的反驳辩护都不必。

## GitHub 行内评论

回复 GitHub 上的行内评审评论时，回复到该评论的线程里（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为 PR 顶层评论。
