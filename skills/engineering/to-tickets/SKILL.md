# 拆成工单

把计划、规格或对话拆成一组**工单**：曳光弹（tracer bullet）式的垂直切片，每张声明**阻塞**它的其他工单。

issue 追踪器和分诊标签词汇应已提供给你；若没有，告诉用户运行 `/setup-dev-skills`。

## 过程

### 1. 收集上下文

以对话上下文里已有的内容为准。用户作为参数传入了引用（规格路径、issue 编号或 URL）时，拉取并读完它的正文和全部评论。

### 2. 探索代码库（可选）

还没探索过代码库的话，先探索，了解代码现状。工单标题和描述使用项目术语表的词汇，并尊重所涉及区域的 ADR。

寻找预重构的机会，让实现变容易。"先让改动变容易，再做容易的改动。"

### 3. 起草垂直切片

把工作拆成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片窄但**完整**地穿过每一层（schema、API、UI、测试）：是垂直的，不是某一层的水平切片
- 完成的切片本身就能演示或验证
- 每个切片的大小能装进一个全新的上下文窗口
- 预重构放在最前面

</vertical-slice-rules>

给每张工单标上**阻塞边**：开始它之前必须完成的其他工单。没有阻塞者的工单可以立即开始。

给每张工单写上**接口**：

- **消费**：它用到的、由前面工单产出的东西，写到名字和形状（函数名、参数与返回类型、事件名、schema 字段）
- **产出**：后续工单要依赖的东西，同样写到名字和形状

一张工单的实现者只看得到自己这一张，这一块就是他得知相邻工单所用名字和类型的途径。接口写的是契约，不是文件路径。

**大范围重构是垂直切片的例外。** **大范围重构**是一个机械性改动（重命名一列、给共享符号换类型），其**爆炸半径**扇出到整个代码库，改一处就同时弄坏成千上万个调用点，任何垂直切片都无法保持绿色落地。不要硬塞进曳光弹；按**扩展-收缩**排序。先扩展：在旧形式旁边加上新形式，什么都不坏。再按爆炸半径分批迁移调用点（每个包、每个目录），每批一张工单，被扩展工单阻塞；由于旧形式还在，批与批之间 CI 保持绿色。最后收缩：没有调用方剩下时删掉旧形式，这张工单被所有迁移批次阻塞。连单独的批次都无法保持绿色时，保留这个顺序，但让它们共享一个集成分支，全部阻塞最后一张"集成并验证"的工单；只在那里承诺绿色。

### 4. 自查

展示给用户之前，自己先查一遍，发现问题当场改：

- **覆盖**：逐节扫一遍源头规格或计划。每条要求都能指到一张实现它的工单吗？找不到就补工单。
- **占位符**：有没有"待定""TODO""加上适当的错误处理""处理边界情况""类似第 N 张"这种没有实际内容的描述？改成具体的行为和验收标准。
- **接口一致**：后面工单消费的名字和类型，与前面工单产出的完全一致吗？第 3 张叫 `clearLayers()`、第 7 张叫 `clearFullLayers()`，就是 bug。
- **阻塞边**：每条边都是真的门槛吗？有没有漏掉的依赖？

### 5. 与用户确认

把拟定的拆分以编号列表展示。每张工单显示：

- **标题**：简短的描述性名字
- **被阻塞于**：必须先完成的其他工单（如有）
- **交付什么**：这张工单让哪段端到端行为可以工作

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对吗：每张工单是否只依赖真正卡住它的工单？
- 有没有该合并或进一步拆分的？

反复修改，直到用户认可这个拆分。

### 6. 发布到已配置的追踪器

发布认可后的工单。**怎么发**取决于 `/setup-dev-skills` 配置的追踪器；工单本身一样，只是阻塞边的表达形式不同：

- **本地文件** → 每张工单一个文件：`.scratch/<功能-slug>/issues/<NN>-<slug>.md`，按依赖顺序从 `01` 编号（阻塞者在前）。每个文件的"被阻塞于"列出它依赖的编号 / 标题。用下面的单工单模板：一张工单一个文件，不合并。
- **真实 issue 追踪器（GitHub、GitLab 等）** → 按依赖顺序（阻塞者在前）每张工单发一个 issue，这样每张工单的阻塞边能引用真实的标识符。平台有原生阻塞 / 子 issue 关系就用；没有就把"被阻塞于"写成阻塞者 issue 的引用。除非另有指示，打上 `ready-for-agent` 分诊标签；这些工单天生就能被 agent 领走。

按**前沿**推进：阻塞者全部完成的任意工单。纯线性链就是从上到下。

不要关闭或修改任何父 issue。
