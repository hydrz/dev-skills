# 拆分开发任务

把计划、规格或对话拆成一组**开发任务**。每项任务都是端到端最小闭环任务（思路来自“曳光弹”，tracer bullet）：范围窄，但完整穿过各层。每项任务都列出自己的**前置依赖**，也就是开始它之前必须完成的其他任务。

issue 追踪器和分诊标签词汇应该已经提供给你；如果没有，告诉用户运行 `/setup-dev-skills`。范围清单的格式和规则见 `docs/agents/scope-inventory.md`。

## 过程

### 1. 收集上下文

以对话中已有的内容为准。用户通过参数传入引用（规格路径、issue 编号或 URL）时，读取它的正文和全部评论。

读取规格的“事实来源”和“范围项”两节，以及链接到的范围清单。这份规格负责的范围项及其状态集就是本次拆分必须完整覆盖的对象。

### 2. 探索代码库（可选）

如果还没有探索过代码库，先探索，了解代码现状。任务标题和描述使用项目术语表中的词汇，并遵守涉及区域的 ADR。

寻找可以先做的重构，让后续实现变得容易。“先让改动变容易，再做容易的改动。”

### 3. 起草任务

把工作拆成端到端最小闭环任务。

<vertical-slice-rules>

- 每项任务范围窄，但**完整**穿过每一层（schema、API、UI、测试）：按功能纵向切分，而不是只做某一层
- 任务完成后本身就能演示或验证
- 每项任务的规模能在一个全新的上下文窗口内完成
- 预备性重构放在最前面
- 验收标准写明覆盖的**范围项编号和具体状态**，例如“S-042：默认、支付中、已解锁”；只写“符合设计”“处理各种错误”不算验收标准
- 界面范围项的验收标准包含“与设计依据逐个状态截图对比一致”，并链接设计依据
- 只打通一条链路的任务（一个支付渠道、一种分成模式、一个端）可以先做，但同一范围项的其余变体和状态必须由后续任务覆盖
- 一项任务覆盖的范围项超过 5 个时，考虑继续拆分

</vertical-slice-rules>

为每项任务写上**前置依赖**：开始它之前必须完成的其他任务。没有前置依赖的任务可以立即开始。

为每项任务写上**接口**：

- **依赖**：它要用到、由前面任务提供的内容，写清名称和结构（函数名、参数与返回类型、事件名、schema 字段）
- **提供**：后续任务要依赖的内容，同样写清名称和结构

实现者只看得到自己负责的那一项任务，接口这一节是实现者了解相邻任务所用名称和类型的唯一途径。接口描述的是契约，不是文件路径。

#### 大范围重构

大范围重构不适用纵向切分。**大范围重构**指机械性改动（例如重命名一列、修改共享符号的类型），它的影响会扩散到整个代码库：改一处就会同时破坏大量调用点，任何纵向切分都无法让测试保持通过。

这类工作按**扩展、迁移、收缩**排序：

1. **扩展**：在旧形式旁边加入新形式，不破坏任何代码。
2. **迁移**：按影响范围分批迁移调用点（例如每个包、每个目录），每批一项任务，前置依赖为扩展任务。旧形式仍然存在，所以批次之间 CI 保持通过。
3. **收缩**：没有调用方后删除旧形式。这项任务以所有迁移批次为前置依赖。

如果连单个批次都无法保持测试通过，仍然保留上述顺序，但让所有批次共享一个集成分支，并统一作为最后一项“集成并验证”任务的前置依赖。只在这项任务中要求测试通过。

### 4. 自查

展示给用户之前，自己先检查一遍，发现问题就地修改：

- **覆盖**：逐节检查源规格或计划。每条要求都能对应到实现它的任务吗？找不到就补充任务。
- **范围项覆盖**：列出这份规格负责的每个范围项和它的每个状态，逐个找到覆盖它的任务。有任何状态没有任务覆盖，就补充任务，不发布缺口。确实认为某个范围项或状态不该做时，停下来问用户，由用户确认后按清单规则记录，不自行删减。
- **事实来源**：每项任务都链接了它需要的事实来源；界面范围项链接了设计依据。
- **占位符**：是否有“待定”、TODO、“加上适当的错误处理”“处理边界情况”“类似第 N 项”这类没有实际内容的描述？改成具体的行为和验收标准。
- **接口一致**：后面任务依赖的名称和类型，是否与前面任务提供的完全一致？例如第 3 项叫 `clearLayers()`、第 7 项叫 `clearFullLayers()`，这就是 bug。
- **前置依赖**：每条依赖都是真实的前提吗？是否漏掉了依赖？

### 5. 与用户确认

用编号列表展示拟定的拆分。每项任务显示：

- **标题**：简短的描述性名称
- **前置依赖**：必须先完成的其他任务（如有）
- **交付内容**：这项任务让哪段端到端行为可以工作
- **范围项**：覆盖的范围项编号和状态

最后附一张覆盖表：范围项编号、状态、覆盖任务，让用户一眼看出没有遗漏。

询问用户：

- 粒度是否合适，是太粗还是太细？
- 前置依赖是否准确，每项任务是否只依赖真正需要先完成的任务？
- 是否有需要合并或进一步拆分的任务？

根据反馈修改，直到用户认可这个拆分。

### 6. 发布到已配置的追踪器

发布用户认可的任务。发布前再核对一次范围项覆盖：仍有状态没有任务覆盖时，不发布，回到第 3 步。

发布方式取决于 `/setup-dev-skills` 配置的追踪器；任务内容相同，只是前置依赖的表达形式不同：

- **本地文件**：每项任务一个文件，路径为 `.scratch/<功能-slug>/issues/<NN>-<slug>.md`。按依赖顺序从 `01` 编号，被依赖的任务在前。每个文件的 `Blocked by` 行列出所依赖任务的编号。使用下面的本地任务模板，一项任务一个文件，不合并；字段行的含义见追踪器文档。
- **真实 issue 追踪器（GitHub、GitLab 等）**：按依赖顺序（被依赖的任务在前）为每项任务创建一个 issue，这样前置依赖可以引用真实的 issue 标识。平台支持原生的阻塞关系或子 issue 关系时就使用；不支持时，在“前置依赖”中写上对应 issue 的引用。除非另有指示，加上 `ready-for-agent` 分诊标签，这些任务创建后就可以交给 agent 领取。

发布后回填范围清单的“任务”列，写明每项任务覆盖哪些状态，例如 `T09（默认、支付中）、T11（失败）`。小功能没有独立清单时，回填规格的“范围项”一节。

执行顺序：任意时刻，前置依赖全部完成的任务都可以开始。纯线性依赖就是从上到下依次执行。

不要关闭或修改任何父 issue。
