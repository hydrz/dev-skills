# ADR 格式

ADR 放在 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`。

`docs/adr/` 目录在需要第一条 ADR 时再创建。

## 模板

```md
# {决策的简短标题}

{1 到 3 句：背景是什么，决定了什么，为什么。}
```

就这些。一条 ADR 可以只有一段。价值在于记下*做过*这个决定以及*为什么*，而不在于填满各个小节。

## 可选小节

只在确有价值时加。大多数 ADR 用不到。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时有用
- **考虑过的方案**：只在被否决的方案值得记住时写
- **后果**：只在下游影响不明显、需要点出时写

## 编号

扫描 `docs/adr/` 找到最大编号，加一。

## 何时提议 ADR

三条必须同时成立：

1. **难以逆转**：以后改主意的代价不小
2. **缺乏上下文会令人意外**：未来的读者看代码时会纳闷"他们到底为什么这么做？"
3. **确有取舍**：存在真正的备选方案，出于具体理由选了其中一个

容易逆转的，跳过：到时候改回来就是。不令人意外的，没人会问为什么。没有真正备选的，除了"我们做了显而易见的事"之外没什么可记。

### 符合条件的

- **架构形态。** "我们用 monorepo。""写模型用事件溯源，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "订购和计费通过领域事件通信，不走同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库都算，只算那些要花一个季度才换得掉的。
- **边界与范围决策。** "客户数据归客户上下文所有；其他上下文只按 ID 引用。"明确的"不做"和"做"一样有价值。
- **有意偏离显而易见的路径。** "我们用手写 SQL 而不是 ORM，因为 X。"任何理智读者都会默认相反做法的地方。这能防止下一个工程师去"修复"一个有意为之的设计。
- **代码里看不到的约束。** "因为合规要求不能用 AWS。""响应时间必须低于 200ms，因为合作方 API 合同这么规定。"
- **否决理由不明显的备选方案。** 你考虑过 GraphQL，出于微妙的理由选了 REST，就记下来；否则半年后又会有人提 GraphQL。
