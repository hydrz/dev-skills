# ADR 格式

ADR 放在 `docs/adr/`，按顺序编号：`0001-slug.md`、`0002-slug.md`。

需要第一条 ADR 时，再创建 `docs/adr/` 目录。

## 模板

```md
# {决策的简短标题}

{1 到 3 句：背景是什么，决定了什么，为什么这样决定。}
```

这就足够了。一条 ADR 可以只有一段。它的价值在于记录*作过*这个决定以及*为什么*，而不在于填满各个小节。

## 可选小节

只在确实有价值时添加。大多数 ADR 用不到。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策可能被重新审视时有用
- **考虑过的方案**：只在被否决的方案值得记住时写
- **后果**：只在下游影响不明显、需要特别指出时写

## 编号

扫描 `docs/adr/`，找到最大编号，加一。

## 何时提议 ADR

必须同时满足三个条件：

1. **难以逆转**：以后改变决定的代价不小
2. **缺少上下文时会令人意外**：未来的读者看代码时会疑惑“为什么要这样做？”
3. **确实存在取舍**：有真正可行的备选方案，基于具体理由选择了其中一个

容易逆转的决定，不写：需要时改回来即可。不令人意外的决定，不会有人问为什么。没有真正备选方案的决定，除了“我们做了显而易见的选择”之外没有可记录的内容。

### 符合条件的例子

- **架构形态。** “我们使用 monorepo。”“写模型使用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成方式。** “订购和计费通过领域事件通信，不使用同步 HTTP。”
- **有锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库都算，只算那些需要花一个季度才能替换的选择。
- **边界与范围决策。** “客户数据归客户上下文所有；其他上下文只通过 ID 引用。”明确记录“不做什么”和“做什么”同样有价值。
- **有意偏离常规做法。** “我们使用手写 SQL 而不是 ORM，因为 X。”凡是理性的读者会默认采用相反做法的地方，都值得记录。这样能避免下一位工程师“修复”一个有意为之的设计。
- **代码中看不到的约束。** “因为合规要求，不能使用 AWS。”“响应时间必须低于 200ms，因为合作方 API 合同有此规定。”
- **否决理由不明显的备选方案。** 如果你考虑过 GraphQL，却因为不明显的原因选择了 REST，就记录下来；否则半年后又会有人提议 GraphQL。
