# 领域建模

设计过程中主动构建并打磨项目的领域模型。这是*主动*的纪律：质疑术语、编造边界场景、在术语表和决策成形的那一刻就写下来。（只是*读* `CONTEXT.md` 获取词汇不属于本 skill，那是任何 skill 都能做的一行习惯。本 skill 用于你在改变模型，而不只是消费它。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

根目录有 `CONTEXT-MAP.md` 时，仓库有多个上下文，地图指向每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文内决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

文件按需创建：有东西要写时才建。没有 `CONTEXT.md`，第一个术语确定时创建；没有 `docs/adr/`，第一条 ADR 需要时创建。

## 会话中

### 对照术语表质疑

用户用的词与 `CONTEXT.md` 里已有的语言冲突时，立刻指出。"你的术语表把'取消'定义为 X，但你现在的意思似乎是 Y。到底是哪个？"

### 磨尖模糊的说法

用户用了含糊或一词多义的词时，提出一个精确的规范术语。"你说的'账户'，指的是客户还是用户？这是两个东西。"

### 用具体场景推敲

讨论领域关系时，用具体场景做压力测试。编造能探到边界的场景，逼用户把概念之间的界线说准。

### 与代码交叉核对

用户陈述某件事如何运作时，检查代码是否一致。发现矛盾就摆出来："你的代码会取消整个订单，但你刚才说可以部分取消。哪个对？"

### 就地更新 CONTEXT.md

一个术语确定下来，当场更新 `CONTEXT.md`，一个一个随时记，不攒批。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 只收领域术语，不含实现细节。它是术语表，不是规格、草稿本或实现决策的仓库。

### 克制地提议 ADR

只有三条同时成立时，才提议写 ADR：

1. **难以逆转**：以后改主意的代价不小
2. **缺乏上下文会令人意外**：未来的读者会纳闷"他们为什么这么做？"
3. **确有取舍**：存在真正的备选方案，出于具体理由选了其中一个

缺任何一条就不写。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

### 标出 ADR 冲突

你的产出与已有 ADR 相矛盾时，显式标出，而不是悄悄覆盖：

> _与 ADR-0007（订单事件溯源）矛盾，但值得重新讨论，因为……_
