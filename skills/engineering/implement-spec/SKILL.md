你拿到了一份规格，以及实现它的开发任务。目标是在**一个分支**上实现整份规格，通过一个 PR 交付。

issue 追踪器配置应该已经提供给你；如果没有，告诉用户运行 `/setup-dev-skills`。

## 角色

你是**协调者**。实现、修复、合并和评审都交给子代理完成。你的上下文留给协调工作：阅读报告、作出代行决策、更新进度记录、派发当前可执行的任务。亲自修改代码会占用你的上下文，也会绕过评审。

与子代理的沟通尽量精简，主要使用**上下文指针**：指向规格、任务、进度记录、报告文件和之前的提交。

- 指针能提供的信息，不在派发提示中重复。
- 不要把前面任务的历史摘要贴进后续派发。
- 你贴进提示的内容和子代理打印回来的内容都会一直占用你的上下文，所以产物以文件形式交接。

## 按依赖关系调度任务

任务之间有前置依赖，因此任何时刻都有一组**当前可执行任务**：前置依赖都已完成、现在就能领取的任务。这些任务并行推进，以获得**最大并行度**。一项任务完成后，可执行任务集合会变化，立即为新解锁的任务派出实现者。

并行的前提是互不干扰：

- 每个实现者在**自己的工作树**和分支上工作，分支基于集成分支的当前头部。
- 两项可执行任务会修改同一个模块或同一个接口时，改为串行：先完成一项并合并，再派发另一项。

## 自行决策，不停下等待

规格执行期间不等待用户回复。遇到冲突、歧义、任务缺陷或需要突破的上限时，由你决定。

- **规格是最终依据**，任务是对规格的拆解。功能清单和设计依据是规格的依据文档，同样以它们为准。
- 规格和任务都没有回答的问题，由你判断。

每个代行决策都写入进度记录：

```
决策：<决定了什么> | 理由：<为什么> | 如果错了：<会造成什么影响>
```

然后继续推进。错误决策造成的返工，用户能看到、也能纠正；停在一个问题上等回复，会浪费用户一整天。

只有以下五类情况需要停下来询问用户：

1. 不可逆或破坏性操作
2. 安全敏感操作
3. 当前工作树之外、按惯例需要先询问的副作用（合并到共享分支、推送到共享分支、发布），开始时已获授权的除外
4. 任务或规格缺陷严重，任何推进方式都只能靠猜测
5. **缩减范围**：把功能项改为“不做”、删掉或推迟某个状态、页面做得达不到设计依据。这类改动会让交付物缺功能，只能由用户决定，不能作为代行决策

增加范围可以作为代行决策：发现漏掉的功能项或状态时，补进功能清单和对应任务（必要时新增任务），写入进度记录后继续。

## 准备

1. **阅读规格和任务。** 读到足以理解任务依赖关系即可：每项任务的标题、前置依赖、接口、功能项，以及规格的全局约束和依据文档。无需读入每项任务的细节，实现者会阅读自己负责的任务。

2. **进度记录。** 进度记录用于在上下文压缩或会话中断后恢复状态，格式见 [LEDGER.md](LEDGER.md)。
   - 路径：`<仓库根>/.dev-skills/implement-spec/<规格-slug>/ledger.md`，并确保 `.dev-skills/` 被 git 忽略。
   - 已有进度记录且第一行指向这份规格时，从记录恢复：已标为完成的任务不再派发，根据进度记录和 `git log` 重建状态。两者与你的记忆不一致时，以它们为准。
   - 第一行指向其他规格时，那是另一份规格的进度。保持原样，为当前规格新建记录。

3. **预检。** 派发第一项任务之前，检查所有任务之间的冲突，边检查边写入进度记录：
   - 共享同一接口的每对任务：一方**提供**的名称和结构，是否与另一方**依赖**的一致
   - 与规格全局约束矛盾的任务
   - 任务的验收标准是否与它描述的行为一致
   - 规格负责的每个功能项的每个状态，是否都有任务覆盖；页面类功能项的任务是否链接了设计依据。缺口按增加范围处理：补任务或补链接，写入进度记录

   预检的输出是进度记录中的一张表，不是一句“没问题”。每发现一个冲突，就当场作出代行决策并记录，然后开始执行。实现过程中才出现的冲突由评审环节发现。

4. **分支与 PR。** 与用户确认一次：新建集成分支并创建草稿 PR（注明关闭规格 issue 和任务 issue），还是只在本地分支完成。之后按确认结果执行，不再逐次询问。

5. **可选：探索子代理。** 任务需要大量探索（相关代码文件、外部文档）时，派一个探索子代理，把 Markdown 笔记写到仓库外、所有后续子代理都能访问的目录。这样实现者可以专注于实现。

## 每项任务的循环

### 1. 派发实现者

记下 BASE（集成分支当前头部的 SHA）。为这项任务创建工作树和分支，然后派发实现者。提示按 [IMPLEMENTER-PROMPT.md](IMPLEMENTER-PROMPT.md) 填写：

- 一句话说明这项任务在项目中的位置
- 任务的指针（链接或路径），并说明“先读它，这是你的需求”
- 全局约束的指针或原文
- 依据文档的指针：功能清单，以及本任务功能项的设计依据
- 前面任务已提供、本任务要依赖的接口，以及任务本身无法得知的相关决策
- 你对任务中歧义之处作出的决策
- 报告文件路径：`<进度记录目录>/ticket-<NN>-report.md`

**模型选择：** 使用能胜任的最便宜模型，并且每次派发都**显式指定模型**（省略时会继承会话中最贵的模型）：

| 工作                                         | 模型                     |
| -------------------------------------------- | ------------------------ |
| 任务已写清完整行为，只涉及一两个文件         | 快速、低成本的模型       |
| 需要协调多个文件，或需要参照已有模式作判断   | 标准模型                 |
| 需要设计判断或广泛理解代码库；最终整分支评审 | 最强模型                 |
| 修复循环第 3 轮                              | 比卡住的实现者至少高一档 |

轮数比 token 单价更重要：最便宜的模型处理多步工作时，经常多花两三倍轮数，总成本反而更高。评审者，以及根据文字描述工作的实现者，至少使用中档模型。

### 2. 处理报告

实现者只返回简短的状态，细节写在报告文件中：

| 状态                   | 处理方式                                                                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DONE**               | 进入评审                                                                                                                                           |
| **DONE_WITH_CONCERNS** | 阅读顾虑。涉及正确性或范围的，评审前先解决；只是观察（例如“这个文件越来越大”）的，记录后进入评审                                                   |
| **NEEDS_CONTEXT**      | 补充缺少的上下文，重新派发                                                                                                                         |
| **BLOCKED**            | 判断原因：缺上下文就补充后重新派发；推理能力不足就换更强的模型重新派发；任务太大就拆分；任务本身有错就作出代行决策、写入进度记录，带着决策重新派发 |

实现者报告卡住时，重新派发前必须改变某些条件：同一模型、同样输入的重试不会得到不同结果。

### 3. 评审

为 `BASE..<任务分支头部>` 生成评审材料：提交列表、`git diff --stat` 和 `git diff -U10`，写入进度记录目录下一个名称唯一的文件。然后派发评审者，提示按 [REVIEWER-PROMPT.md](REVIEWER-PROMPT.md) 填写：任务指针、全局约束原文、报告文件路径、评审材料路径。

评审者返回两个结论：**任务符合度**（✅、❌ 或 ⚠️）和**质量**（通过或需修复）。两个结论都必须有。实现者的自查不能替代评审。

⚠️ 项指只看 diff 无法核实的要求，由你亲自核实，因为你掌握评审者没有的跨任务上下文。确认是真实缺口的，按符合度失败处理。页面类功能项缺少截图对比证据时，评审者会标为 ⚠️；不能放行，退回实现者补齐证据。环境确实无法运行页面时，把缺失的对比证据写入进度记录，并在收尾时列入需要用户验收的清单，不算作已完成。

写评审提示时只提供材料，不预设结论。如果提示中出现“不必标记”“最多算次要”之类的话，说明你在替自己省掉一轮修复。

### 4. 修复循环

以下任一情况触发修复循环：符合度为 ❌、有任何**严重**或**重要**发现，或你确认为真实缺口的 ⚠️ 项。

先分出两类发现：

- **次要**发现直接写入进度记录（`任务 NN：次要（延后）：<一句话>`），不进入循环。最终评审会看到这份清单。
- 与任务原文要求冲突的发现，由你作出代行决策（以规格为最终依据），写入进度记录，再决定是否修复。

其余发现进入循环。一轮包括一次修复派发和一次限定范围的复审。**每项任务最多 3 轮：**

- **第 1、2 轮**：恢复原来的实现者，原样发送未解决的发现。运行环境不支持向仍在运行的子代理发消息时，派一个新实现者，并提供任务指针、报告文件和发现清单。
- **第 3 轮**：派一个**新的**实现者，模型至少高一档，并告诉它：“之前的实现者尝试了 2 次，现在由你负责。先读报告文件，了解之前试过什么。”两轮恢复仍未解决，通常说明原实现者看不到自己的问题。

每一轮的顺序：

1. 实现者修复问题，重新运行覆盖改动的测试，把修复报告追加到同一个报告文件。
2. 确认修复报告包含覆盖测试、运行的命令和输出之后，再派发复审。
3. 复审只看 `上一次评审看到的头部..当前头部` 的 diff，逐条判定**已解决**或**未解决**，并只在修复 diff 内标记新引入的问题。
4. 复审发现的范围外问题记为延后的次要项，不延长循环。

每轮结束后写入进度记录：`任务 NN：修复第 R/3 轮（已解决 X，未解决 Y：<一句话>；提交 <a7>..<b7>）`

**达到重试上限。** 第 3 轮复审后仍有未解决的发现时，停止派发，由你逐条作出代行决策：

- **评审者判断错误，或存在争议**：搁置，记录为 `任务 NN：搁置：<发现> | 决策：<代码为何保持现状>`
- **问题真实，但下游没有内容依赖它**：同样搁置，决策中写明“真实，延后”
- **问题真实，且下游依赖它**（后续任务依赖它，或它暴露了任务缺陷）：决定能让下游继续推进的最小改动，写入进度记录，并带入下一项相关任务的派发。只有缺陷导致任何推进方式都只能靠猜测时才停下

只在达到重试上限时对评审发现作代行决策。更早作决策，只是换了个名义提前下结论。每个决策都写成一条进度记录。

### 5. 合并

评审通过（或达到重试上限后所有决策都已完成）后，派一个**合并子代理**，把任务分支合并到集成分支：

- 遇到冲突时，调用 Skill 工具，参数为 `resolving-merge-conflicts`。
- 合并后运行类型检查和相关测试，并报告结果。
- 合并后测试失败时，把失败作为这项任务的发现，回到修复循环。

合并成功后，一次性完成记录：

```
任务 NN：完成（提交 <base7>..<head7>，评审通过）
```

达到重试上限后完成的，追加 `（<K> 项搁置）`。然后更新追踪器上的任务状态，删除该任务的工作树。

### 6. 派发新解锁的任务

合并会改变当前可执行任务：立即为新解锁的任务派出实现者。

**等待子代理时**：有本地工作（更新进度记录、准备下一次评审材料、阅读报告）就继续做，子代理的结果会自动返回。确实空闲时，分段等待（平台允许时每段五到十分钟）。每段之间发送一行状态，清点仍在运行的子代理，并追问已经结束却没有报告的子代理。

## 最终评审

所有任务完成后，调用 Skill 工具，参数为 `code-review`，比较基准是集成分支的起点，规格来源是这份规格，使用最强模型。把进度记录中所有“延后”和“搁置”的行提供给评审，让它判断哪些必须在合并前修复。

有发现时，只派**一个**修复子代理，并提供完整的发现清单。不要每条发现派一个修复者：每个修复者都要重建上下文、重新运行测试，总成本会超过所有任务加起来。然后只做**一次**限定范围的复审。剩余发现按达到重试上限的规则作出代行决策。没有第二轮修复。

声明最终完成之前，调用 Skill 工具，参数为 `verifying-completion`：完整测试套件已在本轮运行，规格的每个用户故事都有对应的任务或说明，功能清单中这份规格负责的每个功能项的每个状态都有完成证据。

## 收尾

1. **汇报代行决策。** 删除任何内容之前，把进度记录中每一条决策（预检决策、搁置、达到重试上限后的决策，全部包括）按作出的顺序整理到最终消息的“我作出的决策”一节，每条都带“如果错了”的影响。清单必须完整：进度记录中有的，清单中都要有。这是你代替用户作出的决定传达给用户的唯一途径；随工作区一起删除而没有汇报的决策，等于瞒着用户作出的决定。
2. **汇报范围。** 列出本次交付覆盖的功能项；列出缺少截图对比证据、需要用户验收的页面状态。有任何功能项或状态没有完成时，明确写出，不写成“已完成”。
3. **交付。** 已创建草稿 PR 的，把 PR 标为可评审。只在本地分支完成的，调用 Skill 工具，参数为 `finishing-a-branch`。
4. **清理。** 删除所有实现者工作树。PR 合并前保留进度记录；用户确认不再需要后，删除本规格的进度记录目录，git 历史就是记录。

## 常见借口与对应事实

| 借口                               | 事实                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| “我自己修一下更快”                 | 协调者亲自修改会占用上下文并跳过评审。恢复实现者。                                 |
| “这个状态不重要，先不做”           | 删减状态就是缩减范围，停下来问用户。                                               |
| “差不多符合任务要求了”             | 评审发现了缺口就是没完成。修复，或达到上限后作出代行决策。                         |
| “再来一轮就能收敛”                 | 超过上限的循环不会收敛，问题出在结构上。作出代行决策并分类处理。                   |
| “修复很小，跳过复审”               | 未经评审的修复正是回归混入的途径。每轮都以复审结束。                               |
| “这条发现明显不对，删掉就好”       | 只在达到重试上限时对发现作代行决策，每个决策都写入进度记录。                       |
| “写进度记录太麻烦”                 | 进度记录是上下文压缩后唯一可靠的状态。没有它，协调者会把已完成的任务整批重新派发。 |
| “实现者自己派了个评审，多一层保险” | 那是对同一份 diff 的重复评审，花费全额成本却不计入流程。任务评审才是有效的检查点。 |
