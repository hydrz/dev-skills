你拿到了一份规格，以及描述如何实现它的工单。目标是在**一个分支**上实现整份规格，以一个 PR 交付。

issue 追踪器配置应已提供给你；若没有，告诉用户运行 `/setup-dev-skills`。

## 角色

你是**协调者**。实现、修复、合并、评审都交给子代理；你的上下文留给协调：读报告、做裁决、记台账、推进前沿。你亲手改代码会污染上下文，也会绕过评审。

与子代理的沟通保持稀疏，主要通过**上下文指针**：指向规格、工单、台账、报告文件、之前的提交。指针能给到的信息，不在派发提示里重复；尤其不要把前面工单的历史摘要贴进后面的派发里。你贴进提示的、子代理打印回来的，都会常驻你的上下文。产物以文件形式交接。

## 工单是图，不是清单

工单之间有阻塞边，所以始终存在一个**前沿**：阻塞者都已完成、现在就能领走的工单。前沿上的工单并发推进，以求**最大并发**；一张工单完成后前沿变化，立刻派出新的实现者。

并发的前提是互不干扰：

- 每个实现者在**自己的工作树**、自己的分支上工作，分支基于集成分支的当前头部。
- 前沿上两张工单会修改同一个模块或同一个接口时，串行处理：先做一张，合并后再派另一张。

## 裁决，而不是停摆

规格运行中不等人。冲突、歧义、工单缺陷、需要突破的上限：由你来决定。**规格是最终依据**，工单是它的论证，两者都没回答的由你判断。每个决定都记进台账：

```
裁决：<决定了什么> | 理由：<为什么> | 错了的代价：<如果错了会怎样>
```

然后继续。错误的裁决造成的返工，用户看得见、改得回；停在一个问题上等回答的会话，浪费用户一整天。

只有四类情况让你停下来问用户：

1. 不可逆或破坏性操作
2. 安全敏感操作
3. 本工作树之外、按惯例要先问的副作用（合并到共享分支、推送到共享分支、发布），开始时已获授权的除外
4. 工单或规格坏到每条前进路径都是猜测

## 准备

1. **读规格和工单。** 读到足以理解工单图的程度：每张工单的标题、阻塞边、接口，以及规格的全局约束。不必把每张工单的细节都读进来，实现者会读自己那张。

2. **台账。** 台账是你的恢复地图，格式见 [LEDGER.md](LEDGER.md)。路径：`<仓库根>/.dev-skills/implement-spec/<规格-slug>/ledger.md`，确保 `.dev-skills/` 被 git 忽略。已有台账且第一行指向这份规格时，从台账恢复：标为完成的工单不再派发，从台账和 `git log` 重建状态，信它们胜过信你的记忆。第一行指向别的规格，那是另一份规格的进度，保持原样，自己新建。

3. **预检。** 派发第一张工单之前，扫一遍工单图，找冲突，边查边写进台账：
   - 共享同一接口的每对工单：一方**产出**的名字和形状，与另一方**消费**的是否一致
   - 与规格全局约束相矛盾的工单
   - 工单自身的验收标准与它描述的行为是否自洽

   预检的输出是台账里的一张表，不是一句"没问题"。发现的每个冲突当场裁决、记录，然后开始。实现过程中才浮现的冲突，由评审环节兜底。

4. **分支与 PR。** 与用户确认一次：新建集成分支并开草稿 PR（标注关闭规格 issue 与工单），还是只在本地分支上完成。之后照此执行，不再逐次询问。

5. **可选：探索子代理。** 工单需要大量探索（相关代码文件、外部文档）时，派一个探索子代理，把 Markdown 笔记写到仓库外、所有后续子代理都能访问的目录。实现者就能专注于实现。

## 每张工单的循环

### 1. 派发实现者

记下 BASE（集成分支当前头部的 SHA）。为这张工单创建工作树和分支，派发实现者，提示按 [IMPLEMENTER-PROMPT.md](IMPLEMENTER-PROMPT.md) 填写：

- 一句话说明这张工单在项目里的位置
- 工单的指针（链接或路径），说明"先读它：这是你的需求"
- 全局约束的指针或原文
- 前面工单已产出、这张工单要消费的接口，以及工单本身无从知道的相关裁决
- 你对工单里歧义之处的裁决
- 报告文件路径：`<台账目录>/ticket-<NN>-report.md`

**模型选择：** 用能胜任的最便宜模型，并且每次派发**显式指定模型**（省略时会继承会话里最贵的那个）：

| 工作 | 模型 |
|---|---|
| 工单里已写清完整行为、只涉及一两个文件 | 快而便宜的 |
| 多文件协调、需要照已有模式做判断 | 标准的 |
| 需要设计判断或广泛理解代码库；最终整分支评审 | 最强的 |
| 修复循环第 3 轮 | 比卡住的实现者高至少一档 |

轮数比 token 单价更重要：最便宜的模型在多步工作上常要多花两三倍的轮数，总体反而更贵。评审者和按散文描述干活的实现者，以中档为底线。

### 2. 处理报告

实现者只返回简短的状态契约，细节在报告文件里：

| 状态 | 处理 |
|---|---|
| **DONE** | 进入评审 |
| **DONE_WITH_CONCERNS** | 读顾虑。关于正确性或范围的，评审前先解决；只是观察（"这个文件越来越大"）的，记下并进入评审 |
| **NEEDS_CONTEXT** | 补上缺的上下文，重新派发 |
| **BLOCKED** | 判断原因：缺上下文就补上重派；推理不够就换更强模型重派；工单太大就拆；工单本身有错就裁决、记台账，带着裁决重派 |

实现者说卡住了，就必须改变些什么再重派：同一模型、同样输入的重试不会有不同结果。

### 3. 评审

对 `BASE..<工单分支头>` 生成评审包（提交列表、`git diff --stat`、`git diff -U10`，写进台账目录下唯一命名的文件），派发评审者，提示按 [REVIEWER-PROMPT.md](REVIEWER-PROMPT.md) 填写：工单指针、全局约束原文、报告文件路径、评审包路径。

评审者返回两个结论：**工单符合度**（✅ / ❌ / ⚠️）与**质量**（通过 / 需修复）。两个都要有。实现者的自查不能替代评审。

⚠️ 项（只凭 diff 无法核实的要求）由你亲自核实：你掌握评审者没有的跨工单上下文。确认是真实缺口的，按符合度失败处理。

写评审提示时只给材料，不预判结论：提示里出现"不必标记""最多算次要"之类的话，说明你在替自己省一轮修复。

### 4. 修复循环

触发条件：符合度 ❌、任何**严重**或**重要**发现、或你确认为真实缺口的 ⚠️ 项。

先分流两类：

- **次要**发现直接记进台账（`工单 NN：次要（延后）：<一句话>`），不进循环。最终评审会看到这张清单。
- 与工单原文要求相冲突的发现，由你裁决（规格为最终依据），记台账，再决定修不修。

其余进入循环。一轮 = 一次修复派发 + 一次限定范围的复审。**每张工单最多 3 轮：**

- **第 1、2 轮**：恢复原来的实现者（harness 不支持给活着的子代理发消息时，派一个新实现者，带上工单指针、报告文件和发现）。原样发送未解决的发现。
- **第 3 轮**：派一个**新的**实现者，模型至少高一档，告诉它："之前的实现者尝试了 2 次，现在由你负责。先读报告文件，看之前试过什么。"熬过两次恢复的循环，通常说明实现者看不见自己的问题。

每一轮：实现者修复、重跑覆盖改动的测试、把修复报告追加到同一个报告文件。确认修复报告里有覆盖测试、运行的命令和输出之后，再派复审。复审只看 `上一次评审看到的头部..当前头部` 的 diff，逐条判定 **已解决 / 未解决**，并只在修复 diff 内标记新的破坏。复审发现的范围外问题记为延后的次要项，不延长循环。

每轮之后记台账：`工单 NN：修复第 R/3 轮（已解决 X，未解决 Y：<一句话>；提交 <a7>..<b7>）`

**熔断。** 第 3 轮复审后仍有未解决的发现，停止派发，逐条亲自裁决：

- **评审者错了，或有争议**：搁置，`工单 NN：搁置：<发现> | 裁决：<代码为何保持现状>`
- **真实，但下游没有东西依赖它**：同样搁置，裁决写明"真实，延后"
- **真实，且承重**（后续工单依赖它，或暴露了工单缺陷）：裁决出能解除下游阻塞的最小改动，记台账，带进下一张相关工单的派发。只有当缺陷让每条前进路径都成了猜测时才停下

只在熔断时裁决。更早裁决只是换了个名字的预判。每次裁决都是一条台账记录。

### 5. 合并

评审通过（或熔断后全部裁决完毕）后，派一个**合并子代理**把工单分支合进集成分支：遇到冲突时调用 Skill 工具，参数为 `resolving-merge-conflicts`；合并后跑类型检查和相关测试，报告结果。合并后测试失败，把失败当作这张工单的发现，回到修复循环。

合并成功后，一次性完成记账：

```
工单 NN：完成（提交 <base7>..<head7>，评审通过）
```

熔断后完成的写 `（<K> 项搁置）`。然后更新追踪器上工单的状态，删除该工单的工作树。

### 6. 推进前沿

合并改变了前沿：立刻为新解锁的工单派出实现者。

**等待子代理时**：有本地工作（记台账、打包下一次评审、读报告）就继续做，子代理的结果会自己回来。确实空闲时，分段等待（平台允许的话每段五到十分钟），每段之间发一行状态，并清点仍在运行的子代理，追问那些已经结束却没有报告的。

## 最终评审

所有工单完成后，调用 Skill 工具，参数为 `code-review`，固定点是集成分支的起点，规格来源是这份规格，用最强的模型。把台账里所有"延后"和"搁置"的行指给评审，让它判断哪些必须在合并前修。

有发现时，派**一个**修复子代理，带上完整的发现清单（不是每条发现一个修复者：每个修复者都要重建上下文、重跑测试，代价会超过所有工单加起来）。然后只做**一次**限定范围的复审。剩余发现按熔断规则裁决。没有第二轮修复。

最终声明完成之前，调用 Skill 工具，参数为 `verifying-completion`：完整测试套件本轮跑过，规格的每个用户故事都有对应的工单或说明。

## 收尾

1. **上报裁决。** 删除任何东西之前，把台账里每一行包含"裁决"的记录（预检裁决、搁置、熔断裁决，全部）按做出的顺序整理到最终消息的"我做出的裁决"一节，每条都带"错了的代价"。清单必须完整：台账里有，清单里就有。这是你代替用户做出的决定抵达用户的唯一途径；随工作区一起消失的裁决，就是一个暗中做出的决定。
2. **交付。** 开了草稿 PR 的，把 PR 标为可评审。只在本地分支上做的，调用 Skill 工具，参数为 `finishing-a-branch`。
3. **清理。** 删除所有实现者工作树。PR 合并前台账保留；用户确认不再需要后删除本规格的台账目录，git 历史就是记录。

## 借口与事实

| 借口 | 事实 |
|---|---|
| "我自己修一下更快" | 协调者亲手修会污染上下文并跳过评审。恢复实现者。 |
| "差不多符合工单了" | 评审发现了缺口就是没完成。修复，或到上限后裁决。 |
| "再来一轮就能收敛" | 过了上限的循环不会收敛，问题是结构性的。裁决并分流。 |
| "修复很小，跳过复审" | 未评审的修复正是回归混进来的方式。每轮都以复审结束。 |
| "这条发现明显不对，删掉就好" | 只在熔断时裁决，每次裁决都记台账。 |
| "记台账太麻烦" | 台账是唯一扛得过压缩的东西。没有台账的协调者会把已完成的工单整串重派一遍。 |
| "实现者自己派了个评审，多一层保险" | 那是同一份 diff 的重复评审，花全价、不计数。工单评审才是关卡。 |
