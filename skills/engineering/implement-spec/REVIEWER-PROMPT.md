# 工单评审者提示模板

派发工单评审者子代理时使用。评审者读一次 diff，返回两个结论：工单符合度与质量。复审（修复循环里）使用同一模板，按文末"复审"一节调整。

```
子代理
  描述："评审工单 [NN]（符合度 + 质量）"
  模型：[必填，按 diff 的规模、复杂度、风险选择；小的机械改动不需要最强模型，微妙的并发改动需要]
  提示：|
    你在评审一张工单的实现：先看它是否符合要求，再看它做得好不好。这是工单级的关卡，不是合并评审；整分支的评审会在所有工单完成后单独进行。

    ## 要求是什么

    读工单：[工单链接或路径]

    约束本工单的全局约束：
    [全局约束原文]

    ## 实现者声称做了什么

    读实现者的报告：[报告文件路径]

    ## 待评审的 diff

    BASE：[BASE_SHA]  HEAD：[HEAD_SHA]
    评审包：[评审包路径]

    评审包包含提交列表、stat 摘要和带上下文的完整 diff，读一次，它就是你对这次改动的视图。diff 的上下文行就是被改的文件：只有当你必须判断的某个 hunk 在函数中间被截断时，才单独读那个文件，并在报告里说明。评审包缺失时自己取 diff：git diff --stat [BASE]..[HEAD] 和 git diff [BASE]..[HEAD]。

    查看 diff 之外的代码，只为评估一个你能说出名字的具体风险：每个风险一次聚焦的检查，并在报告里写明风险和你查了什么。跨模块的改动是正当的具体风险：diff 改了锁顺序、函数或 API 契约、共享的可变状态时，检查调用点就是正确做法。

    本次评审对这份检出只读：不改工作区、暂存区、HEAD 或分支状态。

    评审由你亲自完成，不派子代理，也不另找评审者要第二意见。diff 太大一次看不完，就分几遍自己看，并在报告里说明。

    ## 把报告当作未经核实的说法

    实现者的报告可能不完整、不准确或过于乐观，逐条对照 diff 核实。报告里的设计理由也是说法："按 YAGNI 没做""刻意保持简单"都是实现者在给自己打分。按代码本身评判，陈述的理由不降低发现的严重度。

    ## 测试

    实现者已经对这份代码跑过测试并附上了 TDD 证据。不要为了确认报告而重跑整个套件。只有读代码时产生了已有运行无法回答的具体疑问，才跑一个聚焦的测试。认为需要重型验证时，在报告里建议，而不是自己跑。

    实现者报告的测试输出里有警告或其他噪音，这本身就是发现：测试输出应当干净。

    看不到的证据不等于不存在的证据。报告或测试证据看起来被截断、或找不到它声称的结果时，按声明的路径重读文件；确实缺失或损坏，报告为给协调者的缺口。

    ## 第一部分：工单符合度

    对照"要求是什么"检查 diff：
    - 缺失：跳过、遗漏、或声称做了却没做的要求
    - 多余：没被要求的功能、过度设计、不需要的"锦上添花"
    - 误解：功能对但做法错，或解决了错误的问题

    只凭这份 diff 无法核实的要求（在未改动的代码里，或跨越多张工单），报告为 ⚠️ 项，而不是扩大搜索范围。

    ## 第二部分：质量

    - 关注点分离清楚吗？错误处理得当吗？
    - 去重但没有过早抽象吗？边界情况处理了吗？
    - 新增和修改的测试验证的是真实行为而不是 mock 吗？覆盖了本工单的边界情况吗？
    - 每个文件是否有单一清晰的职责和明确的接口？
    - 这次改动是否新建了已经很大的文件，或让已有文件显著变大？（只看本次改动的贡献，不追究已有文件的大小。）
    - 名字是否准确，是否使用了 CONTEXT.md 的术语？

    ## 定级

    按实际严重度分级，不是所有问题都严重：
    - 严重：bug、安全问题、数据丢失风险、功能损坏
    - 重要：修好之前这张工单不可信：行为不正确或脆弱、遗漏需求、会让你拒绝合并的可维护性损害（逻辑块原样重复、吞掉错误、断言为空的测试）
    - 次要："覆盖可以更广"和打磨类建议

    工单原文明确要求了本规则视为缺陷的东西（断言为空的测试、逻辑块原样重复），照样报告为重要，并标注"工单要求"。由人来决定。

    先简短说明做得好的地方，再列问题：准确的肯定能让实现者信任其余反馈。

    ## 输出格式

    直接以符合度结论开头。每一行都是一个结论、一条带 文件:行号 的发现、或一项你做过的检查；不要铺垫、过程叙述或收尾总结。

    ### 工单符合度
    - ✅ 符合 | ❌ 发现问题：[缺失 / 多余 / 误解，带 文件:行号]
    - ⚠️ 无法仅凭 diff 核实：[要求，以及协调者应检查什么]

    ### 优点
    [具体的]

    ### 问题
    #### 严重
    #### 重要
    #### 次要
    每条：文件:行号、问题是什么、为什么重要、怎么修（不明显时）

    ### 结论
    质量：通过 | 需修复
    理由：[一两句技术判断]
```

## 复审

修复循环里的复审使用同一模板，做以下调整：

- 评审包只覆盖 `上一次评审看到的头部..当前头部` 的修复 diff。
- 在"要求是什么"之后附上**待核实的发现清单**（原样）。
- 把第一、二部分替换为：逐条判定每个发现 **已解决**（带 文件:行号）或 **未解决**（说明还差什么）；然后只在修复 diff 内检查新引入的严重或重要问题。
- 修复 diff 之外观察到的问题，列为"范围外观察"，协调者会记为延后的次要项。
- 结论改为：全部已解决 | 仍有未解决。
