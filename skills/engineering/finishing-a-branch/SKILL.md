# 收尾一个分支

**顺序：** 验证测试 → 识别环境 → 确认基线分支 → 给出选项 → 执行选择 → 清理。

集成是用户的决定。你负责把选项摆清楚，然后等待。

## 1. 验证测试

对即将集成的这棵树运行项目的完整测试套件，读输出（遵循 `verifying-completion`）。

**测试失败**：报告失败并停下，选项在测试变绿之后才给：

```
测试失败（<N> 个）。收尾之前必须修好：

<失败输出>
```

**测试通过**：继续。

## 2. 识别环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 趁还在工作区里时记下；第 5 步会切换目录，第 6 步清理还要用
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

| 状态 | 菜单 | 清理 |
|---|---|---|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准 3 选项 | 没有工作树要清 |
| `GIT_DIR != GIT_COMMON`，在具名分支上 | 标准 3 选项 | 按来源判断（见第 6 步） |
| `GIT_DIR != GIT_COMMON`，detached HEAD | 精简 2 选项（不合并） | 外部管理，保留原样 |

## 3. 确认基线分支

基线分支就是这份工作分出来的那个分支，通常在规格、工单、对话或分支的 upstream 里写着。不确定就问："这个分支是从 <你的最佳猜测> 分出来的，对吗？"合并之前先确认：合错基线的代价很高。

## 4. 给出选项

**普通仓库或具名分支的工作树，照原样给出这 3 个选项：**

```
实现已完成。你想怎么处理？

1. 在本地合并回 <基线分支>
2. 推送并创建 Pull Request
3. 保持分支原样（我稍后处理）

选哪个？
```

**detached HEAD，照原样给出这 2 个选项：**

```
实现已完成。当前是 detached HEAD（外部管理的工作区）。

1. 推送为新分支并创建 Pull Request
2. 保持原样（我稍后处理）

选哪个？
```

菜单就是上面这些。丢弃工作只在用户明确要求时才进入流程（见下文）。

## 5. 执行选择

### 选项 1：本地合并

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

git checkout <基线分支>
git pull
git merge <功能分支>

<测试命令>
```

合并后测试失败：停下，工作树和分支原样保留，开始调查。还没推送，合并是本地的、可恢复的。

合并结果变绿后：清理工作树（第 6 步），然后删除分支：

```bash
git branch -d <功能分支>
```

### 选项 2：推送并创建 PR

```bash
git push -u origin <功能分支>
# detached HEAD 时，在远端命名新分支：
# git push origin HEAD:refs/heads/<新分支>
```

然后用托管平台的工具（有 CLI 用 CLI，否则用推送时打印的创建链接）针对 <基线分支> 创建 PR / MR，遵循仓库的 PR 模板和约定，把链接报告给用户。

工作树保留：用户要在那里根据 PR 反馈继续改。

### 选项 3：保持原样

报告："保留分支 <名字>。工作树位于 <路径>。"

### 用户要求丢弃工作时

这条路径只响应明确的丢弃请求。先确认：

```
这将永久删除：
- 分支 <名字>
- 全部提交：<提交列表>
- 工作树 <路径>

输入 discard 确认。
```

等到这个确切的词。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

清理工作树（第 6 步），再强制删除分支：

```bash
git branch -D <功能分支>
```

## 6. 清理工作区

**只在选项 1 和确认过的丢弃时运行。** 选项 2 和 3 总是保留工作树。调用方此时已切换到主仓库根目录（移除工作树必须在工作树之外执行），并使用第 2 步切换目录之前记下的值。

**`GIT_DIR == GIT_COMMON`：** 普通仓库，无工作树可清。完成。

**`WORKTREE_PATH` 位于 `.worktrees/` 或 `worktrees/` 下：** 这是本流程创建的工作树，由我们负责清理：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune
```

**移除被拒绝**（`contains modified or untracked files`）：说明工作树里有别处都没有的文件（未提交的计划、笔记、草稿）。给用户看有什么，然后问：

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
工作树移除被拒绝，以下文件从未提交：

<文件列表>

1. 先提交到 <分支> 再清理
2. 移到 <主仓库根目录>
3. 删除（不可恢复）

选哪个？
```

执行用户的选择，然后再移除工作树。`--force` 只在用户选了 3 之后使用。

**其他情况：** 工作区归宿主环境管理，保留原样。平台提供退出工作区的工具时，使用它。

## 速查

| 选项 | 合并 | 推送 | 保留工作树 | 删分支 |
|---|---|---|---|---|
| 1. 本地合并 | 是 | 否 | 否 | 是 |
| 2. 创建 PR | 否 | 是 | 是 | 否 |
| 3. 保持原样 | 否 | 否 | 是 | 否 |
| 丢弃（仅明确要求） | 否 | 否 | 否 | 是（强制） |

## 借口与事实

| 借口 | 事实 |
|---|---|
| "这个会话早些时候测试过了" | 对即将集成的这棵树重跑。一次通过只证明它跑的那棵树。 |
| "用户显然想合并" | 集成是用户的决定。给出菜单，等待。 |
| "'嗯，删了吧'算确认" | 只有输入 `discard` 才授权删除。 |
| "PR 开了，工作树没用了" | PR 反馈要在那个工作树里修，工作落地前一直保留。 |
| "另一个工作树看着废弃了，顺手清掉" | 只清理 `.worktrees/` 或 `worktrees/` 下的工作树，其他的归宿主管。 |
| "合并后失败大概是偶发的" | 合并结果失败就停下，分支和工作树原样保留，先调查。 |
| "推送被拒，强推一下就好" | 推送被拒说明远端变了。先调查；只在用户明确要求时强推。 |
