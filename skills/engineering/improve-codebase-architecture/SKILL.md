# 改进代码库架构

找出架构上的摩擦，提出**加深机会**：把浅模块变成深模块的重构。目标是可测性和 AI 可导航性。

本命令以项目的领域模型为依据，建立在一套共享的设计词汇之上：

- 调用 Skill 工具，参数为 `codebase-design`，获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口就是测试面"、"一个适配器是假想的接缝，两个才是真的"）。每条建议都严格使用这些词，不滑向"组件""服务""API""边界"。
- `CONTEXT.md` 里的领域语言为好的接缝命名；`docs/adr/` 里的 ADR 记录了本命令不应重新争论的决定。

## 过程

### 1. 探索

**先定范围再扫描：YAGNI。** 加深一个模块的回报是让以后改它更容易，所以给代码库里最近在变的部分更高权重。看之前先决定*往哪看*：

- 用户点名了方向（某个模块、子系统、痛点），就按它来，跳过下面的推断。
- 否则，往回翻一大段提交历史（`git log --oneline`），找出代码库的热点：反复出现的文件和区域，让这些路径优先吸引你的注意。改动分散、没有明显热点时，扩大范围。

先读项目的术语表（`CONTEXT.md`）和所涉区域的 ADR。

然后派一个子代理遍历代码库。不按僵硬的启发式走，有机地探索，记下哪里让你感到摩擦：

- 理解一个概念，是否需要在很多小模块之间来回跳？
- 哪些模块是**浅**的，接口几乎和实现一样复杂？
- 哪里为了可测性抽出了纯函数，但真正的 bug 藏在它们如何被调用里（没有**局部性**）？
- 哪些紧耦合的模块跨接缝泄漏？
- 代码库的哪些部分没有测试，或者通过当前接口很难测？
- 最近的 bug 修复里，有没有因为找不到正确接缝而没能写回归测试的？

对任何怀疑是浅的东西做**删除测试**：删掉它，复杂性是集中起来了，还是只是挪了地方？"集中起来了"就是你要找的信号。

### 2. 以 HTML 报告呈现候选

把一个自包含的 HTML 文件写到操作系统临时目录，不在仓库里留任何东西。临时目录取 `$TMPDIR`，回退到 `/tmp`（Windows 用 `%TEMP%`），写到 `<临时目录>/architecture-review-<时间戳>.html`，每次运行得到一个新文件。替用户打开它（Linux 用 `xdg-open <路径>`，macOS 用 `open <路径>`，Windows 用 `start <路径>`），并告诉他们绝对路径。

报告用 **CDN 引入的 Tailwind** 做布局和样式，在图结构、流程、时序能可靠表达结构的地方用 **CDN 引入的 Mermaid** 画图。Mermaid 与手工 CSS / SVG 图示混用：关系是图状的（调用图、依赖、时序）用 Mermaid，想要更有编辑感的（质量图、剖面图、塌缩图）用手工 div / SVG。每个候选都有一张**前 / 后对比图**。要可视化。

每个候选渲染成一张卡片：

- **文件**：涉及哪些文件 / 模块
- **问题**：当前架构为什么造成摩擦
- **方案**：用平实的话描述会改变什么
- **收益**：用局部性和杠杆来解释，以及测试会如何改善
- **前 / 后对比图**：并排、定制绘制，展示浅在哪里、如何加深
- **推荐强度**：`强烈推荐`、`值得探索`、`推测性` 之一，渲染成徽章

报告以**首要推荐**一节收尾：你会先处理哪个候选、为什么。

**领域用 CONTEXT.md 的词汇，架构用 `codebase-design` 的词汇。** `CONTEXT.md` 定义了"订单"，就说"订单录入模块"，而不是"FooBarHandler"，也不是"订单服务"。

**ADR 冲突**：某个候选与已有 ADR 相矛盾时，只在摩擦真实到值得重新审视那条 ADR 时才提出。在卡片里清楚标出（比如一个警告框：_"与 ADR-0007 矛盾，但值得重新讨论，因为……"_）。ADR 禁止的理论性重构不必逐一列出。

完整的 HTML 骨架、图示模式和样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

这一步只呈现候选，接口设计留到第 3 步。文件写好后，问用户："你想深入探讨哪一个？"

### 3. 拷问循环

用户挑中一个候选后，调用 Skill 工具，参数为 `grilling`，和用户一起走设计树：约束、依赖、加深后模块的形状、接缝后面藏什么、哪些测试能留下来。

决定成形时就地产生副作用；调用 Skill 工具，参数为 `domain-modeling`，随时保持领域模型最新：

- **给加深后的模块起了一个 `CONTEXT.md` 里没有的概念名？** 把术语加进 `CONTEXT.md`。文件不存在就按需创建。
- **对话中磨尖了一个模糊的术语？** 当场更新 `CONTEXT.md`。
- **用户以一个承重的理由否决了候选？** 提议写 ADR，这样说：_"要不要把这个记成 ADR，免得以后的架构评审再提同样的建议？"_ 只在未来的探索者确实需要这个理由来避免重复建议时才提；暂时性的理由（"现在不值得"）和不言自明的理由跳过。
- **想为加深后的模块探索备选接口？** 调用 Skill 工具，参数为 `codebase-design`，使用它的"设计两次"并行子代理模式。

拷问达成共识后，告诉用户：要实现它，从 `/to-spec` 汇入主流程。
