# 测试驱动开发

TDD 就是 红 → 绿 的循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好测试、测试放在哪、反模式、循环的规则。每一节在每一轮都适用：循环之前和之中都要查，而不是事后。

探索代码库时，读 `CONTEXT.md`（如果有），让测试名和接口词汇与项目的领域语言一致，并尊重相关区域的 ADR。

## 好测试是什么

测试通过公开接口验证行为，不验证实现细节。代码可以整个换掉，测试不必跟着变。好测试读起来像规格："用户可以用有效购物车结账"准确说明了存在什么能力，而且它扛得住重构，因为它不关心内部结构。

每个测试都**说得出它抓的是哪种破坏**：写测试体之前，先回答"生产代码怎样改会让这个测试失败？"答不上来，就围绕一个可观察的行为重新设计这个测试。

示例见 [tests.md](tests.md)，mock 准则见 [mocking.md](mocking.md)。

## 接缝：测试放在哪

**接缝**（seam）是你测试所在的公开边界：不必伸进内部就能观察行为的接口。测试住在接缝上。

**只在事先约定的接缝上测试。** 写任何测试之前，写下要测的接缝并和用户确认。你测不了所有东西，事先约定接缝，测试的力气才会落在关键路径和复杂逻辑上，而不是每一个边缘情况。

问："公开接口是什么？应该在哪些接缝上测试？"

接口本身的形状还有疑问时（模块多深、接缝该放哪、接口该暴露什么），调用 Skill 工具，参数为 `codebase-design`，获取词汇。它是模块、接口、深度、接缝、适配器、杠杆、局部性这些术语的共享来源，是用来查的参考，不是要跑的流程。

## 循环的规则

每一轮是一个**垂直切片**：一个接缝、一个测试、一段最少的实现。

1. **变红**：写一个测试，只描述一个行为。
2. **确认红得有道理**：运行它，读输出。它必须**失败**（不是报错），失败信息是你预期的那条，失败原因是功能缺失（不是拼写错误、导入错误）。
   - 测试直接通过：你测的是已有行为，改测试。
   - 测试报错：修掉报错，重跑，直到它以正确的方式失败。
3. **变绿**：只写恰好让它通过的代码。只为这个测试写，未来的测试留给未来的轮次。
4. **确认绿**：运行它和相关测试，读输出。全部通过，输出干净（没有多余的警告和报错）。

实现代码写在测试之前了，就把那段代码放一边，从测试重新开始：先写的代码会让你按实现去写测试，而那样的测试从来没有证明过它能失败。

**重构不在循环里。** 它属于评审阶段（见 `code-review`），不在 红 → 绿 的实现循环中。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法、通过旁路验证（直接查数据库而不走接口）。征兆：行为没变，一重构测试就挂。
- **同义反复**：断言用代码的算法重新算一遍期望值（`expect(add(a, b)).toBe(a + b)`、用同样方法手工推出的快照、常量等于自己），测试天生通过，永远不会与代码意见相左。期望值必须来自独立的真相源：已知正确的字面量、手算的例子、规格。
- **变更探测器**：只有有意的决定（一个常量的值、确切的文案、私有结构）才能让它失败。它在重新设计时报警，在出 bug 时沉睡。测依赖这个决定的行为：不测 `expect(MAX_RETRIES).toBe(5)`，测"失败的调用会重试 5 次，第 6 次不会发生"。
- **水平切片**：先写完所有测试，再写所有实现。批量写出的测试验证的是*想象中*的行为：你测的是东西的*形状*而不是面向用户的行为，测试对真实变化变得迟钝，而且在理解实现之前就锁定了测试结构。改用**垂直切片**：一个测试 → 一段实现 → 重复，每个测试都是一发**曳光弹**（tracer bullet），根据上一轮学到的东西调整方向。

## 收尾：变异检查

完成前在脑中对生产代码做变异，每种现实的变异都应至少让一个测试失败：

- 常量或参数写错
- 分支处理器写错
- 缺少状态变更或副作用
- 返回空值或默认值
- 缺少对零、空、nil、未授权、格式错误输入的校验

没有测试能抓住的变异，说明那个行为没有保护，或者测试是同义反复。
