本 skill 根据当前对话、功能清单和你对代码库的理解产出规格。不再访谈用户，只综合已经掌握的信息。信息不够时，把缺口列出来交还用户，而不是自己补上或悄悄简化。

issue 追踪器和分诊标签词汇应该已经提供给你；如果没有，告诉用户运行 `/setup-dev-skills`。功能清单的格式、位置和修改规则见 `docs/agents/feature-list.md`；没有这个文件时，同样告诉用户运行 `/setup-dev-skills`。

## 过程

### 1. 了解现状

如果还没有探索过仓库，先探索，了解代码库的当前状态。规格全文使用项目术语表中的词汇，并遵守涉及区域的 ADR。

读取这项工作的功能清单（地图备注或对话中给出的链接，或 `docs/features/` 下对应的文件），记下当前批次。本 skill 只处理当前批次的功能项和状态。

### 2. 判断规模

按下面的顺序判断，命中一条就按那一条处理：

1. **大型工作，没有功能清单。** 讨论涉及多个业务模块，或一眼能看出功能项会超过约 25 个，但找不到功能清单：停下，说明原因，告诉用户运行 `/wayfinder` 补建功能清单。不根据已有文档自行生成清单，补建清单会暴露设计缺口，需要人来决定。
2. **有功能清单，当前批次还没有规格拆分表，且需要拆分。** 当前批次的功能项涉及多个业务模块，或超过约 25 个：本次只产出**规格拆分表**（见第 3 步），然后停止。
3. **当前批次已有规格拆分表。** 用户通过参数指定了要整理的规格（模块名或拆分表中的规格标题）时，只整理这一份，从第 4 步继续。没有指定时，列出当前批次中尚未发布、前置规格已发布的规格，请用户选择一份。
4. **小功能。** 一份规格就能描述全部内容：从第 4 步继续，在规格的“功能项”一节直接列出功能项。

### 3. 产出规格拆分表

按业务模块（限界上下文）划分当前批次的规格：一份规格对应“模块 × 批次”，例如“商业化（MVP）”。把当前批次的每个功能项和状态分配给恰好一份规格，写明规格之间的前置关系。写入功能清单的“规格拆分表”一节，并回填每个功能项的“规格”列。

更晚批次的内容不在这次拆分。切换到下一个批次后，再为同一模块写新的规格。

检查：

- 当前批次的每个功能项和状态都分配到了规格，没有遗漏，也没有重复。
- 一份规格负责的功能项超过约 25 个时，考虑继续拆分。
- 前置关系没有环。

把拆分表展示给用户确认，然后告诉用户按依赖顺序对每份规格运行 `/to-spec <模块>`，每份规格之后接着运行 `/to-tickets`。

### 4. 确定测试方案

测试方案在规格中确定一次。之后 `/to-tickets`、`/implement` 和 `tdd` 直接沿用，不再逐项任务询问。

列出以下内容，与用户确认：

- **测试层次**：每个模块用哪几层测试，例如单元、契约、集成、端到端。模块之间或前后端之间通过契约交互时，用契约测试验证双方都遵守契约。
- **接缝**：每一层在哪个接缝上测试。
  - 优先使用已有接缝，而不是新建。
  - 选择尽可能高层的接缝。需要新接缝时，也放在尽可能高的位置。
  - 同一层的接缝越少越好。
- **页面状态的自动检查**：页面类功能项的每个状态，都要有一条可以重复运行的自动化检查，能进入该状态并断言关键内容。写明用什么工具；项目已有截图对比能力时，写明截图基线的视口和设备。
- **非功能需求的验证方式**：每条非功能需求用什么命令或工具验证。

项目还没有合适的测试工具时，把工具选择列为未决问题交给用户，不自行选定。

### 6. 自查

换个角度重读写好的规格，发现问题就地修改：

- **占位符**：是否有“待定”、TODO、没写完的小节或含糊的要求？
- **内部一致**：各节之间是否矛盾？实现决策与用户故事是否对得上？
- **歧义**：是否有要求能读出两种意思？有就选定一种并写明。
- **范围**：它是否聚焦在一个业务模块的一个批次？包含几个独立模块时必须拆分：有功能清单时回到第 3 步，没有功能清单时按第 2 步第 1 条处理。
- **功能项覆盖**：这份规格负责的每个功能项都出现在“功能项”一节，并且当前批次的每个状态都能在用户故事或实现决策中找到对应的行为。
- **非功能需求**：每条都有指标、目标值和验证方式；没有目标值的，列为未决问题。
- **测试方案**：测试层次、接缝和页面状态的检查工具都已写明。
- **设计依据**：每个功能项都有需覆盖状态；每个页面类功能项的设计依据满足清单规则，并在“依据文档”一节中链接。

功能项缺需覆盖状态、缺设计依据，或结论仍是“待定”时，不能靠自己补全。把它们列成**未决问题**交给用户，本次不发布。用户补齐后重新运行 `/to-spec`；用户决定把某项移出范围时，按清单规则记录确认。

### 7. 发布

发布到项目的 issue 追踪器，加上 `ready-for-agent` 分诊标签，无需再做分诊。在规格拆分表中把这份规格的状态改为“已发布”。向用户报告链接或路径。

## 问题陈述

从用户的视角描述用户面临的问题。

## 解决方案

从用户的视角描述解决方案。

## 依据文档

实现者和评审者需要打开的文档，每项一行，写成链接：功能清单、规格拆分表、设计稿或设计资料目录、视觉规格章节、相关 ADR、原型分支。没有就写“无”。

## 功能项

这份规格负责的全部功能项，写明批次。有独立功能清单时，列出编号、名称和本批次的需覆盖状态，并链接清单；小功能没有独立清单时，按功能清单的列直接写成表格，编号同样使用 `F-001` 的形式。

## 用户故事

一份很长的编号用户故事列表。每条格式如下：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行用户，我想看到各账户余额，以便在花钱时做出更明智的决定
</user-story-example>

这份列表要非常详尽，覆盖这个功能的各个方面。涉及功能项时，在故事末尾标注编号，例如“（F-042）”。

## 全局约束

适用于整个项目、所有开发任务都必须满足的硬性要求。每条一行，数值照原样写，例如版本下限、依赖限制、命名与文案规则、平台要求。项目使用特性开关隐藏未完成的功能时，在这里写明开关方案。每项任务都默认包含这一节的要求。没有就写“无”。

## 非功能需求

性能、无障碍、多语言、可观测性等要求，每条一行：

| 编号 | 要求     | 指标与目标值             | 验证方式             | 任务                  |
| ---- | -------- | ------------------------ | -------------------- | --------------------- |
| N-01 | 首屏加载 | 4G 网络下 2.5 秒内可交互 | CI 中运行 Lighthouse | 由 `/to-tickets` 回填 |

目标值必须是可以测量的数值或可以检查的条件，例如“所有页面通过 axe 检查，无严重问题”。没有就写“无”。

## 实现决策

已经确定的实现决策，可以包括：

- 要新建或修改的模块
- 这些模块中要修改的接口
- 开发者给出的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体交互，以及每个状态下的表现

不写代码文件路径或代码片段，它们很快会过时。依据文档不受这条限制，统一写在“依据文档”一节并按需引用。

例外：如果原型产出的片段（状态机、reducer、schema、类型结构）比文字更准确地表达了某个决策，把它内联到相关决策中，并简短注明来自原型。只截取表达决策的部分，不放完整的可运行演示。

## 测试决策

已经确定的测试决策，包括：

- 什么是好的测试（只测外部行为，不测实现细节）
- 每个模块的测试层次，以及每一层的接缝
- 页面状态自动检查使用的工具，以及截图基线的视口和设备
- 每条非功能需求的验证方式
- 可以参考的已有测试（代码库中类似的测试）

## 不在范围内

描述本规格不包含的内容。涉及功能项时，只能引用功能清单中已由用户确认为“不做”的项、延后到更晚批次的项，或属于规格拆分表中其他规格的项（写明是哪份规格）。

## 补充说明

关于这个功能的其他说明。
