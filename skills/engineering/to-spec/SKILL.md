本 skill 基于当前对话上下文和对代码库的理解产出一份规格。不再访谈用户，只综合你已经知道的。

issue 追踪器和分诊标签词汇应已提供给你；若没有，告诉用户运行 `/setup-dev-skills`。

## 过程

### 1. 了解现状

还没探索过仓库的话，先探索，了解代码库当前状态。规格全文使用项目术语表的词汇，并尊重你所涉及区域的 ADR。

### 2. 勾勒测试接缝

勾勒出你将在哪些接缝上测试这个功能。优先用已有的接缝，而不是新建。用尽可能高层的接缝。需要新接缝时，也提在尽可能高的位置。整个代码库里接缝越少越好，理想数量是一个。

与用户确认这些接缝符合他们的预期。

### 3. 写规格

按下面的模板写。

### 4. 自查

用全新的眼光看一遍写好的规格，发现问题当场改：

- **占位符**：有没有"待定""TODO"、没写完的小节、含糊的要求？
- **内部一致**：各节之间有矛盾吗？实现决策与用户故事对得上吗？
- **歧义**：有没有哪条要求能被读成两种意思？有就选一种并写明。
- **范围**：它聚焦到足以拆成一组工单吗？还是其实是几个独立子系统，应该分成几份规格？是后者就告诉用户。

### 5. 发布

发布到项目的 issue 追踪器，打上 `ready-for-agent` 分诊标签，不需要额外分诊。报告链接或路径。

<spec-template>

## 问题陈述

从用户的视角描述用户面临的问题。

## 解决方案

从用户的视角描述解决方案。

## 用户故事

一份很长的、编号的用户故事列表。每条的格式：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行用户，我想看到各账户余额，以便在花钱时做出更明智的决定
</user-story-example>

这份列表要非常详尽，覆盖这个功能的方方面面。

## 全局约束

项目级、贯穿所有工单的硬性要求，每条一行，数值照原样写：版本下限、依赖限制、命名与文案规则、平台要求、性能预算。每张工单的要求都隐含包含这一节。没有就写"无"。

## 实现决策

已经做出的实现决策清单，可以包括：

- 要新建或修改的模块
- 这些模块中要修改的接口
- 开发者给出的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体交互

不写具体文件路径或代码片段，它们很快就会过时。

例外：原型产出了一段比文字更精确地编码了某个决策的片段（状态机、reducer、schema、类型形状）时，把它内联到相关决策里，简短注明来自原型。只截取承载决策的部分，不要一个能跑的演示。

## 测试决策

已经做出的测试决策清单，包括：

- 什么是好测试（只测外部行为，不测实现细节）
- 哪些模块会被测试，在哪些接缝上
- 可参考的已有测试（代码库里类似的测试）

## 不在范围内

描述本规格不包含的内容。

## 补充说明

关于这个功能的其他说明。

</spec-template>
