本 skill 根据当前对话和你对代码库的理解产出一份规格。不再访谈用户，只综合已经掌握的信息。

issue 追踪器和分诊标签词汇应该已经提供给你；如果没有，告诉用户运行 `/setup-dev-skills`。

## 过程

### 1. 了解现状

如果还没有探索过仓库，先探索，了解代码库的当前状态。规格全文使用项目术语表中的词汇，并遵守涉及区域的 ADR。

### 2. 确定测试接缝

列出你打算在哪些接缝上测试这个功能：

- 优先使用已有接缝，而不是新建。
- 选择尽可能高层的接缝。需要新接缝时，也放在尽可能高的位置。
- 整个代码库中的接缝越少越好，理想情况是一个。

与用户确认这些接缝符合预期。

### 3. 写规格

按下面的模板写。

### 4. 自查

换个角度重读写好的规格，发现问题就地修改：

- **占位符**：是否有“待定”、TODO、没写完的小节或含糊的要求？
- **内部一致**：各节之间是否矛盾？实现决策与用户故事是否对得上？
- **歧义**：是否有要求能读出两种意思？有就选定一种并写明。
- **范围**：它是否聚焦到足以拆成一组开发任务？如果其实包含几个独立子系统，应拆成几份规格，并告诉用户。

### 5. 发布

发布到项目的 issue 追踪器，加上 `ready-for-agent` 分诊标签，无需再做分诊。向用户报告链接或路径。

<spec-template>

## 问题陈述

从用户的视角描述用户面临的问题。

## 解决方案

从用户的视角描述解决方案。

## 用户故事

一份很长的编号用户故事列表。每条格式如下：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行用户，我想看到各账户余额，以便在花钱时做出更明智的决定
</user-story-example>

这份列表要非常详尽，覆盖这个功能的各个方面。

## 全局约束

适用于整个项目、所有开发任务都必须满足的硬性要求。每条一行，数值照原样写，例如版本下限、依赖限制、命名与文案规则、平台要求、性能预算。每项任务都默认包含这一节的要求。没有就写“无”。

## 实现决策

已经确定的实现决策，可以包括：

- 要新建或修改的模块
- 这些模块中要修改的接口
- 开发者给出的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体交互

不写具体文件路径或代码片段，它们很快会过时。

例外：如果原型产出的片段（状态机、reducer、schema、类型结构）比文字更准确地表达了某个决策，把它内联到相关决策中，并简短注明来自原型。只截取表达决策的部分，不放完整的可运行演示。

## 测试决策

已经确定的测试决策，包括：

- 什么是好的测试（只测外部行为，不测实现细节）
- 哪些模块需要测试，在哪些接缝上测试
- 可以参考的已有测试（代码库中类似的测试）

## 不在范围内

描述本规格不包含的内容。

## 补充说明

关于这个功能的其他说明。

</spec-template>
