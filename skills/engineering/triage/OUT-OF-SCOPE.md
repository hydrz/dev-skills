# 不在范围内知识库

仓库里的 `.out-of-scope/` 目录保存被否决的功能请求的持久记录。它有两个用途：

1. **组织记忆**：功能为什么被否决，issue 关闭后理由不会丢失
2. **去重**：新 issue 与之前的否决相匹配时，skill 可以摆出之前的决定，而不是重新争论一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

一个**概念**一个文件，而不是一个 issue 一个文件。请求同一件事的多个 issue 归到同一个文件下。

## 文件格式

文件用轻松易读的风格写，更像一篇简短的设计文档而不是数据库条目。用段落、代码示例和例子把理由讲清楚，让第一次看到它的人也能受益。

~~~markdown
# 深色模式

本项目不支持深色模式或面向用户的主题切换。

## 为什么不在范围内

渲染管线假设 `ThemeConfig` 中只定义了一套调色板。支持多主题需要：

- 一个包裹整个组件树的主题上下文提供者
- 每个组件按主题解析样式
- 保存用户主题偏好的持久层

这是一次重大的架构改动，与项目专注内容创作的定位不符。主题是嵌入或再分发产出的下游消费者要关心的事。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，构建时解析
  fonts: FontStack;
}
```

## 此前的请求

- #42："加个深色模式"
- #87："为无障碍提供夜间主题"
- #134："深色主题选项"
~~~

### 文件命名

用简短、描述性的 kebab-case 概念名：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名字要足够好认，浏览目录的人不打开文件就知道被否决的是什么。

### 写理由

理由要有实质内容：不是"我们不想要"，而是为什么。好的理由会引用：

- 项目范围或理念（"本项目专注 X；主题是下游关心的事"）
- 技术约束（"支持它需要 Y，这与我们的 Z 架构冲突"）
- 战略决定（"我们选择了 A 而不是 B，因为……"）

理由要经得起时间。暂时性的情况（"我们现在太忙"）不是真正的否决，而是推迟，不写进这里。

## 何时检查 `.out-of-scope/`

分诊时（第 1 步：收集上下文），读 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否匹配某个已有的不在范围内概念
- 按概念相似度匹配，而不是关键词："夜间主题"匹配 `dark-mode.md`
- 匹配到了就告诉维护者："这与 `.out-of-scope/dark-mode.md` 相似。我们之前否决它是因为[理由]。你现在还这么看吗？"

维护者可能：

- **确认**：把新 issue 加到已有文件的"此前的请求"列表，然后关闭
- **重新考虑**：删除或更新该文件，issue 走正常分诊
- **不同意匹配**：两个 issue 相关但不同，走正常分诊

## 何时写入 `.out-of-scope/`

只在 **enhancement**（不是 bug）以 `wontfix` *被否决*时写。这对 enhancement PR 和 issue 一样适用：被否决的 PR 也记录在这里，同样的请求就不会以新代码的形式再回来。

因为**已实现**而以 `wontfix` 关闭的，不写这里。那是已经建好的功能，不是被否决的；记下来会用虚假的否决污染去重检查。关闭评论改为指出该功能已在哪里。

流程：

1. 维护者判定某个功能请求不在范围内
2. 检查是否已有匹配的 `.out-of-scope/` 文件
3. 有：把新 issue 追加到"此前的请求"列表
4. 没有：新建文件，写上概念名、决定、理由和第一个请求
5. 在 issue 上发评论说明决定，并提及该 `.out-of-scope/` 文件
6. 以 `wontfix` 标签关闭 issue

## 更新或删除

维护者对之前否决的概念改变主意时：

- 删除该 `.out-of-scope/` 文件
- 不需要重新打开旧 issue，它们是历史记录
- 触发重新考虑的新 issue 走正常分诊
