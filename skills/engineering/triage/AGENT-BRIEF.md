# 编写 agent 简报

agent 简报是一条结构化评论，在 issue 或 PR 移到 `ready-for-agent` 时发布。它是 agent 独立工作时依据的权威规格。原始正文和讨论只是背景，简报才是约定。

简报说明 **agent 应该做什么**，issue 和 PR 两种入口都适用：对 issue，是从零开始实现改动；对 PR，是说明*基于现有 diff* 还要做什么，例如补全功能、弥补缺口、处理评审意见。原则相同，下文的 PR 示例展示了区别。

## 原则

### 长期有效优先于精确定位

issue 可能在 `ready-for-agent` 中停留几天甚至几周，期间代码库会变化。编写简报时，要让它在文件被重命名、移动或重构之后依然有用。

- **写**接口、类型和行为契约
- **写**agent 应当查找或修改的具体类型、函数签名或配置结构
- **不写**文件路径和行号，它们会过时
- **不假设**当前的实现结构会保持不变

### 描述行为，不描述步骤

描述系统**应该做什么**，而不是**怎么实现**。agent 会重新探索代码库，自己作出实现决策。

- **好：** “`SkillConfig` 类型应接受一个可选的 `schedule` 字段，类型为 `CronExpression`”
- **差：** “打开 src/types/skill.ts，在第 42 行加一个 schedule 字段”
- **好：** “用户不带参数运行 `/triage` 时，应看到需要处理的 issue 摘要”
- **差：** “在主处理函数里加一个 switch 语句”

### 验收标准完整

agent 需要知道什么时候算完成。每份简报都必须有具体、可测试的验收标准，每条都能独立验证。

- **好：** “运行 `gh issue list --label needs-triage` 返回已经过初步分类的 issue”
- **差：** “分诊应该正常工作”

### 范围边界明确

写明哪些内容不在范围内，避免 agent 做超出需求的额外工作，或对相邻功能作出假设。

## 模板

```markdown
## Agent 简报

**类别：** bug 或 enhancement
**摘要：** 一句话说明要做什么

**当前行为：**
描述现在的情况。对 bug，写出错的行为；对 enhancement，写新功能所基于的现状。

**期望行为：**
描述 agent 完成工作后应该出现的行为。边界情况和错误条件要写具体。

**关键接口：**

- `TypeName`：需要改什么，为什么
- `functionName()` 的返回类型：现在返回什么，应该返回什么
- 配置结构：需要新增的配置项

**验收标准：**

- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**不在范围内：**

- 本 issue 不应改动或处理的内容
- 看似相关、实际独立的相邻功能
```

## 示例

### 好的简报（bug）

```markdown
## Agent 简报

**类别：** bug
**摘要：** skill 描述截断时切在单词中间，输出残缺

**当前行为：**
skill 描述超过 1024 个字符时，不考虑单词边界，一律在第 1024 个字符处截断，
导致描述停在单词中间（例如 "Use when the user wants to confi"）。

**期望行为：**
截断位置应落在第 1024 个字符之前的最后一个单词边界，并追加 "..." 表示截断。

**关键接口：**

- `SkillMetadata` 类型的 `description` 字段：类型不变，但填充它的校验和处理逻辑
  需要考虑单词边界
- 所有读取 SKILL.md frontmatter 并提取 description 的函数

**验收标准：**

- [ ] 不足 1024 字符的描述保持不变
- [ ] 超过 1024 字符的描述在第 1024 个字符之前的最后一个单词边界处截断
- [ ] 被截断的描述以 "..." 结尾
- [ ] 包括 "..." 在内的总长度不超过 1024 字符

**不在范围内：**

- 修改 1024 字符的上限本身
- 支持多行描述
```

### 好的简报（enhancement）

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 支持用 `.out-of-scope/` 目录记录被否决的功能请求

**当前行为：**
功能请求被否决时，issue 加上 `wontfix` 标签和一条评论后关闭，没有关于决定和理由的长期记录。
以后出现类似请求时，需要维护者回忆或搜索之前的讨论。

**期望行为：**
被否决的功能请求应记录在 `.out-of-scope/<概念>.md` 文件中，写明决定、理由，
以及所有请求过该功能的 issue 链接。分诊新 issue 时，应检查这些文件中是否有匹配项。

**关键接口：**

- `.out-of-scope/` 中的 Markdown 文件格式：每个文件有 `# 概念名` 标题、
  `**决定：**` 行、`**理由：**` 行，以及带 issue 链接的 `**此前的请求：**` 列表
- 分诊流程应在早期读取所有 `.out-of-scope/*.md`，并按概念相似度匹配新 issue

**验收标准：**

- [ ] 以 wontfix 关闭功能请求时，创建或更新 `.out-of-scope/` 中的文件
- [ ] 文件包含决定、理由和已关闭 issue 的链接
- [ ] 已存在匹配的 `.out-of-scope/` 文件时，把新 issue 追加到其“此前的请求”列表，而不是新建重复文件
- [ ] 分诊期间检查已有的 `.out-of-scope/` 文件，新 issue 与之前的否决匹配时提示维护者

**不在范围内：**

- 自动匹配（由人确认是否匹配）
- 重新打开之前被否决的功能
- bug 报告（只有 enhancement 的否决写入 `.out-of-scope/`）
```

### 好的简报（PR）

对 PR，“当前行为”描述 diff 的现状，简报要求 agent 补全或修正，而不是从头实现。

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 补全贡献者为 `triage list` 添加的 `--json` 输出参数

**当前行为：**
PR 添加了 `--json` 参数，把 issue 列表序列化为 JSON。正常路径可用，diff 也符合项目的命令结构。
还有两个缺口：错误仍以人类可读的文本输出（不是 JSON），新参数没有测试覆盖。

**期望行为：**
带 `--json` 时，所有输出（包括错误）都是写到 stdout 的合法 JSON，命令的退出码不变。
不带该参数时，现有的人类可读输出不受影响。

**关键接口：**

- 在 `--json` 模式下，命令的错误路径应输出 `{ "error": string }`，而不是纯文本错误
- 复用 PR 已添加的序列化器，不引入第二个

**验收标准：**

- [ ] `triage list --json` 在成功和错误两种情况下都输出合法 JSON
- [ ] 退出码与非 JSON 模式一致
- [ ] 有测试覆盖 `--json` 的成功输出和一种错误情况
- [ ] 默认（非 JSON）输出逐字节保持不变

**不在范围内：**

- 为其他命令添加 `--json`
- 修改 PR 已定义的成功输出的 JSON 结构
```

### 差的简报

```markdown
## Agent 简报

**摘要：** 修一下分诊的 bug

**要做的：**
分诊那块坏了。看看主文件修一下。
大概第 150 行附近的函数有问题。

**要改的文件：**

- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

问题在于：

- 没有类别
- 描述含糊（“分诊那块坏了”）
- 引用了会过时的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前行为和期望行为
