# 分诊

让项目 issue 追踪器上的 issue 在一个小的分诊角色状态机里流转。

本仓库把外部 pull request 当作需求入口时（见 issue 追踪器配置），分诊也覆盖它们：**PR 就是附带了代码的 issue**，用同样的角色、同样的状态、同样的状态机，差异处在下文标注"对 PR"。按追踪器配置把裸的 `#42` 解析为 issue 或 PR。

分诊期间发到 issue 追踪器上的每条评论或 issue，**开头都带**这句声明：

```
> *本内容由 AI 在分诊过程中生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写持久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已完整描述，可交给离席（AFK）的 agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对 PR，同样的状态针对附带的代码来理解：`ready-for-agent` 表示附上了简报，应由 agent 在 diff 上推进下一步；`ready-for-human` 表示可以由人合并。

每个分诊过的 issue 恰好带一个类别角色和一个状态角色。状态角色冲突时，先指出并询问维护者，再做其他事。

这些是规范角色名。issue 追踪器里实际的标签字符串可能不同。映射应已提供给你；若没有，告诉用户运行 `/setup-dev-skills`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`；从那里转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖；看起来不寻常的流转先指出并询问。

## 调用

维护者调用 `/triage` 并用自然语言描述想做什么。理解请求并行动。例如：

- "给我看看需要我关注的"
- "看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有哪些可以交给 agent 的？"

## 展示需要关注的

查询 issue 追踪器，分三组展示，最旧的在前：

1. **未打标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且上次分诊记录之后报告者有新动态**：需要重新评估。

PR 在范围内时，把外部 PR 也放进这些分组，每行标 `[PR]` 或 `[issue]`。发现阶段只列出*外部* PR（追踪器配置定义谁算外部），协作者进行中的 PR 不是分诊工作。这个过滤只用于发现；被明确点名的 PR 不论作者都要分诊。

显示数量，每项一行摘要。让维护者挑。

## 分诊一个具体的 issue 或 PR

1. **收集上下文。** 读完整个 issue 或 PR（正文、评论、标签、作者、日期；对 PR，还有 diff）。解析之前的分诊记录，不重复问已解决的问题。用项目术语表的词汇探索代码库，尊重相关区域的 ADR。对代码库做两项检查：(a) **是否已实现**：按领域概念（而不只是请求的字眼）搜索被请求行为的现有实现，并报告你查了哪里。找到了就是"已实现"的 `wontfix`（第 5 步）。(b) **是否曾被否决**：读 `.out-of-scope/*.md`，把与本请求相似的都摆出来。

2. **给出建议。** 告诉维护者你建议的类别和状态及理由，附上与请求相关的简短代码库摘要（包括是否已实现）。等待指示。

3. **核实主张。** 拷问之前，先确认主张站得住。对 bug，按报告者的步骤复现。对 PR，确认 diff 做了它声称的事：检出，跑相关测试或命令。报告结果：已确认（附代码路径）、复现失败、或细节不足（强烈的 `needs-info` 信号）。经过确认的核实能让 agent 简报有力得多。

4. **拷问（如需要）。** 请求需要充实时，调用 Skill 工具两次，分别为 `grilling` 和 `domain-modeling`，一轮一轮把它问清楚，决定落定时就地打磨领域术语、更新 `CONTEXT.md` 和 ADR。

5. **应用结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但写明为什么不能委派（需要判断、需要外部访问权限、需要设计决策、需要手工测试）。
   - `needs-info`：发分诊记录（模板见下）。
   - `wontfix`：关闭 issue，评论内容取决于*原因*：
     - **已实现**：改动已存在于代码库。指出它在哪里；**不写** `.out-of-scope/`（那个知识库记录的是*被否决*的请求，不是已经建好的）。
     - **否决（bug）**：礼貌说明原因，然后关闭。
     - **否决（enhancement）**：写入 `.out-of-scope/`，在评论里链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上角色。有部分进展时可选附评论。

## 快速覆盖状态

维护者说"把 #42 移到 ready-for-agent"时，信任他们，直接应用角色。先确认你要做什么（角色变更、评论、关闭），然后行动。跳过拷问。没经过拷问就移到 `ready-for-agent` 时，问是否要写 agent 简报。

## needs-info 模板

```markdown
## 分诊记录

**目前已确认的：**

- 要点 1
- 要点 2

**还需要你（@报告者）提供的：**

- 问题 1
- 问题 2
```

拷问中解决的一切都写进"目前已确认的"，工作不会丢。问题要具体、可操作，而不是"请提供更多信息"。

## 恢复之前的会话

issue 或 PR 上已有分诊记录时，读它们，检查报告者是否回答了未决问题，先给出更新后的全貌，再继续。已解决的问题不再重问。
