# 工作流导航

用户记不住每个 skill，所以来这里询问。

阅读用户描述的情况，对照下面的说明，告诉用户该用哪个 skill（或哪几个、按什么顺序）以及原因。情况不清楚时，先问一两个问题再推荐。

这些 skill 可以组合成不同的工作路径。大多数工作沿着**主流程**推进，另有几个**其他入口**产生工作后汇入主流程。其余是独立工具，或者作为方法与术语在其他 skill 内部使用。

## 先看规模

流程随规模简化，**实施前确认**不简化：无论改动多小，开始修改之前都要让用户对“要做什么”明确表示同意。

| 规模             | 例子                                           | 路径                                                                                             |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **可行性验证**   | “能不能用 X 做到 Y？”                          | 说明要验证什么，用户同意后去查证；需要运行代码时用 `prototype`，最后报告结论和建议               |
| **小范围改动**   | 仓库已有流程上的一个参数、一个小接口或一处修复 | 用 `/grill-me` 或 `/grill-with-docs` 追问几轮，在对话里给出简短设计，用户同意后运行 `/implement` |
| **架构级**       | 新项目、新子系统，或改变其他代码依赖的接口     | 完整主流程（见下文）                                                                             |
| **大型模糊工作** | 一个会话无法完成，连实现路径都还不清楚         | `/wayfinder`                                                                                     |

在两档之间拿不准时，选更重的一档。途中发现隐藏的复杂度时，停下来升档。

## 主流程：从想法到交付

大多数工作都走这条路径：你有一个想法，想把它做出来。

1. **`/grill-with-docs`**：通过追问完善想法。只要**在工作目录中**，就从这里开始。它会把讨论中确认的术语和决策写入 `CONTEXT.md` 和 ADR。

   没有工作目录时，用 `/grill-me`（见“独立工具”）。两者使用同一个 `grilling` 方法；`/grill-with-docs` 会留下文字记录，所以有仓库时优先使用它。

2. **判断：每个问题都能在对话里确定吗？** 某个问题需要可运行的答案（状态、业务逻辑、需要亲眼看到的 UI）时，先做原型。原型放在独立目录中，所以前后都用 **`/handoff`** 衔接（见“阶段边界”）：
   - 用 **`/handoff`** 写出交接文件，然后基于该文件开一个新会话；
   - 用 **`prototype`** 编写一次性代码回答问题；
   - 用 **`/handoff`** 把结论带回来，并在原来的讨论中引用它。

3. **判断：这项工作需要多个会话吗？**
   - **需要**：运行 **`/to-spec`**，把讨论整理成规格（包含自查）。工作涉及多个业务模块时，`/to-spec` 第一次运行只为当前发布批次产出**规格拆分表**，之后按依赖顺序对每份规格运行一次 `/to-spec <模块>`，每份规格各自走完下面的步骤；缺少功能清单时，它会让你先运行 `/wayfinder` 补建。然后运行 **`/to-tickets`**，拆成端到端最小闭环任务，每项任务都写明**前置依赖**、**接口**和覆盖的**功能项**；功能项有任何状态没有任务覆盖时，它不会发布。之后二选一：
     - **由你全程跟进**：对每项任务运行 **`/implement`**，**每项任务之间清空上下文**（`/clear`）。每项任务都是自包含的，上一项的上下文可以丢弃。使用本地追踪器时，手动按依赖顺序推进；使用真实追踪器时，前置依赖都已完成的任务谁都可以领取。
     - **交给 agent 独立完成**：运行 **`/implement-spec`**。它作为协调者，并行派出子代理处理当前可执行的任务，逐项评审，把进度写入文件以便上下文压缩后恢复，并汇总它代你作出的所有决策。交付方式在开始时由你选择：整份规格一个 PR；或者每项任务一个 PR，配合特性开关逐项合入主干，并可授权它自行合并评审和 CI 都通过的 PR。
   - **不需要**：直接在当前上下文中运行 **`/implement`**。

   功能清单记录要交付的每个功能项、它的发布批次、需覆盖状态和设计依据。规格、任务、评审和完成验证只核对**当前批次**，并按清单逐项核对，页面要逐个状态截图，与设计依据对比；缩减范围（包括把功能项或状态移到更晚的批次）必须由你确认。这样交付时不会只做了主流程，页面也不会偏离设计。当前批次全部完成后，由你确认切换到下一个批次，再从 `/to-spec` 开始新一轮。

   规格中还会写明**非功能需求**（性能、无障碍、多语言、可观测性）的目标值和验证方式，以及测试层次、接缝和页面状态的自动检查工具。这些在规格里确定一次，实现时不再逐项任务询问。格式见 `docs/agents/feature-list.md`（由 `/setup-dev-skills` 写入）。

   无论走哪条路径，实现时都在约定的接缝上使用 **`tdd`**（每次完成一个从失败到通过的循环），用 **`code-review`**（按编码规范和规格两个维度评审）检查，用 **`verifying-completion`** 核对完成情况，最后用 **`finishing-a-branch`** 决定合并、创建 PR 还是保留分支。

### 上下文管理

步骤 1 到 3 保持在**同一个不中断的上下文窗口**中（运行 `/to-tickets` 之前不压缩、不清空），让追问、规格和任务都基于同一份讨论。之后每次运行 `/implement` 时，从任务描述重新开始。

限制在于模型能否继续可靠推理。运行 `/to-tickets` 之前，如果出现以下信号，在最近的阶段边界运行 `/compact` 后再继续（见“阶段边界”）：

- 上下文已经接近上限；
- 难以准确回忆早期决策；
- 输出开始遗漏已经确认的约束。

## 其他入口

这些入口会产生工作，然后汇入主流程。

- **待处理的 bug 和需求越来越多**：运行 **`/triage`**。它按分诊状态处理 issue，产出可以交给 agent 的 issue，之后由 **`/implement`** 领取。

  分诊只针对**不是你创建的** issue：bug 报告、外部功能请求，以及任何未经整理的输入。`/to-tickets` 产出的任务已经可以交给 agent，**无需再分诊**。

- **代码出了问题**：使用 **`diagnosing-bugs`**。直接描述问题，agent 会自动使用它；也可以输入 `/diagnosing-bugs`。它适用于难排查的问题：一眼看不出原因的 bug、时有时无的不稳定问题、在两个已知正常的版本之间出现的回归。

  它会先建立一个**快速的反馈回路**（一条已经能在*当前* bug 上失败的命令），再开始推理原因；修复时附带回归测试；连续修复三次仍未解决时，停下来检查架构问题。如果最后发现根本原因是缺少合适的接缝来测试这个 bug，它会建议运行 **`/improve-codebase-architecture`**。

- **范围很大、方向还不清楚的工作，例如全新项目或大型功能，一个会话无法完成**：运行 **`/wayfinder`**。这是认知负担最重的流程。实现路径还不明确时，它在 issue 追踪器上建立一张**共享地图**（一个汇总 issue），把工作拆成一组**决策项**，每次解决一项。它产出的是**决定，而不是交付物**，直到后续实现路径变得明确。交付产品或子系统时，它还会建立**功能清单**，并用 `design` 类型的决策项为页面补齐设计依据；当前批次没有待定项、设计依据齐全，才算路径明确。同一模块的普通页面可以合并成一个设计决策项，一次确认。已有规格或任务、但缺少功能清单的工作，也用它补建清单并找出缺口。

  `/grill-with-docs` 适合一个会话能讨论完的想法，`/wayfinder` 适合一个会话讨论不完的想法。它更慢、更重，所以只用于这种情况；范围清楚的功能不需要它。

  路径明确后，**它只负责交接，不负责实现**：通过 **`/to-spec`** 进入主流程，把地图上链接的决策整理成可实现的规格，然后照常运行 `/to-tickets`、`/implement` 或 `/implement-spec`。只有工作最终被证明确实很小时，才直接运行 `/implement`。

## 代码库维护

这部分不是功能开发，而是日常维护。

- **`/improve-codebase-architecture`**：有空时运行，让代码库持续适合 agent 工作。它会找出可以加深模块的机会；选中一个后，把它作为新想法，从 `/grill-with-docs` 进入主流程。它负责寻找候选项；**`codebase-design`**（见下文）负责为选中的候选项做设计。

## 底层方法与术语

这些是可自动触发的 skill：agent 会在合适的场景主动使用，其他 skill 也会调用它们。需要时也可以直接输入名称。

**方法**，约束工作方式：

- **`tdd`**：在约定的接缝上，每次完成一个端到端最小闭环的红、绿循环；确认测试因正确的原因失败，收尾时做变异检查。
- **`verifying-completion`**：先证据后结论。声称完成、修好或通过之前，在本轮运行对应命令并阅读输出。
- **`code-review`**：审查自某个比较基准以来的改动，从编码规范和规格两个维度并行评审，并按严重度分级。
- **`receiving-code-review`**：收到评审意见后先核实再修改，不做表面附和，有理由时提出反对意见。
- **`finishing-a-branch`**：测试通过后，提供合并、创建 PR、保留分支三个选项，由你决定；丢弃分支需要输入 `discard` 确认。

**术语**，各自是一类词汇的唯一权威来源。问题出在**用词**而不是流程上时，直接使用它们：

- **`domain-modeling`**：完善项目的*领域*语言，例如澄清一个模糊的词、拆分一个承担多种含义的词（“账户”同时指三种东西），把难以逆转的决策记录成 ADR。`/grill-with-docs` 在讨论中就会使用这套方法。
- **`codebase-design`**：深模块相关术语（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的*结构*：让简单的接口背后提供丰富的行为，并放在合适的接缝处。它也负责业务模块的结构判断：模块之间只通过公开接口或契约交互，模块内部按业务复杂度决定是否引入 DDD 战术模式。`tdd` 和 `/improve-codebase-architecture` 都使用这套术语。

## 阶段边界

**阶段**是会话中的一段工作，例如追问、实现、QA。在两个阶段之间的**边界**上有五个选项，而如何选择是整个工作流中最难判断的决定：

- **继续**：留在当前会话。没有成本，也不丢失信息。
- **`/clear`**：清空上下文窗口。适用于当前内容与后续工作完全无关的情况。
- **`/handoff`**：写一份可移植的 Markdown 文件。用途很窄，只用于**更换 agent 工具**、**更换目录**、**交给同事**，或在**阶段中途**分出一个旁支任务。它提供的是可移植性。
- **子代理**：把一个范围明确的任务放进独立的上下文窗口，拿回一份报告。
- **`/compact`**：压缩当前上下文，用摘要开启新会话。它是**默认选项**，位于判断顺序的最后，而不是第一反应。

有序的判断步骤（五个问题、每个选项背后的理由，以及为什么要最先考虑**继续**）见 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)。只在边界上作这个决定；阶段中途只能继续，或者把剩余工作交给子代理。

## 独立工具

这些工具不属于主流程。

- **`/grill-me`**：与 `/grill-with-docs` 使用相同的追问方式，但**不保存状态**：不写入本地文件，也不创建 `CONTEXT.md`。**不在工作目录中**时使用，例如完善一个计划、一个设计或一篇文章。在工作目录中时，使用 `/grill-with-docs`，它的追问方式相同，还会留下文字记录。
- **`grilling`**：追问方法本身，包括规模分档、轮次、当前待确认项，以及“事实由 agent 查证、决策由你作出”的分工。`/grill-me` 和 `/grill-with-docs` 是它的两个命名入口，`/triage`、`/wayfinder`、`/improve-codebase-architecture` 也在内部使用它。只有需要不附加任何流程的追问时，才直接使用它。
- **`resolving-merge-conflicts`**：逐个 hunk 处理进行中的 merge 或 rebase 冲突，根据双方一手资料追溯出的**意图**解决冲突，而不是简单挑选某一侧的代码行，然后完成操作。已经处于冲突状态时使用。
- **`prototype`**：编写小型一次性程序来回答一个设计问题，例如某个状态模型是否合理、某个 UI 应该是什么样子。结束时把选定的结果写回功能项的设计依据（UI 原型保存每个状态的截图），实现者照着设计依据做，而不是去翻原型分支。“一次性”约束的是代码写法，而不是必须删除原型：结论会整合进正式代码，原型本身作为**一手资料**保留在主干之外的 `prototype/<名称>` 分支上，并由实现 issue 引用。它是主流程第 2 步的分支，但任何难以在纸面上确定的设计问题都可以使用。
- **`research`**：把资料阅读工作交给一个**后台 agent**。它根据**一手资料**调查问题，并在仓库中留下一份带引用的 Markdown 文件，期间你可以继续工作。产出的文件应带*进*主流程的 `/grill-with-docs`，因为调研为思考提供材料，而不是替代思考。
- **`/to-questionnaire`**：阻碍进展的信息既不在你这里、也不在代码库中，而是在**其他人**那里时使用。它为那个人写一份问卷。它和 `/grill-me` 的方向相反：不追问方案本身，而是追问**发送问卷**这件事（发给谁、需要拿回什么信息），并让问题针对信息缺口。收回的答案可以作为 `/grill-with-docs` 或 `/to-spec` 的输入。
- **`wizard`**：用于只有**人**才能完成的步骤，例如开通基础设施、配置凭据或 CI 密钥、在陌生的第三方控制台中操作、执行一次性迁移或切换。它生成一个交互式 bash 脚本，负责打开每个 URL、收集每个值、写入 `.env` 和 GitHub secrets，这样同一流程就不必每次重新向 agent 解释。agent 遇到只有你能完成的步骤时，会主动使用它；agent 自己能完成的步骤会直接完成。
- **`/wait-what`**：没看懂某条消息时使用。它可以在对话中途、在任何其他 skill 内使用：agent 会用平实的语言和 `CONTEXT.md` 中的词汇，补充你缺少的背景，重新解释刚才的内容。它用于事后补救；`/grill-with-docs` 则是事前预防，因为尽早约定的通用语言能从源头减少行话。
- **`/teach`**：把当前目录作为可跨会话延续的学习工作区，分多次会话学习一个概念。
- **`writing-for-agents`**：为 agent 编写文档的参考，包括 skill、AGENTS.md，以及被上下文指针引用的文档；还包括用子代理压力测试约束型 skill 的方法。

## 前置条件

**`/setup-dev-skills`**：首次运行工程流程之前使用，配置其他 skill 依赖的 issue 追踪器、分诊标签和文档布局。也支持自定义 issue 追踪器。
