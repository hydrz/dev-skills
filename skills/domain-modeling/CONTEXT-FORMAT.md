# CONTEXT.md 格式

## 结构

```md
# {上下文名称}

{一两句话说明这个上下文是什么、为什么存在。}

## 语言

**订单**（Order）：
{一两句话描述这个术语}
_避免_：购买、交易

**发票**（Invoice）：
交付后发给客户的付款请求。
_避免_：账单、付款请求

**客户**（Customer）：
下订单的个人或组织。
_避免_：用户、买家、账户

## 关系

- 一个**客户**可以下多个**订单**
- 一个**订单**交付后产生一张**发票**

## 已澄清的歧义

- “账户”曾同时指**客户**和登录用户。已澄清：前者使用**客户**，后者使用**用户**。
```

## 规则

- **明确选定用词。** 同一个领域概念有多种说法时，选择最合适的一个，其余列在 `_避免_` 下。
- **定义要简洁。** 最多一两句。定义它*是*什么，不写它做什么。
- **只收录本项目上下文特有的术语。** 通用编程概念（超时、错误类型、工具模式）即使项目中大量使用，也不收录。添加术语前先判断：这是本上下文特有的概念，还是通用编程概念？只收录前者。
- **在括号中附上代码中的英文名**，让中文术语与代码标识对应。
- **术语自然成组时，用小标题分组。** 所有术语都属于同一个内聚的领域时，直接平铺即可。

## 单上下文与多上下文

**单上下文（大多数仓库）：** 根目录一个 `CONTEXT.md`。

**多上下文：** 根目录的 `CONTEXT-MAP.md` 列出各个上下文、所在位置及相互关系：

```md
# 上下文地图

## 上下文

- [订购](./src/ordering/CONTEXT.md)：接收并跟踪客户订单
- [计费](./src/billing/CONTEXT.md)：生成发票并处理付款
- [履约](./src/fulfillment/CONTEXT.md)：管理仓库拣货与发货

## 关系

- **订购 → 履约**：订购发出 `OrderPlaced` 事件；履约接收该事件并开始拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费接收该事件并生成发票
- **订购 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

判断采用哪种结构：

- 存在 `CONTEXT-MAP.md`：阅读它，找到各个上下文
- 只有根目录的 `CONTEXT.md`：单上下文
- 两者都没有：在第一个术语确定时，按需创建根目录的 `CONTEXT.md`

有多个上下文时，判断当前话题属于哪一个。不清楚时询问用户。
