你拿到了一份规格，以及实现它的开发任务。目标是实现整份规格，并按开始时与用户确认的方式交付：整份规格一个 PR，或每项任务一个 PR。

issue 追踪器配置应该已经提供给你；如果没有，告诉用户运行 `/setup-dev-skills`。

## 角色

你是**协调者**。实现、修复、合并和评审都交给子代理完成。你的上下文留给协调工作：阅读报告、作出代行决策、更新进度记录、派发当前可执行的任务。亲自修改代码会占用你的上下文，也会绕过评审。

与子代理的沟通尽量精简，主要使用**上下文指针**：指向规格、任务、进度记录、报告文件和之前的提交。

- 指针能提供的信息，不在派发提示中重复。
- 不要把前面任务的历史摘要贴进后续派发。
- 你贴进提示的内容和子代理打印回来的内容都会一直占用你的上下文，所以产物以文件形式交接。

## 按依赖关系调度任务

任务之间有前置依赖，因此任何时刻都有一组**当前可执行任务**：前置依赖都已完成、现在就能领取的任务。这些任务并行推进，以获得**最大并行度**。一项任务完成后，可执行任务集合会变化，立即为新解锁的任务派出实现者。

并行的前提是互不干扰：

- 每个实现者在**自己的工作树**和分支上工作，分支基于集成分支的当前头部。工作树的检测、创建和依赖安装见 `implement` skill 目录下的 [WORKTREE.md](../implement/WORKTREE.md)。
- 两项可执行任务会修改同一个模块或同一个接口时，改为串行：先完成一项并合并，再派发另一项。

### 同类小改动合并派发

每派发一次，子代理都要重新建立上下文、运行测试，评审也要再做一次。几项当前可执行任务都是同一种小改动时（在多个文件中做同样的一行修复、修改同一个常量、添加同一个字段），把它们合成**一个批次**，只派发一次：

- 派一个实现者，派发提示列出批次中每项任务的指针，以及每个文件要做的改动。报告文件以批次中第一项任务命名（`ticket-<NN>-batch-report.md`），报告中逐项列出任务。
- 批次在一个工作树和分支上完成，作为整体评审：评审提示列出每项任务的指针，任务符合度逐项给出结论。
- 修复循环和合并按批次整体进行，修复轮次按批次计数。
- 完成后，批次中每项任务各写一行完成记录，提交范围相同。
- 每项任务一个 PR 时，同一批次的任务共用一个 PR，PR 描述逐项链接任务。把这次合批作为代行决策写入进度记录。

需要独立判断、独立测试或独立评审的任务，保持一项任务派发一次。

## 自行决策，不停下等待

规格执行期间不等待用户回复。遇到冲突、歧义、任务缺陷或需要突破的上限时，由你决定。

- **规格是最终依据**，任务是对规格的拆解。功能清单和设计依据是规格的依据文档，同样以它们为准。
- 规格和任务都没有回答的问题，由你判断。

每个代行决策都写入进度记录：

```
决策：<决定了什么> | 理由：<为什么> | 如果错了：<会造成什么影响>
```

然后继续推进。错误决策造成的返工，用户能看到、也能纠正；停在一个问题上等回复，会浪费用户一整天。

只有以下五类情况需要停下来询问用户：

1. 不可逆或破坏性操作
2. 安全敏感操作
3. 当前工作树之外、按惯例需要先询问的副作用（合并到共享分支、推送到共享分支、发布），开始时已获授权的除外（见“准备”第 4 步）
4. 任务或规格缺陷严重，任何推进方式都只能靠猜测
5. **缩减范围**：把功能项改为“不做”、删掉某个状态或把它移到更晚的批次、页面做得达不到设计依据。这类改动会让交付物缺功能，只能由用户决定，不能作为代行决策

增加范围可以作为代行决策：发现漏掉的功能项或状态时，补进功能清单和对应任务（必要时新增任务），写入进度记录后继续。

## 准备

1. **阅读规格和任务。** 读到足以理解任务依赖关系即可：每项任务的标题、前置依赖、验收标准，以及规格的全局约束和依据文档。无需读入每项任务的细节，实现者会阅读自己负责的任务。

2. **进度记录。** 进度记录用于在上下文压缩或会话中断后恢复状态，格式见 [LEDGER.md](LEDGER.md)。
   - 路径：`<仓库根>/.dev-skills/implement-spec/<规格-slug>/ledger.md`，并确保 `.dev-skills/` 被 git 忽略。
   - 已有进度记录且第一行指向这份规格时，从记录恢复：已标为完成的任务不再派发，根据进度记录和 `git log` 重建状态。两者与你的记忆不一致时，以它们为准。
   - 第一行指向其他规格时，那是另一份规格的进度。保持原样，为当前规格新建记录。

3. **预检。** 派发第一项任务之前，检查任务之间的依赖与约束，边检查边写入进度记录：
   - 任务依赖拓扑：检查是否存在循环依赖、是否存在遗漏前置任务或不合理的顺序
   - 与规格全局约束或已商定测试接缝矛盾的任务
   - 任务的验收标准是否清晰且可独立验证
   - 若项目维护了功能清单，对照核实当前批次范围是否有缺口；缺口按增加范围处理，补建任务并写入进度记录

   预检的输出是进度记录中的一张表，不是一句“没问题”。每发现一个冲突，就当场作出代行决策并记录，然后开始执行。实现过程中才出现的冲突由评审环节发现。

4. **分支与 PR。** 与用户确认一次交付方式和合并授权，之后按确认结果执行，不再逐次询问。

   交付方式有三种：

   - **一份规格一个 PR**：新建集成分支并创建草稿 PR（注明关闭规格 issue 和任务 issue），每项任务合并到集成分支，最后一起评审。
   - **每项任务一个 PR**：每项任务从主干（或前置任务的分支）拉出分支，评审通过后单独创建 PR，合并到主干。未完成的功能按规格全局约束中的特性开关方案隐藏。
   - **只在本地分支完成**：不推送，最后使用 `finish-work` skill。

   默认推荐：规格的全局约束写了特性开关方案时，推荐每项任务一个 PR；没有时，推荐一份规格一个 PR，并提醒用户可以切换。

   选择每项任务一个 PR 时，再确认一次合并授权：是否允许你合并评审通过、CI 也通过的任务 PR。
   - **已授权**：满足条件后直接合并到主干。
   - **未授权**：只创建 PR，不合并，由用户合并。依赖它的任务基于它的分支继续开发，对应 PR 的目标分支是前置任务的分支。依赖 PR 的合并顺序见 [PER-TICKET-PR.md](PER-TICKET-PR.md)，创建依赖 PR 时就把这个顺序告诉用户。

   确定交付方式后，在集成分支（每项任务一个 PR 时为主干）运行一次完整测试套件作为基线，结果写入进度记录。基线失败时的处理见 [WORKTREE.md](../implement/WORKTREE.md) 第 3 步。

5. **可选：探索子代理。** 任务需要大量探索（相关代码文件、外部文档）时，派一个探索子代理，把 Markdown 笔记写到仓库外、所有后续子代理都能访问的目录。这样实现者可以专注于实现。

## 每项任务的循环

### 1. 派发实现者

记下 BASE：一份规格一个 PR 时，是集成分支当前头部的 SHA；每项任务一个 PR 时，是主干当前头部，前置任务的 PR 尚未合并时，是前置任务分支的头部。按 [WORKTREE.md](../implement/WORKTREE.md) 为这项任务创建基于 BASE 的工作树和分支并安装依赖，然后派发实现者。提示按 [IMPLEMENTER-PROMPT.md](IMPLEMENTER-PROMPT.md) 填写：

- 一句话说明这项任务在项目中的位置
- 任务的指针（链接或路径），并说明“先读它，这是你的需求”
- 全局约束的指针或原文
- 依据文档的指针：功能清单，以及本任务功能项的设计依据
- 前面任务已完成的模块、已确立的测试接缝，以及任务本身无法得知的相关决策
- 你对任务中歧义之处作出的决策
- 报告文件路径：`<进度记录目录>/ticket-<NN>-report.md`

**能力选择：** 根据任务难度选择能可靠完成工作的能力等级。宿主支持模型或推理强度覆盖时，才显式设置；具体模型名称和默认继承行为以当前环境为准：

| 工作                                         | 能力等级                 |
| -------------------------------------------- | ------------------------ |
| 任务已写清完整行为，只涉及一两个文件         | 快速、低成本             |
| 需要协调多个文件，或需要参照已有模式作判断   | 标准                     |
| 需要设计判断或广泛理解代码库；最终整分支评审 | 高                       |
| 修复循环第 3 轮                              | 比卡住的实现者至少高一档 |

轮数比 token 单价更重要：低成本档处理多步工作时，经常多花两三倍轮数，总成本反而更高。评审者，以及根据文字描述工作的实现者，至少使用标准档。

### 2. 处理报告

实现者只返回简短的状态，细节写在报告文件中：

| 状态                   | 处理方式                                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DONE**               | 进入评审                                                                                                                                             |
| **DONE_WITH_CONCERNS** | 阅读顾虑。涉及正确性或范围的，评审前先解决；只是观察（例如“这个文件越来越大”）的，记录后进入评审                                                     |
| **NEEDS_CONTEXT**      | 补充缺少的上下文，重新派发                                                                                                                           |
| **BLOCKED**            | 判断原因：缺上下文就补充后重新派发；推理能力不足就换更高能力等级重新派发；任务太大就拆分；任务本身有错就作出代行决策、写入进度记录，带着决策重新派发 |

实现者报告卡住时，重新派发前必须改变某些条件：同样能力等级、同样输入的重试不会得到不同结果。

### 3. 评审

生成评审材料并写入进度记录目录下的独立文件（按提交范围命名，例如 `review-<BASE7>..<HEAD7>.diff`）。把文件路径交给评审者，**你自己不读取材料内容**，让 diff 留在你的上下文之外，避免占用协调者上下文并确保评审独立客观。

BASE 用派发前记下的提交，不用 `HEAD~1`：多提交的任务会只剩最后一个提交。生成前必须进行安全校验：

1. 检查 BASE 是否为 HEAD 的祖先：`git merge-base --is-ancestor <BASE> <HEAD>`。若非祖先，说明分支偏离，diff 会混入无关改动。
2. 检查提交数是否大于 0：`git rev-list --count <BASE>..<HEAD>`。若为 0，说明范围内没有提交，核对 BASE 与 HEAD。

**方式 A：Git 原生管道（推荐，跨平台通用）**

无需依赖任何外部语言运行时，在任意技术栈代码库中均可使用原生 Git 命令组装评审材料：

```bash
OUT="<进度记录目录>/review-$(git rev-parse --short=7 <BASE>)..$(git rev-parse --short=7 <HEAD>).diff"
{
  printf '# 评审材料：%s..%s\n\n## 提交\n\n' "$(git rev-parse --short=7 <BASE>)" "$(git rev-parse --short=7 <HEAD>)"
  git log --oneline --no-decorate <BASE>..<HEAD>
  printf '\n## 改动文件\n\n'
  git diff --stat <BASE>..<HEAD>
  printf '\n## diff\n\n'
  git diff --no-color --no-ext-diff -U10 <BASE>..<HEAD>
} > "$OUT"
```

在不支持子 shell 块重定向的终端（如 Windows PowerShell）中，可依次顺序追加（`>> "$OUT"`），或直接使用 `git format-patch --stdout <BASE>..<HEAD> > "$OUT"` 导出标准补丁材料。

**方式 B：Node.js 快捷脚本（可选）**

环境已具备 Node.js 运行时时，可选用本 skill 目录下的 [review-package.mjs](review-package.mjs) 一键完成校验与打包：

```bash
node <本 skill 目录>/review-package.mjs <BASE> <任务分支头部> <进度记录目录>
```

脚本自动校验祖先关系与空提交，输出生成的文件路径。若以退出码 2 结束，按输出提示核对 BASE 后重新生成。

**派发评审者**

生成材料后派发评审者，提示按 [REVIEWER-PROMPT.md](REVIEWER-PROMPT.md) 填写：任务指针、全局约束原文、报告文件路径、评审材料路径。

评审者返回两个结论：**任务符合度**（✅、❌ 或 ⚠️）和**质量**（通过或需修复）。两个结论都必须有。实现者的自查不能替代评审。

⚠️ 项指只看 diff 无法核实的要求，由你亲自核实，因为你掌握评审者没有的跨任务上下文。确认是真实缺口的，按符合度失败处理；属于无法在当前环境自动核实但符合预期的，写入进度记录并列入收尾验收清单。

写评审提示时只提供材料，不预设结论。如果提示中出现“不必标记”“最多算次要”之类的话，说明你在替自己省掉一轮修复。

### 4. 修复循环

以下任一情况触发修复循环：符合度为 ❌、有任何**严重**或**重要**发现，或你确认为真实缺口的 ⚠️ 项。

按 [FIX-LOOP.md](FIX-LOOP.md) 执行：次要发现延后记录，其余发现每项任务最多修复 3 轮，每轮以限定范围的复审结束；第 3 轮后仍未解决的，按其中“达到重试上限”的规则作出代行决策。只在达到重试上限时对评审发现作代行决策。

### 5. 合并

评审通过（或达到重试上限后所有决策都已完成）后，按“准备”第 4 步确定的交付方式处理。

**每项任务一个 PR**：推送任务分支，创建 PR，PR 描述链接任务和评审结论。已获合并授权且 CI 通过时合并到主干；未获授权时保持 PR 打开，按第 4 步的规则让依赖它的任务继续。CI 失败时，把失败作为这项任务的发现，回到修复循环。

存在依赖 PR 时，合并前置 PR、修改目标分支和重新运行 CI 的顺序见 [PER-TICKET-PR.md](PER-TICKET-PR.md)。

**一份规格一个 PR 或只在本地完成**：派一个**合并子代理**，把任务分支合并到集成分支：

- 遇到冲突时，使用 `resolving-merge-conflicts` skill。
- 合并后运行类型检查和相关测试，并报告结果。
- 合并后测试失败时，把失败作为这项任务的发现，回到修复循环。

合并成功后，一次性完成记录：

```
任务 NN：完成（提交 <base7>..<head7>，评审通过）
```

达到重试上限后完成的，追加 `（<K> 项搁置）`。然后更新追踪器上的任务状态，删除该任务的工作树。

### 6. 派发新解锁的任务

合并会改变当前可执行任务：立即为新解锁的任务派出实现者。每项任务一个 PR 且未获合并授权时，前置任务的 PR 创建后，就视为已解锁依赖它的任务。

**等待子代理时**：有本地工作（更新进度记录、准备下一次评审材料、阅读报告）就继续做，子代理的结果会自动返回。确实空闲时，使用宿主提供的等待机制；定期清点仍在运行的子代理，并追问已经结束却没有报告的子代理。

## 最终评审

所有任务完成后，使用 `code-review` skill，比较基准是集成分支的起点（每项任务一个 PR 时，是开始本规格前的主干提交），规格来源是这份规格，并使用高能力等级。把进度记录中所有“延后”和“搁置”的行提供给评审，让它判断哪些必须在合并前修复。

有发现时，只派**一个**修复子代理，并提供完整的发现清单。不要每条发现派一个修复者：每个修复者都要重建上下文、重新运行测试，总成本会超过所有任务加起来。然后只做**一次**限定范围的复审。剩余发现按 [FIX-LOOP.md](FIX-LOOP.md) 中达到重试上限的规则作出代行决策。没有第二轮修复。

声明最终完成之前，使用 `verifying-completion` skill：完整测试套件已在本轮运行并通过，每项任务的验收标准均已满足，规格的用户故事与全局约束均有对应验证证据。

## 收尾

1. **汇报代行决策。** 删除任何内容之前，把进度记录中每一条决策（预检决策、搁置、达到重试上限后的决策，全部包括）按作出的顺序整理到最终消息的“我作出的决策”一节，每条都带“如果错了”的影响。清单必须完整：进度记录中有的，清单中都要有。这是你代替用户作出的决定传达给用户的唯一途径；随工作区一起删除而没有汇报的决策，等于瞒着用户作出的决定。
2. **汇报范围。** 列出本次交付完成的任务；列出需要用户最终验收确认的事项。有任何任务或要求未完成时，明确写出，不写成“已完成”。
3. **交付。** 已创建草稿 PR 的，把 PR 标为可评审。每项任务一个 PR 时，列出每个 PR 的链接和状态（已合并、等待合并），说明未合并 PR 之间的合并顺序。存在依赖 PR 时，同时告诉用户：每合并一个前置 PR，先把依赖它的 PR 目标分支改为主干，再删除前置分支；改完目标分支后要让 CI 重新运行并通过，才合并依赖 PR。只在本地分支完成的，使用 `finish-work` skill。
4. **清理。** 删除所有实现者工作树。PR 合并前保留进度记录；用户确认不再需要后，删除本规格的进度记录目录，git 历史就是记录。

## 常见借口与对应事实

| 借口                               | 事实                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| “我自己修一下更快”                 | 协调者亲自修改会占用上下文并跳过评审。恢复实现者。                                                                 |
| “这个状态不重要，先不做”           | 删减状态就是缩减范围，停下来问用户。                                                                               |
| “差不多符合任务要求了”             | 评审发现了缺口就是没完成。修复，或达到上限后作出代行决策。                                                         |
| “再来一轮就能收敛”                 | 超过上限的循环不会收敛，问题出在结构上。作出代行决策并分类处理。                                                   |
| “修复很小，跳过复审”               | 未经评审的修复正是回归混入的途径。每轮都以复审结束。                                                               |
| “这条发现明显不对，删掉就好”       | 只在达到重试上限时对发现作代行决策，每个决策都写入进度记录。                                                       |
| “写进度记录太麻烦”                 | 进度记录是上下文压缩后唯一可靠的状态。没有它，协调者会把已完成的任务整批重新派发。                                 |
| “实现者自己派了个评审，多一层保险” | 那是对同一份 diff 的重复评审，花费全额成本却不计入流程。任务评审才是有效的检查点。                                 |
| “合并后顺手删掉分支”               | 依赖 PR 仍指向这个分支时，删分支会让 GitHub 关闭依赖 PR 且无法重新打开。先把依赖 PR 的目标分支改为主干，再删分支。 |
