# 修复与重试循环

`implement-spec` 的按需参考：任务执行受阻、测试失败或整分支评审需要修复时读取。

## 任务执行期间的修复与重试

实现者汇报受阻（BLOCKED）或合并前测试失败时，由协调者介入排查，每项任务最多重试 3 轮：

- **第 1、2 轮**：补充缺失的上下文或测试报错信息，恢复原实现者继续修复。
- **第 3 轮**：若仍未解决，派一个**新的**实现者，能力等级至少提高一档，并提供前两次尝试的排查报告；或由协调者评估后作出代行决策（如拆分任务、调整不合理的前置假定）。

### 达到重试上限

第 3 轮仍未解决时，停止盲目重试，由协调者逐条作出代行决策：

- **属于不影响整体功能的可延后问题**：记录为搁置，写明理由与风险，继续推进后续任务。
- **属于阻碍后续任务的关键缺陷**：决定能让下游继续推进的最小改动，记录代行决策后继续。只有推进方式完全依赖猜测时才停下来询问用户。

## 最终评审发现的集中修复

所有任务合并后，最终整分支 `code-review` 发现的问题按以下方式集中处理：

1. **统一派发一个修复者**：把所有严重和重要发现合并为一份清单，派一个高能力等级的修复子代理集中处理，避免每个问题单独派发造成上下文与测试重复开销。
2. **聚焦复审**：修复完成后只做一次限定范围的针对性复审。
3. **收敛决策**：复审后仍有轻微争议的非关键问题，直接由协调者作出代行决策并记录到进度记录中，不再开展第二轮循环。
