# 修复循环

`implement-spec` 的按需参考：任务评审触发修复循环时读取。

先分出两类发现：

- **次要**发现直接写入进度记录（`任务 NN：次要（延后）：<一句话>`），不进入循环。最终评审会看到这份清单。
- 与任务原文要求冲突的发现，由你作出代行决策（以规格为最终依据），写入进度记录，再决定是否修复。

其余发现进入循环。一轮包括一次修复派发和一次限定范围的复审。**每项任务最多 3 轮：**

- **第 1、2 轮**：恢复原来的实现者，原样发送未解决的发现。运行环境不支持向仍在运行的子代理发消息时，派一个新实现者，并提供任务指针、报告文件和发现清单。
- **第 3 轮**：派一个**新的**实现者，能力等级至少高一档，并告诉它：“之前的实现者尝试了 2 次，现在由你负责。先读报告文件，了解之前试过什么。”两轮恢复仍未解决，通常说明原实现者看不到自己的问题。

每一轮的顺序：

1. 实现者修复问题，重新运行覆盖改动的测试，把修复报告追加到同一个报告文件。
2. 确认修复报告包含覆盖测试、运行的命令和输出之后，再派发复审。
3. 复审只看 `上一次评审看到的头部..当前头部` 的 diff（用 `review-package.mjs` 生成，BASE 是上一次评审看到的头部），逐条判定**已解决**或**未解决**，并只在修复 diff 内标记新引入的问题。
4. 复审发现的范围外问题记为延后的次要项，不延长循环。

每轮结束后写入进度记录：`任务 NN：修复第 R/3 轮（已解决 X，未解决 Y：<一句话>；提交 <a7>..<b7>）`

## 达到重试上限

第 3 轮复审后仍有未解决的发现时，停止派发，由你逐条作出代行决策：

- **评审者判断错误，或存在争议**：搁置，记录为 `任务 NN：搁置：<发现> | 决策：<代码为何保持现状>`
- **问题真实，但下游没有内容依赖它**：同样搁置，决策中写明“真实，延后”
- **问题真实，且下游依赖它**（后续任务依赖它，或它暴露了任务缺陷）：决定能让下游继续推进的最小改动，写入进度记录，并带入下一项相关任务的派发。只有缺陷导致任何推进方式都只能靠猜测时才停下

只在达到重试上限时对评审发现作代行决策。更早作决策，只是换了个名义提前下结论。每个决策都写成一条进度记录。
