# 进度记录格式

进度记录是 `implement-spec` 写在磁盘上的执行状态。对话记忆无法可靠地保留到上下文压缩之后；协调者一旦丢失进度，就会把已完成的任务整批重新派发，这是代价最高的失败。恢复进度时，以进度记录和 `git log` 为依据。

## 位置

`<仓库根>/.dev-skills/implement-spec/<规格-slug>/`

这个目录只属于一份规格：进度记录、实现者报告和评审材料都放在这里。不读写其他规格的目录。确保 `.dev-skills/` 已加入 `.gitignore`。

`git clean -fdx` 会删除这个目录。发生这种情况时，根据 `git log` 和追踪器上的任务状态恢复。

## 文件：`ledger.md`

第一行标明所属规格，其余内容按时间顺序追加，不修改已有记录。

```markdown
# implement-spec 进度记录 · 规格：<规格链接或路径>

集成分支：<分支名> · 起点：<sha7> · PR：<链接或“仅本地”>

## 预检

| 对象              | 检查内容                                                                     | 结果           | 决策                                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------- |
| 任务 02 ↔ 任务 04 | 02 提供 `parseOrder(raw): Order`，04 依赖 `parseOrder(input): Order \| null` | 返回类型不一致 | 决策：以规格“非法输入返回错误结果”为准，统一为 `Order \| null` \| 理由：规格用户故事 7 \| 如果错了：04 需修改一处调用 |
| 任务 03           | 验收标准与“要构建什么”是否一致                                               | 一致           | 无                                                                                                                    |

## 进度

- 任务 01：派发（BASE a1b2c3d，模型：低成本档，工作树 .worktrees/ticket-01）
- 任务 01：完成（提交 a1b2c3d..d4e5f6a，评审通过）
- 任务 02：修复第 1/3 轮（已解决 2，未解决 0；提交 d4e5f6a..b7c8d9e）
- 任务 02：次要（延后）：错误信息未包含订单号
- 任务 02：完成（提交 d4e5f6a..b7c8d9e，评审通过）
- 任务 03、07、09：合批派发（BASE d4e5f6a，模型：低成本档，工作树 .worktrees/ticket-03-batch）| 决策：三项都是给接口响应添加 `requestId` 字段，合成一个批次 | 理由：同类小改动 | 如果错了：拆回单项评审
- 任务 05：搁置：评审认为应缓存汇率 | 决策：规格要求实时汇率，保持现状 | 如果错了：高并发下多一次外部调用
```

## 恢复规则

- 有 `任务 NN：完成` 记录的任务已经完成，不再派发。
- 某项任务的最后一条记录是修复轮次时，说明它处于修复循环中途：从下一轮继续。
- 最后一条记录是“派发”且没有后续时：检查该任务分支的提交和报告文件，再决定继续评审还是重新派发。
- 进度记录与你的记忆不一致时，以进度记录和 `git log` 为准。
