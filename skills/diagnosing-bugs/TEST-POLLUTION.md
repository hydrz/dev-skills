# 定位污染环境的测试

测试之间共享了不该共享的东西（全局变量、单例、环境变量、数据库记录、磁盘文件、mock 没有还原），就会出现两类症状：

- **测试跑完后多出不该有的文件或目录**，例如子目录里冒出一个 `.git`、仓库根目录多了临时文件。
- **某个测试单独运行通过，和其他测试一起运行就失败**，而且失败与否取决于运行顺序。

两类问题都由某个*别的*测试造成，读失败测试本身的代码找不到原因。先用 [scripts/find-polluter.mjs](scripts/find-polluter.mjs) 找出是哪个测试文件，再对那个文件按阶段 3 提出假设。脚本只依赖 Node.js 标准库，Windows 上也能直接运行。

## 准备

1. **测试命令。** 用 `--cmd` 传入，`{files}` 会替换为本次要运行的测试文件。命令要让测试**按给定顺序串行运行**，否则顺序相关的问题无法复现：

   | 运行器 | 命令示例                                                   |
   | ------ | ---------------------------------------------------------- |
   | Vitest | `npx vitest run --no-file-parallelism {files}`             |
   | Jest   | `npx jest --runInBand {files}`                             |
   | pytest | `pytest -p no:randomly {files}`（装了 pytest-randomly 时） |

   运行器会自行调整文件顺序时（例如按上次耗时排序），先关闭这个行为。运行器默认把每个文件隔离在单独的进程或模块环境中时，内存中的全局状态不会跨文件传递，这时污染通常来自磁盘、数据库或环境变量。

2. **候选测试文件。** 按失败时的实际顺序列出。数量多时写入一个文件，每行一个，用 `--list` 传入，避免超出 Windows 命令行长度限制，例如 `git ls-files "*.test.ts" > candidates.txt`。Windows PowerShell 写出的 UTF-16 文件也能读取。

## 多出文件：`--creates`

```bash
node <diagnosing-bugs 目录>/scripts/find-polluter.mjs --cmd "npx vitest run {files}" --creates packages/app/.git --list candidates.txt
```

脚本逐个运行候选文件，报告第一个运行后让该路径出现的文件。运行前路径已经存在时，脚本拒绝执行：先删除它。

## 一起运行才失败：`--victim`

```bash
node <diagnosing-bugs 目录>/scripts/find-polluter.mjs --cmd "npx jest --runInBand {files}" --victim src/order.test.ts --list candidates.txt
```

脚本先确认两个前提，再二分查找：

1. 受影响的测试单独运行通过。单独运行也失败时，问题不是其他测试造成的，回到普通的诊断流程。
2. 全部候选文件在前、受影响的测试在后，按顺序运行时失败。不失败说明无法复现，检查命令是否串行、顺序是否与失败时一致。

之后每次把嫌疑文件分成两半，分别放在受影响的测试前面运行，保留会让它失败的那一半。候选文件有 N 个时，除了确认前提的 2 轮，最多再运行约 2 × log₂N 轮。

**无法定位到单个文件时**（退出码 1），说明污染需要多个测试共同作用：脚本列出剩余的嫌疑文件，在这个较小的范围内手动组合排查。

## 找到之后

脚本只回答“是哪个文件”。接着：

- 把“先运行污染源、再运行受影响的测试”作为阶段 1 的反馈回路，它快速、确定，而且会变红。
- 在污染源中找出没有清理的共享状态，在**源头**修复：让测试自己创建并清理资源，还原 mock 和环境变量，而不是在受影响的测试里加防御来掩盖它。
- 回归测试就是这对文件按顺序一起运行时通过。
