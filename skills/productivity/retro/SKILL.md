# 会话复盘

根据会话记录和仓库中的实际改动，找出可以让下一次工作更可靠、更省上下文的改进。复盘针对已经结束的工作；仍在实现或排错时，先完成当前任务。

## 改进层级

同一个问题只放在最靠前、能够可靠拦住它的层级：

1. 编译器、类型检查、测试或 lint 等自动检查
2. 代码评审规则
3. 按需读取的参考文档或导航指针
4. 每轮都会加载的 `AGENTS.md` 或 `CLAUDE.md`

能自动检查的规则不重复写进 agent 指令。只有未来任务普遍需要、又无法从环境中直接查出的信息，才进入顶层指令。

## 过程

### 1. 收集证据

读取用户指定的会话记录；没有单独记录时，使用当前对话、git diff、测试输出和相关 issue。列出观察到的事实：错误发生在哪里、为什么会绕路、哪些工具调用或文件读取重复出现、哪条现有规则没有起作用。

不要用通用最佳实践填充没有证据的空白。

**完成条件：** 每个候选问题都能指向一次具体事件或一份具体产物。

### 2. 找到最早拦截点

对每个问题判断：

- 能否由类型系统、测试、lint、格式化器或 CI 直接检查？
- 是否只在评审阶段需要完整编码规范？
- agent 是否因为缺少一个路径、命令或权威文档入口而反复搜索？
- 顶层 agent 指令中是否有无效、重复、过时或可以下沉的内容？
- 是否读取了过大的文件或重复调用了昂贵工具？

实现 agent 的上下文通常更紧张，只给它完成任务所需的导航；完整标准优先交给评审和自动检查。

**完成条件：** 每个问题都有唯一的建议落点，并说明为何该层级能够比后面的层级更早发现问题。

### 3. 给出改进清单

按影响排序，每项写清：证据、建议修改的位置、预期拦截的失败、成本与副作用。把“删除无效指令”和“缩短重复上下文”视为有效改进，不以新增规则数量衡量复盘质量。

如果用户只要求复盘，到这里停止。用户明确要求实施时，再修改相应检查、评审文档或指令，并运行与修改相匹配的验证。

**完成条件：** 用户可以逐项接受或拒绝建议；已实施的项目都有当前状态下的验证证据。
