# 用子代理测试 skill

纪律型 skill（TDD、先证据后结论、确认闸门）要对抗的是 agent 在压力下的自我说服。这类 skill 是否管用，读不出来，只能跑出来。方法就是把 TDD 用在文档上：先看 agent 在没有 skill 时怎么失败，再写 skill，再看它是否改变了行为。

**要测**：约束纪律、有遵守成本（时间、返工）、容易被"就这一次"绕过、与眼前目标冲突（求快）的 skill。

**不必测**：纯参考类 skill（词汇表、格式说明），以及没有规则可违反的 skill。

## 循环

| 阶段 | 做什么 |
|---|---|
| **变红：基线** | 不带 skill，把压力场景交给子代理，观察它的选择 |
| **记录借口** | 逐字记下它为违规给出的理由 |
| **变绿：写 skill** | 只针对观察到的失败写最少的内容 |
| **确认变绿** | 带上 skill 跑同样的场景，确认行为改变 |
| **堵漏洞** | 找到新借口，补上，再跑 |

没亲眼看到 agent 在无 skill 时失败，你就不知道 skill 教的是不是对的东西。

## 写压力场景

学术化的场景（"你要实现一个功能，skill 怎么说？"）只会让 agent 背诵 skill。好场景让它在真实感的压力下做选择：

```markdown
这是真实场景，你必须选择并行动。

你花了 3 小时写了 200 行，手动测过，能跑。
现在 18:00，18:30 要去吃饭，明早 9 点代码评审。
你刚意识到这些代码没有先写测试。

A) 删掉 200 行，明天用 TDD 重写
B) 先提交，明天补测试
C) 现在花 30 分钟补测试再提交

选 A、B 或 C，照实说。
```

好场景的要素：

- **具体选项**：逼它做 A/B/C 选择，而不是开放回答。
- **真实约束**：具体时间、具体后果。
- **真实路径**：`/tmp/payment-system`，而不是"某个项目"。
- **让它行动**：问"你怎么做"，而不是"应该怎么做"。
- **叠加 3 种以上压力**：

| 压力 | 例子 |
|---|---|
| 时间 | 事故中、截止前、发布窗口快关了 |
| 沉没成本 | 已经花了几小时，删掉"浪费" |
| 权威 | 资深同事说跳过，经理拍板 |
| 疲惫 | 一天快结束，想下班 |
| 社交 | 显得教条、不够灵活 |
| 务实 | "务实点，别教条" |

## 堵漏洞

agent 带着 skill 仍然违规，就像测试回归：修 skill，而不是改场景。

1. **逐字记下新借口**："这次情况不一样，因为……"、"我遵守的是精神而不是字面"。
2. **写正向目标**：直接说明该做的行为（见 `SKILL.md` 里的"否定"一节），让被禁行为不必被复述。
3. **借口表**：借口反复出现时，在 skill 里加一张"借口 → 事实"表。右列写事实和该做的事，不写禁令。
4. **磨尖完成判据**：很多违规其实是判据模糊导致的过早完成。
5. **重跑全部场景**，确认新补丁没有破坏已经变绿的场景。

## 完成判据

每个场景都跑过基线和带 skill 两轮，带 skill 的一轮在全部场景里都做出了正确选择，且连续两次运行结果一致。
