# 代码坏味道基线

**规范**维度始终附带这组固定的 Fowler 代码坏味道（《重构》第 3 章）。即使仓库没有任何成文规范，它也适用。TDD 的实现循环不做重构，重构建议在评审阶段通过这份基线提出。

使用基线时遵循两条规则：

- **仓库规范优先。** 成文的仓库规范总是优先；仓库明确认可、但基线会标记的写法，不报告。
- **始终是判断性建议。** 每个坏味道都是带标签的启发式判断（例如“可能是依恋情结”），不是硬性违规。工具已经强制检查的内容不报告。

每个坏味道都写成“是什么，怎么修”，逐一对照 diff 检查：

- **神秘命名**：函数、变量或类型的名称无法说明它做什么或存什么。修复：重命名；想不出准确的名称，说明设计本身不清楚。
- **重复代码**：同样的逻辑结构出现在改动的多个 hunk 或文件中。修复：提取共同结构，在两处调用。
- **依恋情结**：一个方法访问另一个对象的数据，比访问自身数据还多。修复：把方法移到它所依赖的数据所在的位置。
- **数据泥团**：同样几个字段或参数总是一起出现，说明缺少一个类型。修复：封装成一个类型并传递它。
- **基本类型偏执**：用基本类型或字符串代替一个应该拥有独立类型的领域概念。修复：为这个概念定义一个小类型。
- **重复的 switch**：针对同一类型的相同 `switch` 或 `if` 级联在改动中反复出现。修复：用多态替代，或让多处共用一张映射表。
- **霰弹式修改**：一个逻辑改动迫使 diff 在多个文件中分散修改。修复：把一起变化的代码集中到一个模块。
- **发散式变化**：一个文件或模块因为几个互不相关的原因被修改。修复：拆分，让每个模块只因一个原因变化。
- **夸夸其谈通用性**：为规格中并不存在的需求添加抽象、参数或钩子。修复：删除或内联，等真实需求出现再加。
- **过长的消息链**：`a.b().c().d()` 这类调用方不应依赖的长链导航。修复：在第一个对象上提供一个方法，隐藏这段遍历。
- **中间人**：一个类或函数几乎只做转发。修复：去掉它，直接调用真正的目标。
- **被拒绝的遗赠**：子类或实现类忽略或覆盖了继承来的大部分内容。修复：放弃继承，改用组合。
