# 分支收尾

**顺序：** 验证测试 → 识别环境 → 确认基线分支 → 提供选项 → 执行选择 → 清理。

是否集成、如何集成由用户决定。你负责把选项说明清楚，然后等待用户选择。

## 1. 验证测试

对即将集成的代码运行项目的完整测试套件，并阅读输出。调用 Skill 工具，参数为 `verifying-completion`。

**测试失败**：报告失败并停止。测试通过之后才提供选项：

```
测试失败（<N> 个）。收尾之前必须修复：

<失败输出>
```

**测试通过**：继续。

## 2. 识别环境

```bash
GIT_DIR=$(git rev-parse --path-format=absolute --git-dir)
GIT_COMMON=$(git rev-parse --path-format=absolute --git-common-dir)
# 趁仍在工作区内时记录；第 5 步会切换目录，第 6 步清理时还要使用
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

两个路径都让 git 直接输出绝对路径（需要 git 2.31 及以上）。用 `cd` 加 `pwd -P` 自行转换时，Windows 的 Git Bash 可能把同一个目录显示成不同的挂载路径，在子目录中运行会把普通仓库误判为工作树。

| 状态                                   | 选项                      | 清理                            |
| -------------------------------------- | ------------------------- | ------------------------------- |
| `GIT_DIR == GIT_COMMON`（普通仓库）    | 标准的 3 个选项           | 无工作树需要清理                |
| `GIT_DIR != GIT_COMMON`，位于具名分支  | 标准的 3 个选项           | 根据工作树来源判断（见第 6 步） |
| `GIT_DIR != GIT_COMMON`，detached HEAD | 精简的 2 个选项（不合并） | 由外部管理，保持原样            |

## 3. 确认基线分支

基线分支是这项工作分出来的分支，通常写在规格、开发任务、对话或分支的 upstream 中。不确定时询问用户：“这个分支是从 <你的最佳猜测> 分出来的，对吗？”合并之前必须确认，因为合并到错误的基线代价很高。

## 4. 提供选项

**普通仓库或位于具名分支的工作树，按原样提供以下 3 个选项：**

```
实现已完成。你想怎么处理？

1. 在本地合并回 <基线分支>
2. 推送并创建 Pull Request
3. 保持分支原样（我稍后处理）

选哪个？
```

**detached HEAD，按原样提供以下 2 个选项：**

```
实现已完成。当前是 detached HEAD（外部管理的工作区）。

1. 推送为新分支并创建 Pull Request
2. 保持原样（我稍后处理）

选哪个？
```

只提供以上选项。只有用户明确要求时，才进入丢弃工作的流程（见下文）。

## 5. 执行选择

### 选项 1：本地合并

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

git checkout <基线分支>
git pull
git merge <功能分支>

<测试命令>
```

合并后测试失败时：停止，保留工作树和分支原样，开始调查。此时还没有推送，合并只发生在本地，可以恢复。

合并后测试通过时：清理工作树（第 6 步），然后删除分支：

```bash
git branch -d <功能分支>
```

### 选项 2：推送并创建 PR

```bash
git push -u origin <功能分支>
# detached HEAD 时，在远程仓库创建新分支：
# git push origin HEAD:refs/heads/<新分支>
```

然后使用托管平台的工具（有 CLI 时用 CLI，否则用推送时打印的创建链接），针对 <基线分支> 创建 PR 或 MR。遵循仓库的 PR 模板和约定，并把链接报告给用户。

保留工作树：用户需要在其中根据 PR 反馈继续修改。

### 选项 3：保持原样

报告：“保留分支 <名称>。工作树位于 <路径>。”

### 用户要求丢弃工作时

只有用户明确要求丢弃时才进入这个流程。先确认：

```
这将永久删除：
- 分支 <名称>
- 全部提交：<提交列表>
- 工作树 <路径>

输入 discard 确认。
```

等待用户输入这个确切的词。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

清理工作树（第 6 步），再强制删除分支：

```bash
git branch -D <功能分支>
```

## 6. 清理工作区

**只在选项 1 和已确认的丢弃流程中执行。** 选项 2 和 3 始终保留工作树。执行到这一步时，已经切换到主仓库根目录（移除工作树必须在工作树之外执行），并使用第 2 步切换目录之前记录的值。

**`GIT_DIR == GIT_COMMON`：** 普通仓库，无工作树需要清理。完成。

**`WORKTREE_PATH` 位于 `.worktrees/` 或 `worktrees/` 下：** 这是本流程创建的工作树，由本流程负责清理：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune
```

**移除被拒绝**（`contains modified or untracked files`）：说明工作树中有其他地方都没有的文件（未提交的计划、笔记、草稿）。先查看有哪些文件，展示给用户，然后询问：

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
工作树移除被拒绝，以下文件从未提交：

<文件列表>

1. 先提交到 <分支> 再清理
2. 移到 <主仓库根目录>
3. 删除（不可恢复）

选哪个？
```

执行用户的选择，然后再移除工作树。只有用户选择 3 之后，才使用 `--force`。

**其他情况：** 工作区由宿主环境管理，保持原样。平台提供退出工作区的工具时，使用该工具。

## 速查

| 选项                 | 合并 | 推送 | 保留工作树 | 删除分支   |
| -------------------- | ---- | ---- | ---------- | ---------- |
| 1. 本地合并          | 是   | 否   | 否         | 是         |
| 2. 创建 PR           | 否   | 是   | 是         | 否         |
| 3. 保持原样          | 否   | 否   | 是         | 否         |
| 丢弃（仅限明确要求） | 否   | 否   | 否         | 是（强制） |

## 常见借口与对应事实

| 借口                                 | 事实                                                                        |
| ------------------------------------ | --------------------------------------------------------------------------- |
| “这个会话早些时候测试过了”           | 对即将集成的代码重新运行。一次通过只能证明当时运行的那份代码。              |
| “用户显然想合并”                     | 是否集成由用户决定。提供选项，等待选择。                                    |
| “‘嗯，删了吧’算确认”                 | 只有输入 `discard` 才授权删除。                                             |
| “PR 已经创建，工作树没用了”          | PR 反馈需要在该工作树中修改，工作合并前一直保留。                           |
| “另一个工作树看起来废弃了，顺手清掉” | 只清理 `.worktrees/` 或 `worktrees/` 下的工作树，其他工作树由宿主环境管理。 |
| “合并后失败大概是偶发的”             | 合并结果测试失败就停止，保留分支和工作树原样，先调查。                      |
| “推送被拒绝，强制推送就好”           | 推送被拒绝说明远程分支有变化。先调查；只有用户明确要求时才强制推送。        |
