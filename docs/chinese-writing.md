# 中文写作规范

本规范适用于仓库中的 README、skill、模板和说明文档。目标是让熟悉常见工程术语的中文开发者能够快速理解，同时保持 agent 执行指令的准确性。

## 1. 读者与语气

- 默认读者熟悉 Git、PR、API、TDD 等基础工程概念，但不了解本项目的内部术语和上游背景。
- 使用专业、直接、协作的语气。强约束应明确写出条件和结果，不依赖“无情”“拒绝”“裁决”等情绪或身份词强化。
- README 可以保留适量个性；skill 的执行步骤优先使用可以直接观察和验证的动作。

## 2. 中英文选择

保留中文开发者普遍使用且翻译后反而不自然的技术词：

- 普通英文技术词使用小写：agent、skill、issue、diff、mock、schema。在讨论词本身时可以使用行内代码。
- 固定缩写使用大写：PR、API、TDD、ADR、CI。
- 产品名、协议名和编程语言遵循官方写法。
- 命令、路径、文件名、字段、标签和代码标识使用行内代码。

中文句子负责解释。不要为了显得专业，把已经有自然中文表达的普通动作换成英文。

## 3. 术语选择

- `CONTEXT.md` 只约束项目特有概念，不充当通用工程词典。
- 组件、服务、模块、API、签名、边界等词按各自原义使用。
- 抽象工作项称“任务”或“开发任务”；追踪器中的具体项目称 `issue`；运维、支持和审批场景才称“工单”。
- 不要求英文概念在所有场景使用同一个中文译词。先判断句子要表达的行为，再选择自然说法。

常见场景：

| 英文概念              | 方案讨论               | 任务执行                   |
| --------------------- | ---------------------- | -------------------------- |
| frontier              | 当前待确认项           | 当前可执行任务、就绪任务   |
| blocking dependency   | 前置问题               | 前置依赖、任务依赖关系     |
| input/output relation | 依赖的信息、形成的结论 | 依赖 / 提供，或输入 / 输出 |

## 4. 标点与排版

- 中文引语使用全角引号“”。
- 中文列举使用顿号、逗号或 Markdown 列表，不使用带空格的斜杠代替顿号。
- 中文与行内代码之间不强制插入空格；同一文档保持一致。
- 箭头只用于流程和状态转换。普通说明写成完整句子。
- 英文括号只用于代码或固定英文内容；中文解释使用全角括号。

## 5. description 的写法

仅用户触发的 skill description 应优先说明：

1. 用户在什么场景运行它；
2. 它产生什么结果；
3. 它与名称或用途最接近的 skill 有什么区别。

可自动触发的 skill description 还应包含中英文触发词，让 agent 能在正确场景发现它。触发范围应足够窄，不把普通任务误路由到成本较高的完整流程。

示例：

```yaml
description: 在当前会话实现一项或少量已明确的开发任务。整份规格需要由多个子代理并行交付时使用 implement-spec。
```

## 6. 操作步骤的句式

一条规则优先按以下顺序表达：

1. 条件：什么时候适用；
2. 动作：agent 具体做什么；
3. 结果：产生什么可检查的状态；
4. 例外：什么情况下不这样做。

不要把多个条件、动作和例外压进一个长句。Markdown 源码行长不是硬指标；判断标准是读者是否需要反复回看才能执行。

## 7. 隐喻

- 每一段最多让一个隐喻承担解释作用。
- 隐喻首次出现时给出直白定义。
- 命令名可以保留品牌隐喻，执行步骤必须在不了解隐喻时仍然可操作。
- 对话、任务调度和架构设计使用各自自然的词，不为了统一而共享一套隐喻。

## 8. 上游内容的本地化

修改上游内容时，先列出原文约束的行为：触发条件、必须动作、禁止越过的边界、错误处理和完成条件。中文可以重新分段、换词和调整顺序，但这些行为必须保留。

不要逐句翻译后再润色。先理解规则，再用中文重新表达，最后逐项核对行为语义。

## 9. 正反例

| 不推荐                   | 推荐                                 |
| ------------------------ | ------------------------------------ |
| 被无情拷问一个计划或设计 | 逐轮澄清并压力测试一个计划或设计     |
| 按设计树逐轮处理前沿     | 每轮询问当前能够确认的全部决策       |
| 每张声明自己的阻塞边     | 每项任务明确列出前置依赖             |
| 台账扛过上下文压缩       | 将进度写入文件，以便上下文压缩后恢复 |
| 模型自主伸手去用它       | 模型在合适场景主动调用它             |
| 把迷雾毕业成新工单       | 将已经明确的问题拆成新的开发任务     |

## 10. 修改检查清单

- 普通工程词是否被错误合并成项目术语？
- 相邻 skill 的边界是否无需打开正文就能理解？
- 每个长句是否只表达一个主要判断？
- 是否可以把隐喻替换为可观察动作？
- 中英文大小写、行内代码和中文标点是否一致？
- 重写前后的触发条件、行为约束和完成条件是否一致？
