# 功能清单

功能清单列出一项工作要交付的全部功能项：页面、功能、后台任务和第三方对接。规格、开发任务、实现和验收都用功能项编号引用它。清单里记录了每个功能项属于哪个发布批次、由哪些任务实现，便于在复杂或多端项目中清晰追踪范围。

性能、无障碍、多语言、可观测性这类非功能需求不写在清单里，写在规格的“非功能需求”一节，编号为 `N-01` 的形式。

## 什么时候需要

- **大型或多端工作**（通过 `/wayfinder` 规划，或涉及多端协同与复杂前端交互）：建立独立的清单文件。
- **小功能或单模块改动**（一个切片或一份规格就能写完）：在规格的“功能项”一节使用同样的表头，不单独建文件。

## 位置

- 清单：`docs/features/<工作-slug>.md`
- 设计资料（设计稿导出、选定原型变体的截图）：`docs/features/design/<工作-slug>/`，文件名以功能项编号开头，例如 `F-042-锁定.png`

多上下文仓库放在对应上下文的 `docs/features/` 下，跨上下文的工作放在根目录的 `docs/features/`。

## 文件结构

```markdown
# <工作名称> 功能清单

目标：<一两行，与地图或规格的目标一致>

当前批次：MVP

批次顺序：MVP、V1.1、V1.2

## 功能项

| 编号  | 类型     | 名称         | 角色 | 端               | 批次 | 需覆盖状态                                         | 设计依据                               | 任务     | 结论   |
| ----- | -------- | ------------ | ---- | ---------------- | ---- | -------------------------------------------------- | -------------------------------------- | -------- | ------ |
| F-042 | 核心页面 | 剧集解锁面板 | 观众 | iOS、Android、H5 | MVP  | 默认、余额不足、支付中、失败、已解锁、离线（V1.1） | [设计稿](design/actoya/F-042-默认.png) | T09、T11 | 已确定 |

## 不做

- F-050 <名称>：<原因>。确认人：<用户>，<日期>

## 批次调整记录

- F-042 离线状态：MVP → V1.1。原因：<原因>。确认人：<用户>，<日期>
```

整项工作只发布一次时，只用一个批次，例如 `V1`。

## 字段

- **当前批次**：正在规划、实现和验收的批次。批次顺序写在它下面，当前批次全部完成后，由用户确认切换到下一个批次。
- **编号**：`F-` 加三位数字。创建后不再修改，也不复用。
- **类型**：`核心页面`、`普通页面`、`功能`、`后台任务`、`第三方对接`。核心页面指首屏、转化路径和核心体验上的页面，其余页面都是普通页面。
- **名称**：使用 `CONTEXT.md` 中的词。
- **角色、端**：用到这个功能项的全部角色和客户端。同一个页面在不同端差别很大时，拆成多个功能项。
- **批次**：这个功能项在哪个批次交付。
- **需覆盖状态**：核心流程与关键状态（如默认、异常分支、空数据等）。聚焦高频路径与关键边界，避免形式主义罗列。
  - 某个状态在更晚的批次交付时，在状态后面括注批次，例如 `离线（V1.1）`。没有括注的状态跟随功能项的批次。
- **设计依据**：写成链接。
  - 核心页面：设计稿、选定原型变体的截图或分支链接，或视觉规格中的具体章节。
  - 普通页面：可以写一条决定，“按设计系统实现，参照 <具体页面或功能项编号>”。只写“按设计系统实现”不算设计依据。
  - 功能、后台任务、第三方对接：链接到对应的行为决策（规格章节、ADR、决策项或逻辑原型）。
- **任务**：由 `/to-tickets` 回填对应任务编号或链接。需要运行严格覆盖检查时，可括注覆盖的状态（例如 `T09（默认、已解锁）`）。
- **结论**：`待定`、`已确定` 或 `不做`。

## 规则

- **增加范围时直接改。** 新增功能项或补充交互要求时，直接写进清单，并在对应规格或进度记录中说明原因。
- **缩减范围必须由用户确认。** 以下改动都要先得到用户明确同意：
  - 把功能项改为“不做”：同意后写进“不做”一节。
  - 把功能项或状态移到更晚的批次：同意后写进“批次调整记录”。它仍然留在清单中，到对应批次时照常覆盖。
  - 删掉某个状态，或放宽设计依据的要求：同意后写进“不做”一节。

  每条记录都写明确认人和日期。agent 不能用代行决策缩减范围。

- **只核对当前批次。** 规格、任务覆盖和完成验证只核对当前批次的功能项，更晚批次的内容不算缺口。更晚批次的功能项可以暂时保持“待定”，在切换到该批次之前确定。
- **改为“已确定”的条件。** 关键交互要求已经明确，设计依据符合上面的要求。
- **拆分参考。** 一份规格负责的功能项超过 25 个左右时，考虑拆分规格；一项任务覆盖的功能项超过 5 个时，考虑拆分任务。

## 覆盖检查

项目需要严格核验覆盖矩阵时，可运行：

```bash
node scripts/check-feature-coverage.mjs <功能清单> [规格 ...]
```

它检查：

- 功能项表的列、编号、类型、结论是否合法；
- 当前批次中是否还有“待定”的功能项；
- 当前批次页面类功能项的设计依据是否符合要求；
- 任务列是否覆盖了当前批次要求的所有状态（开启严格状态检查时）；
- 规格中每条非功能需求是否有目标值、验证方式和任务覆盖。

发现问题时以退出码 1 结束。项目需要时，可以把这条命令加进 CI。
