# 中文本地化审查报告

状态：已批准，第一、二阶段已实施

审查范围：仓库中的 Markdown 文档、所有 `SKILL.md` frontmatter，以及插件的用户可见元数据

本报告只提出修改方案，不修改现有文档或 skill 行为。

## 1. 结论

这个项目已经完整使用中文表达，但目前更像“英文原作概念的中文映射”，还不像中国开发者自然形成的工程文档。主要摩擦不是英文技术词太多，而是三类语言叠加：

1. 开发者熟悉的英文词，例如 `agent`、`skill`、`issue`、PR、TDD；
2. 项目内部定义的词，例如“前沿”“阻塞边”“确认闸门”；
3. 从英文直译过来的隐喻和动作，例如“台账扛过压缩”“毕业成新工单”“自主伸手去用”。

读者需要先学习项目自己的语言，才能判断一个 skill 是否适合当前场景。最先需要改善的是入口体验和术语规则，而不是将英文词全部翻译成中文。

建议按两个阶段实施：

- 第一阶段处理 README、术语表、分类说明、调用机制说明、插件描述和所有 frontmatter，让用户能找到、区分并正确触发 skill。
- 第二阶段逐个清理 skill 正文和配套参考文件中的翻译腔、过密隐喻、长句与不自然模板字段。

命令名在这两个阶段都保持不变。若后续仍有明显误选，再单独评估重命名和兼容策略。

## 2. 已确定的本地化原则

### 2.1 目标读者

主要读者是中国大陆开发者。他们熟悉 Git、PR、API、TDD 等常见工程概念，也可能已经使用过 Claude Code 或 Codex，但不应被要求先了解本项目上游作者的术语体系。

### 2.2 用词原则

- 保留开发者已经熟悉的英文技术词，不追求全中文。
- 中文句子承担解释，英文词只承担确有共识的技术含义。
- 项目特有概念可以进入术语表；通用工程词按原义使用，不强制合并。
- 同一个英文词可以根据场景采用不同中文表达，不要求逐词对应。
- 命令、字段名、文件名和代码标识使用行内代码格式。

### 2.3 语气原则

- README 可以保留适量个性和一个主要隐喻。
- skill 正文保持专业、直接、协作，优先描述可观察的动作。
- 强约束仍然明确表达，但不使用敌意、司法化或人格化措辞强化它。
- 每段只承担一个主要判断；复杂规则优先拆成短段落、列表或表格。

### 2.4 上游保真原则

保留上游的行为约束、决策边界和设计意图；允许重组句子、替换隐喻，并根据中文语境重新命名概念。需要同步的是行为语义，而不是英文句子的表面结构。

## 3. 高优先级问题

### P0-1：“工单”不适合作为所有开发任务的统称

证据：

- `CONTEXT.md:86-94` 将 `ticket` 统一译为“工单”，并明确排除“任务”。
- `README.md:82-102` 使用“曳光弹工单”“工单图前沿”等表达主流程。
- `skills/to-tickets/SKILL.md` 和 `skills/implement-spec/SKILL.md` 将这一选择扩散到任务拆分、依赖和执行流程。

问题：中文工程语境中的“工单”通常指支持、运维、审批或服务请求。需求拆解后的工作项更常被称为“任务”“开发任务”或直接称 `issue`。禁止使用“任务”还会与 Codex 等工具的用户界面产生冲突。

建议：

- 抽象工作项称“任务”或“开发任务”。
- 已发布到 GitHub、GitLab 等追踪器的具体项目称 `issue`。
- 只有运维、客服或审批场景继续使用“工单”。
- `/to-tickets` 的命令名暂不改变，对外显示名使用“拆分开发任务”。

### P0-2：“用户调用 / 模型调用”没有准确描述分类轴

证据：

- `CONTEXT.md:13-19` 定义“用户调用”和“模型调用”。
- `docs/invocation.md:1-13` 说明两类 skill 的实际差异是“谁能触发”。
- `README.md:89-93`、`skills/README.md` 重复使用现有分类名。

问题：两类 skill 最终都由模型加载并执行。现有名称容易被理解为执行者不同，甚至被误解为 API 调用方式不同。

建议统一为：

- **仅用户触发**：只有用户显式输入名称才触发；
- **可自动触发**：模型可以按场景主动触发，用户也可以显式触发。

技术说明中可以在首次出现时括注 `user-invoked` 和 `model-invoked`。

### P0-3：“拷问”在中文中的攻击性高于 `grill`

证据：

- `README.md:41` 将对齐方法定义为“拷问”。
- `skills/grill-me/SKILL.md:3` 和 `skills/grill-with-docs/SKILL.md:3` 使用“无情拷问”。
- `skills/grilling/SKILL.md` 高频使用“拷问”“设计树”“前沿”。

问题：“拷问”容易让协作流程显得敌意、表演化，也掩盖了实际行为：分轮提出决策问题，检验假设，直到获得实施确认。

建议：

- 保留 `/grill-me`、`/grill-with-docs` 和 `grilling` 命令名。
- 对外中文显示名使用“方案追问”。
- 描述使用“逐轮澄清并压力测试方案”。
- 正文根据具体动作写“追问”“确认”“澄清”“检验假设”，不再用“无情”修饰。

### P0-4：同一译词被强行用于不同场景

证据：

- `CONTEXT.md:37-44` 用“设计树、前沿、确认闸门”描述对话决策。
- `CONTEXT.md:86-103` 又用“工单、阻塞边、前沿、台账、裁决”描述任务调度。
- `README.md:99-104` 在面向新用户的 skill 摘要中直接使用这些内部词。

问题：`frontier` 在对话中表示现在可以询问的问题，在任务图中表示依赖已经满足的任务。用同一个“前沿”贯穿两种场景，看似统一，实际增加了解码成本。

建议按场景表达：

| 原表达           | 推荐表达                 | 使用说明                         |
| ---------------- | ------------------------ | -------------------------------- |
| 设计树           | 决策关系、待确认事项     | 只有确实呈树状时才称“决策树”     |
| 前沿（方案讨论） | 当前待确认项             | 描述这一轮现在能问的问题         |
| 前沿（任务图）   | 当前可执行任务、就绪任务 | 描述依赖已满足的任务             |
| 阻塞边           | 前置依赖、任务依赖关系   | 图论说明中才使用“依赖边”         |
| 确认闸门         | 实施前确认               | 直接描述必须发生的动作           |
| 消费 / 产出      | 依赖 / 提供              | 数据接口场景使用“输入 / 输出”    |
| 曳光弹工单       | 端到端最小闭环任务       | 首次可括注“曳光弹”说明来源       |
| 台账             | 进度记录                 | 强调用于上下文恢复时直接写明用途 |
| 裁决             | 代行决策、执行期间的决策 | 避免司法化语气                   |
| 熔断             | 达到重试上限并停止       | 描述条件和结果，不另造术语       |

### P0-5：术语表错误合并了正常的工程概念

证据：

- `CONTEXT.md:60-73` 建议用“模块”替代组件、服务和单元，用“接口”替代 API、签名，用“接缝”替代边界。
- `CONTEXT.md:86-88` 禁止用“任务”表达 `ticket`。
- `skills/codebase-design/SKILL.md` 和架构审查模板进一步执行这些替换。

问题：组件、服务、模块、API、签名和边界在工程设计中并不等价。全局替换会丢失架构信息，也会让文档偏离团队已有语言。

建议：

- `CONTEXT.md` 只定义项目特有概念及它们之间的关系。
- 将“避免”改为适用条件或消歧说明。
- 只有两个词确实表示同一项目概念时才规定首选词。
- 新增 `docs/chinese-writing.md` 承担风格、排版和中英混排规则。

### P0-6：相邻命令的名称无法体现关键差异

证据：

- `README.md:100-101` 中 `/implement` 与 `/implement-spec` 的名称接近，但一个用于当前会话实现少量任务，另一个用于并行交付整份规格。

建议本轮不改命令名，为每个入口提供稳定的中文显示名和“何时使用”说明：

| 命令                             | 建议显示名       | 一句话定位                                           |
| -------------------------------- | ---------------- | ---------------------------------------------------- |
| `/ask-dev-skills`                | 工作流导航       | 不确定下一步使用哪个 skill 时运行                    |

## 4. 中优先级问题

### P1-1：翻译腔集中在动作直译和名词堆叠

典型证据与建议：

| 位置                                  | 当前表达                                   | 建议方向                                                                 |
| ------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------ |
| `docs/invocation.md:13`               | 模型能否有用地自主伸手去用它               | 模型能否在合适场景主动调用它                                             |
| `README.md:101`                       | 工单图前沿并发、台账扛过压缩、上报所有裁决 | 并行执行当前可开始的任务，用持久化进度记录支持上下文恢复，并汇总代行决策 |
| `skills/ask-dev-skills/SKILL.md:85`   | 单一真相源                                 | 唯一权威来源                                                             |
| `skills/wayfinder/SKILL.md:84`        | 毕业成新工单                               | 转化或拆分成新的开发任务                                                 |
| `skills/setup-dev-skills/SKILL.md:42` | 默认姿态                                   | 默认推荐、默认做法                                                       |
| `skills/code-review/SKILL.md`         | 钉住固定点、评审包                         | 确定比较基准、评审材料                                                   |

迁移时不宜执行简单的全局替换。应先判断每句话要驱动的行为，再用中文重新组织。

### P1-2：隐喻密度过高

`README.md` 同时使用“拷问”“盲飞”“大泥球”“曳光弹”“匝道”等隐喻；`skills/wayfinder/SKILL.md` 又连续使用“迷雾”“目的地”“地图”“道路”“毕业”等同一组延伸隐喻。

建议：

- README 每一节最多保留一个帮助记忆的主要隐喻。
- skill 名称可以保留品牌隐喻，操作步骤改用可观察动作。
- 隐喻首次出现时立即给出直白定义，后文不依赖隐喻才能理解规则。

### P1-3：长句影响扫描和执行

静态检查发现多处单行超过 180 个字符，其中包括：

- `skills/writing-for-agents/SKILL-MECHANICS.md:16`：354 个字符；
- `skills/code-review/SKILL.md:62`：307 个字符；
- `skills/to-tickets/SKILL.md:47`：305 个字符；
- `skills/ask-dev-skills/SKILL.md:61`：270 个字符；
- `skills/wayfinder/SKILL.md:80`：274 个字符。

Markdown 源码中的长行本身不是错误，但这些位置通常也包含多个条件、例外和动作。第二阶段应以语义为单位拆分：先写判断，再写动作，最后写例外。

不建议把固定字数作为硬性 lint 规则。验收时检查“一句话是否要求 agent 同时记住多个独立条件”更有意义。

### P1-4：中文标点和中英混排缺少统一规则

证据：

- `README.md:41`、`CONTEXT.md:128-129` 等中文正文使用半角双引号。
- `README.md:113` 等位置用“合并 / 开 PR / 保留”表达中文列举。
- `README.md:59` 等位置写作“红 → 绿”，空格和符号风格不稳定。
- 正文中的 `agent`、`skill`、`issue` 与标题或定义中的 `Agent`、`Skill` 大小写不一致。

建议写作规则：

- 中文引语使用全角引号“”。
- 中文列举使用顿号或列表；斜杠只用于命令、路径和固定技术组合。
- 普通英文技术词统一小写：`agent`、`skill`、`issue`、`diff`、`mock`、`schema`。
- 缩写统一大写：PR、API、TDD、ADR、CI。
- 文件名、命令、字段、标签和代码标识使用行内代码。
- 箭头只用于真正表达状态转换；普通说明优先写“失败后通过”或“红、绿、重构”。

### P1-5：README 偏向项目设计说明，不利于首次使用

当前顺序是安装、五种失败、主流程、完整清单、设计来源。缺少以下关键信息：

- 两种安装方式分别适合谁；
- 安装后的第一个命令是什么；
- 用户输入什么、会得到什么；
- 几个名称相近的 skill 如何选择；
- 一个最小成功路径长什么样。

建议的新结构：

1. 项目定位和适用人群；
2. 60 秒快速开始；
3. 三个典型场景；
4. 主工作流；
5. 精简 skill 导航；
6. 设计原则与上游来源。

完整 skill 清单链接到分类 README；详细设计来源表移入 `docs/`。

三个场景草图：

1. **需求还不清楚**：`/grill-with-docs` → `/to-spec` → `/to-tickets`。
2. **已有明确任务，需要实现**：少量任务用 `/implement`；完整规格需要并行交付时用 `/implement-spec`。
3. **代码坏了或外部 issue 不完整**：可复现问题用 `diagnosing-bugs`；外部报告先用 `/triage`。

### P1-6：frontmatter 没有始终承担好路由职责

重点问题：

- `skills/implement/SKILL.md:3` 与 `skills/implement-spec/SKILL.md:3` 没有在开头突出规模和执行方式差异。
- `skills/grill-me/SKILL.md:3` 与 `skills/grill-with-docs/SKILL.md:3` 使用语气词描述强度，却没有优先说明使用环境差异。
- `skills/tdd/SKILL.md:3` 的“或需要集成测试时”范围过宽，可能让普通的集成测试请求触发完整 TDD 流程。
- `skills/research/SKILL.md:3` 使用了较泛的名称，description 应更明确限定为技术调研、一手资料和落盘产物。
- `skills/wayfinder/SKILL.md:3` 依赖内部隐喻说明用途。

第一阶段改写 description 时，应统一回答三个问题：

1. 什么情况下触发；
2. 产生什么结果；
3. 与最相近的 skill 有什么区别。

### P1-7：“效率”不是合适的分类名称

`skills/` 包含方案追问、教学、交接、外部问卷和重新解释。它们不都以效率为主要目标。

建议中文分类名称改为“协作与思考”。目录名 `productivity` 暂时保持不变，避免产生路径迁移。

## 5. 低优先级与维护风险

### P2-1：易过时的模型容量被写成固定事实

`skills/ask-dev-skills/SKILL.md:51` 和 `skills/ask-dev-skills/PHASE-BOUNDARIES.md:21` 将“智能区”描述为约 15 万 token。模型能力和上下文窗口会变化，也不能用固定 token 数准确表示推理质量。

建议删除固定数字，直接描述判断信号，例如：上下文已接近上限、早期决策难以准确回忆、输出开始丢失约束。

### P2-2：README 与分类 README 重复维护 skill 摘要

同一项 skill 的说明分散在根 README、两个分类 README、`ask-dev-skills` 和 frontmatter 中。重复内容已经出现细微差异。

建议明确唯一权威来源：

- frontmatter 负责触发条件和一句话结果；
- 分类 README 负责面向人的完整导航；
- 根 README 只保留典型场景和少量关键入口；
- `ask-dev-skills` 负责运行时选择流程，不重复项目背景。

## 6. `docs/chinese-writing.md` 草案范围

第一阶段新增的写作规范建议包含以下章节：

1. 目标读者与语气；
2. 中文优先但保留哪些英文技术词；
3. 大小写、行内代码和标点规则；
4. 项目术语与普通工程词的边界；
5. skill description 的写法；
6. 操作步骤的句式：条件、动作、结果、例外；
7. 隐喻使用规则；
8. 修改上游内容时如何验证行为语义没有变化；
9. 正反例对照。

建议至少收入以下对照例：

| 不推荐                   | 推荐                                 |
| ------------------------ | ------------------------------------ |
| 被无情拷问一个计划或设计 | 逐轮澄清并压力测试一个计划或设计     |
| 按设计树逐轮处理前沿     | 每轮询问当前能够确认的全部决策       |
| 每张声明自己的阻塞边     | 每项任务明确列出前置依赖             |

## 8. 验收标准

### 第一阶段

- 命令名、目录名、插件注册路径和触发权限没有改变。
- README 能让首次使用者在 60 秒内确定安装方式和第一个命令。
- README 至少提供三个输入到结果明确的典型场景。
- `/implement` 与 `/implement-spec`、`/grill-me` 与 `/grill-with-docs` 的差异无需阅读 skill 正文即可理解。
- 所有 frontmatter description 都说明触发条件和结果；存在相邻 skill 时说明边界。
- “仅用户触发 / 可自动触发”在所有入口文档中一致。
- “开发任务 / `issue` / 工单”的使用符合场景，不再全局禁止“任务”。
- `CONTEXT.md` 不再禁止 API、组件、服务、边界等普通工程词。
- 中英大小写、行内代码和中文标点符合 `docs/chinese-writing.md`。
- `.claude-plugin/plugin.json` 中的 skill 注册数组与修改前完全一致。

### 第二阶段

- 所有行为约束、确认要求、错误处理和依赖关系与修改前一致。
- 操作步骤可以在不理解上游隐喻的情况下执行。
- 同一段不依赖两个以上未解释的隐喻。
- 模板字段采用团队常见表达，例如“前置依赖”“依赖”“提供”。
- 长句按判断、动作和例外拆分，但不遗漏条件。
- 对所有高风险 skill 做修改前后语义对照，尤其是 `grilling`、`to-tickets`、`implement-spec`、`diagnosing-bugs` 和 `verifying-completion`。
